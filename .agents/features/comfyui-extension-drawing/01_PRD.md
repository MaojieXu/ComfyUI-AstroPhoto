# ComfyUI 扩展底座与绘图节点 · 产品需求

**版本** v0.7 · 2026-11-21 · 现行实现对账与逐项评审稿
**身份** `comfyui-extension-drawing` · 首版软件历史基线 0.0.1

本稿延续 v0.1 的 FR-01～03 编号，将当时放在链接中的产品规则展开为正文，并为原稿未单列的要求分配新编号。Confirmed 来自已有用户决定或采纳基线，Inferred 从已交付行为回溯，Proposed 为本轮建议，Open 等待事实或选择。Observed 记录实际验证，不用于认定产品选择。

## 背景、目标与使用者

工作流作者需要直接在 ComfyUI 中画一张可保存、可再次编辑并可送给图像节点的草图。维护者需要判断扩展到底有没有加载，以及哪个能力因依赖不可用。成功信号是同一工作流重开的像素一致、原生队列的每个阶段可独立观察、降级原因可核实。

工作流作者负责绘图、保存和提交。维护者通过宿主及状态结果排查。ComfyUI 拥有节点、工作流、画布、上传与队列；AstroPhoto 提供绘图及真实状态。独立 MCP 默认诊断可帮助定位连接，不能证明画板或科学处理成功。

## 业务对象及集成边界

一个工作流可以有多个 `vue-basic` 实例，每个节点有自己的 `CUSTOM_VUE_COMPONENT_BASIC` Widget 和画板内容。保存版可带 PNG 像素，提交版引用本次宿主上传的临时文件；下游消费普通 `IMAGE`。状态中的数据根表示配置位置，数据库健康、节点注册和队列成功各自独立。

## 主要场景

- S-01 维护者启动已安装的宿主，查看实际节点目录和状态，遇到数据服务失败时仍能定位扩展与绘图可用性。
- S-02 作者用鼠标或触摸绘图、调整颜色或笔刷大小、清空重画，再用宿主保存并重开；旧空值继续可画，错误 PNG 提示恢复失败。
- S-03 作者将绘图节点连接到 PreviewImage 后排队。浏览器先上传 PNG，再交付临时引用；只有队列成功且下游图像可见才算完整链通过。

## 状态、权限与异常规则

保持既有节点 ID、Widget 键、工作流格式和中英文翻译。损坏图像不得覆盖同图中的其他节点；旧文件未包含像素时无像素可恢复。存储失败、节点未注册、上传失败、正式队列失败是独立状态。扩展报告当前可用性，不借注册成功承诺执行成功。

## 绘图、保存与执行的完整用户路径

| 用户动作 | 用户需要得到的结果 | 当前实现或待验证边界 |
| --- | --- | --- |
| 添加节点、开始绘图 | 在宿主画布添加 `vue-basic`，用画笔、颜色及粗细编辑，并可清空后继续绘图。 | 初始与清空画布为白色，工作流保存像素。底层存在橡皮擦逻辑，当前工具栏没有橡皮擦入口。缩放后的落点和触控取消待单独验证。 |
| 保存、重开或撤销 | 每个实例恢复自己的图像，撤销和重做回放对应状态，其他节点保持原状。 | 工作流值包含 PNG data URL。历史无图值可继续绘制，损坏或不符合尺寸的图像触发恢复错误。两种画布的宿主回放已有迁移运行证据，多实例完整像素仍需独立复验。 |
| 分享工作流 | 接收者能够按选择的分享规则重开工作流，作者知道图像是否随文件传递。 | 当前保存的数据包含画板像素。多节点、含敏感绘图的分享控制由 Q-02 决定。 |
| 恢复尚未完成时编辑 | 明确用户新笔画与保存图像的关系，随后保存和提交的内容一致。 | 当前以版本计数阻止旧的成功解码覆盖更新过的画布。旧解码失败提示、笔画进行中提交与选择的交互方式需按 Q-03 验证。 |
| 排队执行 | 当前画板上传到宿主临时目录，节点输出经下游图像节点显示。用户可以区分上传、排队、执行和结果。 | `graphToPrompt` 的临时引用已有证据。真实 `/prompt`、history 与 PreviewImage 输出需 CASE-03E 逐项记录。 |
| 关闭或移除节点 | 宿主移除绘图控件，相关监听与组件随之结束，其他节点不受影响。 | Widget 清理与宿主回调顺序见开发规格。慢解码与卸载交错需测试。 |

上传过程中断、服务返回错误或文件名缺失时，用户的已保存画板应继续可用，队列结果必须由宿主真实执行结果判断。当前实现没有完整校验上传 HTTP 状态及响应文件名，该要求对应待修复差异，不以现有代码推定通过。 [开发规格](04_DEV.md) · [测试计划](05_TEST_PLAN.md)

## 交付范围与非目标

本期覆盖原生扩展、状态信息、画板编辑、保存恢复及既有 PNG→IMAGE 契约。完整 IMAGE 是历史能力目标，与只验收到 `[temp]` 引用的 P0 前端迁移范围分别记录。FITS 科学链、外部画布操作和独立 MCP 工具属于其他专题。

## 功能需求与验收

### FR-01 宿主加载与状态真实

**状态、必要性及场景** Inferred · 首版必要 · S-01。

宿主发现扩展及实际注册的画板节点；状态提供版本、注册状态、已知数据根和各能力可用性及原因。

**验收** 健康宿主可发现 `vue-basic`；失败的本地存储不会被标成可用；节点缺失时报告降级，重复加载无重复暴露。 [CASE-01](05_TEST_PLAN.md)

### FR-02 画板编辑与像素持久化

**状态、必要性及场景** Confirmed · 首版必要 · S-02。

鼠标和触摸可绘图，调整笔刷、颜色与清空；宿主保存和重开恢复对应实例的 PNG，旧空工作流仍可编辑。

**验收** 两实例画不同图，重开后逐像素一致且互不串图；坏 PNG 给本地化反馈；清空重开仍为空。原生撤销和重做应验证相应节点像素及保存值回放。 [CASE-02](05_TEST_PLAN.md)

### FR-03 PNG 上传、引用和下游 IMAGE

**状态、必要性及场景** Inferred · 首版必要 · S-03 / FR-02。

提交时上传当前画板 PNG，并提供有效临时引用给原生队列。保持宿主 LoadImage 委托和 IMAGE 输出契约；产品验收分上传和正式执行两级。

**验收** 上传拒绝、HTTP 错误或无有效文件名时，不应产生有效引用，也不能展示队列已生成图像。真实宿主分开取得上传成功、`[temp]` 引用、成功 history 和 PreviewImage 输出。已有迁移采样只支持前两项，正式执行待复验。 [CASE-03](05_TEST_PLAN.md)

### FR-04 宿主集成与发行边界

**状态、必要性及场景** Inferred · 首版必要 · S-01。

依托宿主原生 UI、生命周期和资源分发，Extension 与 MCP 独立发行并保持版本同步；运行图和设置由宿主持有。

**验收** 宿主通过一个扩展前端入口发现画板；本地构件含所需资产及翻译，排除历史工作资料和运行数据；独立安装后分别检验版本与宿主加载。 [CASE-04](05_TEST_PLAN.md)

## 证据、冲突与限制

**Observed**。历史 Windows ComfyUI 0.45.0 / Frontend 1.59.1 的真实宿主已读到节点和状态；`test:host --skip-image-execution` 的 16 项记录覆盖像素重开并明确跳过 IMAGE。历史失败及 P0 目标宿主结果须单列。

**当前源码。** 构建入口已切至 `extension/frontend-entry.ts`，画板由公共 Vue 入口注册到原生 DOM Widget。工作流值仍保留 PNG，prompt 仍使用临时引用。画板用 revision 防止旧解码成功后覆盖新笔画，新笔画若抢在恢复完成前开始，旧像素可能未显示。现有上传代码解析 JSON，但没有单独校验 HTTP 状态及文件名。

**既有试验采样。** 两类画布的迁移报告分别记录了旧画板像素和临时引用。现行 `js/main.js` 与留存候选产物的 SHA-256 不同，这些报告范围未到绘图节点的正式队列。 [迁移报告 06-A/B](../archive/comfyui-frontend-stack-migration/06_TEST_REPORT.md) · [交互状态](02_UI_UX.md) · [守卫与差异](04_DEV.md)

**Open · 当前评审。** 如果正式队列的下游 IMAGE 仍失败或缺成功证据，下一次完整发行如何处理？

| 选项 | 具体规则 | 优点 | 缺点与影响 |
| --- | --- | --- | --- |
| **A（建议）分阶段发行** | 其他发行条件满足时允许发行。发布说明明确当前已验证到临时引用，正式 IMAGE 未通过前列为未完成能力，并继续独立复验。 | 其他已验证功能可以先交付，问题及其影响有明确记录。 | 用户暂时不能依赖绘图节点的完整输出链，维护者需要持续跟踪和清楚说明限制。该 Feature 的最终关闭仍需依据已确认的验收规则判定。 |

### Q-02 分享与多实例

**Open**。共享工作流会携带画板图像。含私人画板或大量绘图节点时，用户需要什么控制？

| 选项 | 具体规则 | 优点 | 缺点与影响 |
| --- | --- | --- | --- |
| **A（建议）保留原生分享** | 继续随工作流保存图像并提示分享者。需要无图副本时，复制工作流、逐个清空画板、另存并复查。 | 工作流可携带完整画板并在接收端恢复，沿用现有宿主保存方式，实现改动较小。 | 多节点时清理耗时，用户可能遗漏节点，需要提供清晰说明并验证副本和原件。 |
| **B 增加无图导出** | 提供可选的无绘图内容副本，普通保存仍保留像素。导出后其他节点、连接和原工作流保持原状。 | 分享多个画板的工作流更方便，降低手动遗漏画板的机会。 | 需要增加导出入口与宿主集成，定义副本格式、失败反馈和多实例测试，还需维护两种保存结果。 |

**影响及证据** FR-02、UI/UX 分享规则、CASE-02E。测试多节点文件、无内容副本和原件保护。B 还需新增开发任务。

### Q-03 保护已保存画板

**Open**。异步恢复未结束、切换画板模式或用户立即开始画时，谁拥有最新内容？

| 选项 | 具体规则 | 优点 | 缺点与影响 |
| --- | --- | --- | --- |
| **A（建议）允许立即编辑** | 画板保持可编辑，用户开始的新编辑优先，迟到的旧图不能覆盖新内容。提示和提交等待的细节依据竞态测试确定。 | 用户无需等待即可操作，接近当前版本计数的实现方式。 | 旧图尚未显示时，用户可能在白板上开始绘图，新结果可能不含旧图。需要说明这一行为并补测旧错误提示及笔画中提交。 |
| **B 恢复完成后编辑** | 恢复期间显示状态并暂时禁止编辑，成功后解锁旧图，失败后提示并解锁。 | 用户通常能在已保存的图上继续编辑，恢复期间的交互规则更明确。 | 慢设备或大工作流需要等待，需要增加加载、失败和解锁状态，并验证取消、卸载与队列行为。 |

**影响及证据** FR-02、UI/UX、TECH、DEV 和 CASE-02D。代码已给旧成功结果做 revision 检查；旧失败提示和活跃笔画期间准备 prompt 仍需受控复验。

### Q-04 上传失败时如何阻止执行 · P0

现状：上传异常返回 `{image:null}`，Python 节点拒绝非字符串。HTTP 错误返回 JSON 或响应缺少 name 时，当前前端仍可能拼接无效路径。宿主如何呈现由实际队列验证。

| 选项 | 优点 | 缺点与影响 |
| --- | --- | --- |
| **A（建议）明确校验并阻止本次提交** | 校验 HTTP 成功和有效文件名，提供可理解的失败提示，保留画板与工作流，避免伪有效引用。 | 需核实宿主序列化错误传播机制并修改前端；排队整体是否中止由宿主契约和测试确定。 |
| **B 返回空引用并由后端报错** | 接近当前异常路径，修改范围较小。 | 错误较晚且可能不易定位，仍必须先杜绝无效名称拼接；要验证队列不会显示成功。 |

影响 FR-03、CASE-03C/D/E。证据包括断网、非 JSON、HTTP 错误 JSON、缺名、无效名称及重试后画板像素。

### Q-05 进行中的笔画与提交快照 · P0

现状：组件在笔画结束保存快照，提交读取组件已保存的 Canvas 数据。笔画中发起保存或排队的实际时序尚未验证。

| 选项 | 优点 | 缺点与影响 |
| --- | --- | --- |
| **A（建议）先完成当前笔画再提交** | 保存和排队均针对用户可见的完整笔画，状态容易理解。 | 需定义指针仍按下、失焦、触控取消和节点卸载时如何结束，可能干预当前交互。 |
| **B 只使用最近已完成的笔画** | 实现较直接，提交不会等待输入事件。 | 用户可能看到半笔画但提交结果缺少它，需明显提示并测试保存与队列一致性。 |

关联 Q-03、Q-10，影响 FR-02/03、CASE-02A/D 和 CASE-03A/E。

### Q-06 已保存 PNG 损坏或尺寸不符 · P0

现状：恢复要求 PNG data URL 与 300×300，失败会显示提示。后续编辑可能产生新的保存值，损坏原值能否在各种宿主自动保存场景保留仍需验证。

| 选项 | 优点 | 缺点与影响 |
| --- | --- | --- |
| **A（建议）保留原值并要求用户明确开始新图** | 用户有机会保存副本和排查，减少误覆盖已有内容。 | 需要错误状态、明确操作和保存/排队规则；用户多一次操作。 |
| **B 直接允许在白板继续编辑** | 用户可以立即恢复工作，交互简单。 | 后续保存可能替换不可恢复的原始值，需要清晰提醒并验证撤销、自动保存和多实例隔离。 |

影响 FR-02、CASE-02C/D/F。旧空值与损坏图需分开处理。

### Q-07 临时上传的身份、重试和生命周期 · P0

现状：文件名使用时间戳，目录为宿主 temp；代码每次序列化上传。并发同毫秒命名、重复提交以及宿主清理时序尚无充分证据，是否冲突依宿主行为验证。

| 选项 | 优点 | 缺点与影响 |
| --- | --- | --- |
| **A（建议）每次提交独立上传并校验回执** | 各次队列可以绑定当次像素，避免依赖过期临时文件；便于隔离失败。 | 需要唯一命名或依靠经验证的宿主去重行为，重复提交产生额外 I/O 和临时文件。 |
| **B 复用已上传引用** | 重复排队可减少上传和临时文件。 | 必须验证内容身份、宿主重启和清理策略，旧引用失效时需要重新上传，否则容易执行旧图或失败。 |

影响 FR-03、CASE-03A/B/E。测试同节点与多节点并发、重试、宿主重启和临时文件失效。

### Q-08 画布尺寸与旧工作流兼容 · P1

现状：Widget 固定 300×300，恢复拒绝其他尺寸。数据为 PNG 像素，未保存笔画矢量。

| 选项 | 优点 | 缺点与影响 |
| --- | --- | --- |
| **A（建议）首版固定 300×300** | 输出尺寸稳定，旧工作流与下游预期清楚，验证范围可控。 | 大画布需求无法直接满足，未来改变尺寸须定义迁移规则。 |
| **B 支持可配置尺寸** | 适合不同工作流和精度需求。 | 需要限定尺寸、资源预算、缩放/裁剪策略及旧文件兼容，现有恢复检查需调整。 |

影响 FR-02/03、工作流格式、输出尺寸与 CASE-02C/03E；B 属新增能力。

### Q-09 清空后的恢复保障 · P1

现状：清空立即填白并保存快照，真正修改时通知宿主图变更；宿主撤销在已有双画布迁移样本中有证据。

| 选项 | 优点 | 缺点与影响 |
| --- | --- | --- |
| **A（建议）直接清空，依赖宿主撤销** | 保持操作迅速，沿用原生工作流编辑体验。 | 用户需知道撤销入口，撤销历史在重开后是否存在由宿主决定，多实例和清空恢复需验证。 |
| **B 清空前确认** | 降低误触立即清空的概率。 | 增加频繁操作的步骤，需处理键盘、无障碍和确认期间节点移除。 |

影响 FR-02、CASE-02A/F。两选项都须验证清空后保存和原生撤销。

### Q-10 坐标、触控中断与设备范围 · P1

现状：鼠标使用 offset 坐标，触摸使用相对显示矩形坐标；没有明确的尺寸比例换算和 touchcancel 分支。

| 选项 | 优点 | 缺点与影响 |
| --- | --- | --- |
| **A（建议）支持缩放及触控中断** | 鼠标与触摸在缩放、窄节点下仍能按位图坐标绘制，中断后状态可恢复。 | 需明确离开画布、取消、多个触点与浏览器事件规则，增加设备覆盖。 |
| **B 首版限定验证过的交互环境** | 可以先限定交付范围并降低设备测试成本。 | 部分缩放或触控场景可能落点偏移或笔画未提交，需要明确告知支持范围。 |

关联 Q-05，影响 FR-02、CASE-02A。需要真实设备或可信浏览器事件与像素对照。

### Q-11 普通 IMAGE 的像素语义 · P0

现状：白色背景，画板生成 PNG；Python 委托宿主 LoadImage 并只返回 IMAGE，宿主返回的 mask 被丢弃。真实完整输出仍待执行验证。

| 选项 | 优点 | 缺点与影响 |
| --- | --- | --- |
| **A（建议）承诺白底普通 IMAGE** | 语义贴近现有画板，用户可用颜色直接连接普通图像节点，契约较简单。 | 不提供透明度或独立 mask，后续科学数据仍需使用专门类型。需实测尺寸、通道与像素值。 |
| **B 增加透明或 MASK 输出** | 用户可直接把绘图作为遮罩使用。 | 需要定义透明背景、反相、通道与节点兼容，并修改 schema 和旧工作流验收；属于新增范围。 |

影响 FR-03、CASE-03D/E。IMAGE 成功与科学 FITS 精度是不同需求。

### Q-12 状态接口的数据根披露 · P1

现状：状态响应包含配置的数据根，存储与设备操作使用独立授权；状态在不同部署下的可见范围需按真实宿主取证。

| 选项 | 优点 | 缺点与影响 |
| --- | --- | --- |
| **A（建议）状态保留能力与原因，路径仅在受信条件返回** | 共享宿主可减少暴露本机路径，诊断仍能看到能力状态。 | 需定义受信判断与无路径时的诊断方式，可能影响已有调用方和 MCP 兼容。 |
| **B 延续当前状态字段** | 已有诊断消费者保持兼容，排错可直接看到路径。 | 状态可访问者可能看到本机路径，部署与分享说明需明确这一行为。 |

影响 FR-01、CASE-01C、状态 API 与 MCP 消费方。权限变化须作为接口变更评审。

### Q-13 工作流体积和多实例性能 · P1

现状：每个实例把 PNG data URL 写入工作流，完整大小与图像内容和节点数相关，当前未定义预算或性能基线。

| 选项 | 优点 | 缺点与影响 |
| --- | --- | --- |
| **A（建议）先测量并给出支持预算** | 保持离线自包含和现有兼容，按实际加载/保存耗时决定阈值。 | 工作流体积仍随节点数增长，需要代表性设备、复杂图和多实例基准。 |
| **B 改为外部图像引用** | 工作流 JSON 可以更小。 | 分享、路径失效、跨机器移动、清理和备份复杂，需设计迁移与可移植性。 |

影响 FR-02、Q-02、CASE-02B/E，阈值在测量前保持待定。

### Q-14 宿主兼容范围和升级策略 · P1

现状：目标宿主 0.46.0 / Frontend 1.59.6 的迁移证据与历史 0.45.0 / 1.59.1 分开，类型包版本和实际宿主版本不同。

| 选项 | 优点 | 缺点与影响 |
| --- | --- | --- |
| **A（建议）先明确单一已验证组合** | 发行支持声明可核验，回归矩阵和排障责任清楚。 | 其他宿主版本需要自行验证，用户升级可能遇到未覆盖的 Widget 或队列差异。 |
| **B 承诺版本范围** | 用户升级选择更灵活。 | 需要明确上下界并持续运行多版本、两种画布和保存/队列回归，维护成本更高。 |

影响 FR-01/04、CASE-01A、CASE-02F、CASE-03E 和发布说明。

### Q-15 绘图工具范围与可访问性 · P1

现状：工具栏提供画笔、颜色、粗细和清空。底层橡皮擦逻辑没有可见入口；颜色有标签，粗细滑杆的标签关联和键盘操作需验证。

| 选项 | 优点 | 缺点与影响 |
| --- | --- | --- |
| **A（建议）按现有工具交付并补齐可访问性** | 产品承诺与现有界面一致，集中验证键盘、名称和焦点。 | 局部擦除需求暂时没有可见入口，用户只能撤销或清空。 |
| **B 增加橡皮擦入口** | 支持局部修改，减少整图重画。 | 需明确擦除为白色还是透明、粗细共用、撤销粒度与输出语义，需新增 UI 与像素测试。 |

关联 Q-11，影响 FR-02、CASE-02A/F，B 属新增能力。
