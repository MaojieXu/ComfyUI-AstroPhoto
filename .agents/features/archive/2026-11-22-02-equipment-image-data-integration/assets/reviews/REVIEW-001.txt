 3. Findings（按严重度）

 ### F-01 · High · 直传导入没有"失败/放弃/崩溃"终态，位置维护被永久占用

 - 位置：astrophoto/assets/direct_import.py:296（仅 copied == total 才置 completed）、:301-305（_failure 只改条目，不改任务）、:99-103（close() 只
   set 取消事件）、:337-341（writing 只在异常路径撤销）；astrophoto/storage/locations.py:25-32（check_idle_direct_imports：phase == "importing" 且
   status != "copied"）；astrophoto/storage/operations.py:86（活动任务 = phase not in
   TERMINAL）；astrophoto/storage/operations.py:159-168（recover() 只遍历 StorageOperation，不覆盖 direct_import 记录
   ）；astrophoto/storage/migration.py:156、:349-350（.staging 非空即 RECOVERY_REQUIRED）
 - 触发：任一帧失败（SOURCE_CHANGED/INSUFFICIENT_DISK_SPACE/OBJECT_CONFLICT）后用户离开导入页而未点"取消"；或传输中关闭/重启宿主（_stage 因 closing
   抛 STORAGE_BUSY，_put 故意不标记失败，条目停在 pending + writing）。
 - 代码依据：_failure() 只写条目 status=failed；status() 直接返回 job["phase"]；phase 只在 _publish 的全量成功分支被改为 completed，cancel() 是唯一
   的另一种出口。check_idle_direct_imports 把 status != "copied" 全部视为"在途"，包含 failed，因此 WorkspaceMigrationService.remove_location() 与
   start() 对该位置一律抛 STORAGE_BUSY（HTTP 423）。启动时 Operations.recover() 不处理直传任务，故重启也不会收敛。
 - 影响：AC-26（删除位置并迁移）在"曾经失败过一次导入"的位置上无法执行；/storage/operations 永久把该任务列为活动项（TaskPanel 中运行任务不可清除
   ，TaskPanel.vue:dismiss 仅对 terminal 生效），AC-27 的"结束任务可清除"不成立。与常规导入形成不对称：StorageOperation(kind="import") 失败即
   terminal，可释放位置。
 - 建议修复：为直传任务引入显式终态（如 partial / abandoned，或 importing + last_activity 超时），并把 check_idle_direct_imports 的阻塞条件收窄为真
   正可能继续写入的条目（pending/writing）；在 StorageRuntime.initialize 对 direct_import 记录做一次对账（清理无 writing 的 .staging、把长期无进展
   的任务置为终态）；UI 增加"放弃任务"。

 ### F-02 · High · 删除唯一审批决策入口后，MCP 提案队列无回收路径，100 条后永久 423

 - 位置：astrophoto/api/library.py:54-58（required_approval）、:66-72（Agent 请求转 propose）、:88-96（propose，pending >= 100 → STORAGE_BUSY）、
   :104-119（approvals/decide，均 if is_agent: raise）；本增量删除 frontend/src/features/assets/LibraryApprovals.vue（清单
   status=deleted），frontend/src 内已无 approvals 调用方（仅留 i18n 字符串）
 - 触发：MCP 客户端调用 library_create(assets/collections/masters/assignments)、library_update(assets)、library_delete(assets|projects|folders) 或
   library_import_request。这些调用按设计返回 202 pending；而 POST /library/approvals/{id} 只接受浏览器请求，且本次已移除唯一调用它的界面。
 - 代码依据：propose() 计入 status == "pending" 的记录，达 100 即对后续所有需审批写入返回 STORAGE_BUSY；decide() 是唯一改变状态的路径；GET/DELETE
   /library/{kind} 的 KINDS 不含 approvals，无删除接口；全仓无过期/清理逻辑（grep '"approvals"' astrophoto/ 仅命中上述 7 处）。
 - 影响：MCP 的敏感写入从"待审批"变为不可恢复的死状态；累计 100 条后（无需用户操作，Agent 重试亦可）永久拒绝后续所有需审批写入，只能改数据库恢复。
   这直接阻断 AC-07，并使 FR-04"返回可区分的成功、待审批或错误结果"在实际流程上不可闭环。注意：设备/组合工具本身是只读的（见 Q-01），本项仅影响素材
   库写入。
 - 建议修复：Q-03 定案前，先补一条服务端过期/撤销机制（超时 pending → expired，或用户侧一次性 denied 批量清理），并让 propose 的 100 条上限只在"有
   决策通道"时生效；否则应暂时关闭需审批的写入路径，避免产生不可消费的提案。

 ### F-03 · Medium · publish_stat 无可用字节时条目永久不可完成

 - 位置：astrophoto/assets/direct_import.py:347-352（expected = data.get("publish_stat")，有值则 needed=0 且跳过 _stage）、:268-277（_publish：dest
   不存在时 identity(stage)，stage 已被 rename 走后抛 SOURCE_NOT_FOUND）、:364-393（cancel 先删 stage/dest 再清 writing/publish_stat，两步非原子）
 - 触发：cancel() 删除了 stage/目标文件后、在清除 writing/publish_stat 前崩溃或 DB 写失败；或已 publish_stat 落库、目标文件随后被外部删除/所在盘脱
   机。
 - 代码依据：_stage 一旦成功即持久化 publish_stat 并移走 stage（publish_object 为 rename，stage 不再存在）；_put 看到 publish_stat 就永不重新暂存
   ；_publish 只有 dest 存在才跳过 identity(stage)，故 dest 缺失时直接 SOURCE_NOT_FOUND，并被 _failure 记为条目失败，下一次重试仍走同一分支。
 - 影响：该帧永久无法完成，任务无法 completed，叠加 F-01 使位置长期不可维护；用户侧只能靠再次 cancel() 脱困。
 - 建议修复：_publish 在 dest 与 stage 均不存在时清除 publish_stat/writing 并回落到 _stage；cancel() 的文件删除与字段清除应可在重启后依据持久记录重
   放（例如先写"cleanup intent"，再删文件）。

 ### F-04 · Medium · 发布阶段失败遗留 .staging/direct-*.part，占用空间并阻塞迁移

 - 位置：astrophoto/assets/direct_import.py:270-284（dest.exists() 为真但 identity 不符 → OBJECT_CONFLICT；publish_object 竞态失败亦同）、
   :301-305（_failure 不清理文件）、astrophoto/storage/migration.py:349-350、:156
 - 触发：目标路径已存在同键异内容文件，或 publish_object 的"存在性检查→rename"之间被其他写入抢先。
 - 代码依据：_stage 在其自身异常路径会 remove_stage，但 _publish 抛出时 _stage 已正常返回，没有任何清理；stage 文件带 writing=True 持久化，只有
   cancel() 会删除。
 - 影响：磁盘空间泄漏；.staging 非空会让迁移预检与 remove_location 直接报 RECOVERY_REQUIRED（即使任务已被取消以外的方式解除），是 AC-26 的另一个失
   败面。
 - 建议修复：_publish 的失败分支删除本次 stage（保留 publish_stat 以便目标侧重试），或在 _failure 中按条目清理；同时在启动对账中清扫无归属的
   direct-*.part。

 ### F-05 · Low · AssetLocation 唯一约束冲突以 500 泄漏，条目停在半状态

 - 位置：astrophoto/assets/direct_import.py:283-293（session.add(Asset/AssetLocation) 无冲突映射）、:340-343（_put 仅捕获 StorageError/OSError）
 - 触发：目标 (workspace_id, relative_key) 已被另一条 AssetLocation 占用而其文件缺失（例如 delete_file 保留了登记、文件已删），而本条目 dest 恰好不
   存在，publish 成功后 INSERT 触发 IntegrityError。
 - 代码依据：AssetLocation.__table_args__ 有 UniqueConstraint("workspace_id","relative_key")（astrophoto/database/models.py:61-64）；IntegrityError
   不是 StorageError，穿过 _put 到 handler() 的通用兜底 → INTERNAL_STORAGE_ERROR(500)；文件已发布、writing/publish_stat 保留。
 - 影响：该帧重试永远 500，任务无法完成（叠加 F-01 的维护阻塞）。触发面窄，故定为 Low。
 - 建议修复：在发布前用 SELECT 检查键占用并映射为 OBJECT_CONFLICT，或在 _publish 内捕获 IntegrityError 转为业务错误并回滚条目状态。

 ### F-06 · Low · 已结束/已取消的直传任务丢失逐帧错误详情

 - 位置：astrophoto/storage/operations.py:98（if job["phase"] == "importing" 才附带 receipt.errors）
 - 触发：用户取消一个含失败帧的任务，或任务在失败后被放弃。
 - 影响：AC-27 要求任务框"展开后显示…结果和错误详情"；取消后错误列表与任务一起消失，用户无法回看哪些帧失败及原因（条目记录仍在库中，但无读取入口）
   。
 - 建议修复：无论 phase 均返回 errors（或返回 failed 计数 + 前 N 条），仅在 UI 端按终态折叠。
