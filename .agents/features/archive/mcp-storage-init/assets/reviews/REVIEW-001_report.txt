 3. 结论

 无阻断性问题。 init 闭环的核心实现与 PRD/ TECH 主体一致：

 - 数据根取自活宿主 runtime.storage.root（runtime.py:158-183），MCP 不做位置推算；
 - 写入仅限 workspace/{objects,outputs,.staging}/、runtime/migrations/ 与不覆盖的 runtime/workspace-<id>.json，从不改写 manifest/settings/DB/身份标
   记（runtime.py:164-176）；
 - 先只读预检（身份、DB、工作区标记与文件审计、缓存标记），再在 lease → bootstrap lock（与 update/remove/relocate/migration.run 相同的既有顺序）内
   重读配置与默认 ID，默认目标切换即返回 STORAGE_BUSY；
 - 幂等：第二次调用 created=[]；中断后保留已创建项、以磁盘现状收敛；并发得到可串行或 STORAGE_BUSY；
 - HTTP 侧复用本机单用户授权、空 JSON {} 契约、工作线程与既有错误映射；MCP 侧单次 POST、无参 schema、直连回环 + trust_env=False/禁止重定向、回执严
   格校验、错误码与 request_id 透传。

 以下 6 项为非阻断发现，其中 F-02 建议在 TEST_REPORT 前明确决策。

 4. Findings

 ### F-01 · Low（非阻断）· MCP 对可恢复类存储错误的"下一步"指引覆盖不足

 - 文件/符号：mcp/src/astrophoto_mcp/tools/init.py:69-85（_http_error guidance 映射）
 - 描述：指引只对 403/423/507 与 RECOVERY_REQUIRED / DATABASE_INVALID / WORKSPACE_IDENTITY_MISMATCH / CACHE_IDENTITY_MISMATCH 给出针对性操作。
   WORKSPACE_OFFLINE、WORKSPACE_FILES_MISSING、WORKSPACE_DISABLED、TARGET_NOT_EMPTY 等业务码落到 "Check the storage configuration and the ComfyUI
   log, then retry init."（line 82-83）。
 - 证据：astrophoto/api/errors.py 中这些码均映射 409；runtime.py:127（WORKSPACE_OFFLINE）、runtime.py:136（WORKSPACE_FILES_MISSING）、
   locations.py:283-286（require → WORKSPACE_DISABLED）证明其可达。mcp/tests/test_init.py:test_init_preserves_storage_error_and_request_id 只覆盖
   404/409(RECOVERY_REQUIRED)/403/423。
 - 影响：外置默认工作区所在卷离线、注册文件缺失、工作区被停用时，回执要求"重试"，而重试永不成功；与 PRD FR-04「回执说明失败环节及下一步」和 PRD 用
   户目标「用户能按回执处理并重试」存在落差（错误码本身正确稳定，不涉及数据安全）。
 - 建议：为该组码补可执行指引（重新挂载卷 / 恢复缺失文件或在侧栏重定位 / 启用工作区），并补 1 条 MCP 单测断言指引文本。

 ### F-02 · Medium（非阻断，建议决策）· 无位置记录的既有数据根在 init 中不可恢复，且与 snapshot 判定自相矛盾

 - 文件/符号：astrophoto/storage/locations.py:86-99（missing_layout_evidence）、locations.py:226-241（check_status）、
   astrophoto/storage/runtime.py:133-135（_layout_gaps 调用点）
 - 描述：runtime/workspace-<id>.json 位置记录是本工作树新增的产物（git grep 在 HEAD 中无任何写入点）。对"先于本实现创建、且从未登记受管资产/成片"的
   数据根：
     - check_status：evidence={} → known_path=False → 只看工作区标记 → 报 online，GET /astrophoto/v1/storage 的 status 为 ready；
     - ensure_layout：audit_files 返回空 → corroborated=False → missing_layout_evidence 抛 RECOVERY_REQUIRED（"Missing workspace location record
       and no independent location evidence"）；
     - 产品内无补救路径：relocate 要求工作区 offline 且同样要求 same_directory or corroborated（locations.py:320-341）；register 因同一路径已登记而
       报 WORKSPACE_IDENTITY_MISMATCH；validate 不写记录。
 - 证据：runtime.py:120-137 的顺序（审计 → 证据 →
   require）；tests/backend/test_storage_init.py::test_reentry_preserves_conflicting_or_uncorroborated_workspace_evidence（conflict=False 分支）显
   式断言此错误，说明是刻意的保守行为，与 TECH §3「位置记录缺失时仅在数据库登记、磁盘标记和独立位置证据足以确认同一目录时才可原子补写」一致。
 - 影响：升级后的既有实例（无导入数据）会出现"存储页显示就绪、init 永远报 RECOVERY_REQUIRED"，且回执无可行下一步。AC-02 的自动化用例使用本版本创建
   的根（记录已写入），无法暴露该状态。
 - 建议（择一，需 Main Agent 判定）：① 明确该状态为受支持结论，在 docs/local-storage.md/docs/mcp.md 记录人工恢复步骤并在 TEST_PLAN 增加"旧版本数据
   根（无记录、无资产）"用例与预期回执；② 或补 TECH 增补：当 DB 登记的 root_path 与磁盘路径一致且工作区标记 (instance_id, workspace_id) 匹配时，视
   为足以确认同一目录并原子补写记录；③ 同时消除 check_status（online）与 ensure_layout（RECOVERY_REQUIRED）的口径差异。

 ### F-03 · Low（非阻断）· 宿主启动失败的具体原因未进入 MCP 回执

 - 文件/符号：astrophoto/bootstrap.py:initialize_storage_runtime（runtime.storage_error = exc.code）、
   astrophoto/api/storage.py:176-178（respond(StorageError(code), request_id)）、mcp/.../tools/init.py:84（reason != code 时丢弃 detail）
 - 描述：宿主只保留错误码，HTTP 错误 message 等于码本身，MCP 因此丢弃 detail；"manifest 缺失"与"settings 损坏"两种失败的 MCP 文本完全相同。
 - 证据：tests/integration/test_storage_init.py::test_stdio_init_preserves_a_failed_startup_and_recovers 两个参数化分支断言的都是
   "RECOVERY_REQUIRED" in text（无法区分）。
 - 影响：PRD AC-04「工具报告存储未就绪及宿主提供的原因」只满足到稳定错误码层面；TECH §2 的失败表仅要求"沿用分类、保留原始存储错误码"，因此实现与
   TECH 一致，属 PRD 措辞与设计的细小落差。
 - 建议：把 str(exc)（不含绝对路径等敏感信息）作为 message 透传，或将该 AC 的判定口径写进 TEST_REPORT。

 ### F-04 · Low（非阻断）· 公开接口文档未登记 POST /storage/init，协调目录无文档

 - 文件/位置：docs/local-storage.md:83-105（方法/相对路径表）、astrophoto/storage/data_root.py:23-27（~/.astrophoto-control、roots.json）
 - 描述：TECH §4 步骤 4 要求"同步双端使用说明和公开接口文档"。docs/mcp.md 已写工具与端点，但 docs/local-storage.md 的路由表缺少 POST
   /astrophoto/v1/storage/init；bootstrap.py 现在每次宿主启动都会创建 ~/.astrophoto-control/（catalog + <instance>.lock），docs/、mcp/README.md、
   .agents/handoff/ 中均无记载。
 - 影响：文档与实现不同步；用户/后续维护者不了解默认情况下用户目录会新增该协调目录（不构成"另建默认数据根"，无配置文件/数据库，与 AC-02 不冲突）。
 - 建议：路由表补一行（请求 {}、结果形状、created 语义）；在存储/协议文档与 Handoff 中登记协调目录及其用途边界。

 ### F-05 · Low（非阻断，测试覆盖缺口）· TC-07 的"持有工作区锁"场景无确定性自动化入口

 - 文件/位置：tests/backend/test_storage_init.py::test_concurrent_init_converges_and_retry_preserves_completed_steps
 - 描述：该用例容忍"两线程串行都成功"或"一方 STORAGE_BUSY"，即 ensure_layout 的 lease 抢占失败路径（locations.py:163-169 + runtime.py:167）只在竞态
   下偶然覆盖；TEST_PLAN TC-07 明确列出的"持有工作区锁"没有确定性用例。_initialize 启动期补齐（runtime.py:96-104）也只有一条"删空 migrations 后重启
   "的正向用例，缺少"在途操作时启动不补建"的断言。
 - 影响：423/STORAGE_BUSY 与"启动期延后补齐"两条路径的回归保护偏弱（非缺陷，属覆盖缺口）。
 - 建议：用 service.workspaces.lease(workspace_id) 显式占住租约后断言 ensure_layout 抛 STORAGE_BUSY 且未写入；补一条"存在非终态操作时重启不创建
   migrations"的后端用例。

 ### F-06 · Info · 两处健壮性细节

 - 文件/位置：astrophoto/storage/runtime.py:158-163（锁目录 samestat 校验在获取租约之前）、
   runtime.py:96-104（directories["runtime/migrations/"].mkdir()）
 - 描述：① 锁目录同一性核验位于锁外，加锁后未复检，存在窗口（TECH 要求"在锁内……核对默认 ID 和目录身份"）；实际写入目标不受影响，最坏产生误导性
   busy/成功。② 启动期补齐依赖 _layout_gaps 返回的字典必含 runtime/migrations/ 键，仅靠分支条件与 _layout_gaps 的 .exists() 两次判断一致来保证，理
   论上可触发 KeyError 并被降级为 STORAGE_INITIALIZATION_FAILED。
 - 建议：把锁目录核验移入 with lease, lock 之后；_initialize 用 directories.pop("runtime/migrations/", None) 后判断再创建。
