 2. Findings

 ### R-01 · 中 · 启动路径新增对账号级协调目录的硬依赖，失败时缺目标路径诊断

 - 位置：astrophoto/bootstrap.py::initialize_storage_runtime（52–83）、
   ::host_runtime（86–102）；astrophoto/storage/data_root.py::DataRoots.__init__（41–47）、::_read（49–55）
 - 描述：HEAD 的宿主启动直接 StorageRuntime.initialize(config.data_home, …)；本次改为经 DataRoots().open()。DataRoots.__init__ 立即
   self.directory.mkdir(exist_ok=True, parents=True, mode=0o700) 并读取 roots.json，open() 还要取 catalog.lock / <instance>.lock。这些账号级路径不
   在四个验收目录内，若 ~/.astrophoto-control 不可创建（只读 HOME、容器、托管账号），启动会在补齐之前整体失败，四个目录与两份 JSON 均不会生成。
 - 证据：DataRoots.__init__ 无 try/except；_read 抛 StorageError("RECOVERY_REQUIRED", "The active Data Root record cannot be read")（无 details）。
   bootstrap 中 _PUBLIC_RECOVERY_MESSAGES 不含该消息，且 details is None 时走 logger.exception("AstroPhoto storage startup failed")，日志只有
   traceback、无目标路径；runtime.storage_error_message 保持 None。
 - 影响：受限账号下 FR-01/AC-01 首建不可完成且难定位；AC-04 的"报告原因/target path"只覆盖数据根内路径，不覆盖协调目录与 roots.json。
   recover_cache/coordinate 同时被绑定（recover_cache=coordinate），语义耦合也使该参数无法独立关闭协调。
 - 修复建议：(a) 在 TECH 登记"账号级协调目录可写"为启动前置条件，并给出该前置失败时的期望（TEST_PLAN 已要求隔离 ~/.astrophoto-control，但未写不可写
   时的期望）；(b) 为 DataRoots.__init__/_read 的失败补 details={"path": …} 与固定公开原因；(c) 将 recover_cache 与 coordinate 解耦为独立参数，避免
   测试替身只能二选一；(d) 增一条"协调目录不可写 / roots.json 损坏"用例，断言只读不动四目录与两份 JSON。

 ### R-02 · 中（覆盖缺口） · 启动补齐主路径无任何自动化断言

 - 位置
   ：astrophoto/storage/initializer.py::ensure_top_level_directories（76–78）；astrophoto/storage/data_root.py::DataRoots.open（120–129）；tests/in
   tegration/test_status_api.py::test_v3_load_registers_one_live_status_route
 - 描述：ensure_top_level_directories 在 tests/ 中零引用（全仓 grep 仅命中源码）。启动补齐分支仅被 test_status_api 间接经过"空根首建"，且该用例只断
   言 data/database/assets.db 存在，不断言四目录、两份 JSON、ID 有效性；已初始化实例缺 database/、storage/、runtime/ 的同次补齐（AC-03）、组合缺失
   （AC-05）、路径为普通文件（AC-04 冲突）全部无自动化证据。
 - 证据：tests/integration/test_status_api.py 全文 53 行，断言仅 assets.db 与 status 字符串；tests/backend/test_storage_init.py 仍围绕旧
   ensure_layout()/init 契约（tests/backend/test_storage_init.py:28–300），不经过 DataRoots.open 的补齐分支。
 - 影响：Review Gate 的"验证入口"绑定不足；AC-03/AC-05 只能靠真实宿主用例（TC-15/TC-16，当前 Blocked），缺少可复跑的后端级防回归。此缺口 TEST_PLAN
   v0.4 已自述为 Proposed/Blocked，故不属隐藏缺陷，但需在门禁中显式记账。
 - 修复建议：补 3 个后端用例（单缺 / 三缺 / 目标为普通文件），断言：四目录类型、两份 JSON 字节不变、冲突时其余缺项保持原状、锁释放后可重试；并在
   test_status_api 增四目录与两份 JSON 可读断言（TECH"已静态核对…仍为 Proposed"）。

 ### R-03 · 低 · _ensure_directories 竞态分支逃出 StorageError 契约

 - 位置：astrophoto/storage/initializer.py::_ensure_directories（64–74）
 - 描述：except FileExistsError: if not storage_directory_exists(path): raise —— 当目标在"缺失预检"与 mkdir() 之间被创建又被删除时，裸
   FileExistsError 直接逃出，非 StorageError。bootstrap 因此落 runtime.storage_error="STORAGE_INITIALIZATION_FAILED"，无 code、无 details。
 - 证据：同函数第二个分支（对象为非目录）正确转成 StorageError("INVALID_STORAGE_PATH", …, details path)；只有"消失"分支裸露。TECH 的"失败与重试"只
   要求"落在非目录对象时报冲突"，未覆盖"消失"。
 - 影响：错误契约不一致，storage_error_message 无法映射；TC-07 的两种竞态（有效目录 / 普通文件）都能过，第三种（消失）无定义行为。属于窄边界。
 - 修复建议：改为 raise StorageError("INVALID_STORAGE_PATH", "Storage directory is missing", details={"path": str(path)})，或重试一次预检后再判失败
   。

 ### R-04 · 低 · 启动期新建顶层目录使用默认权限，与同次启动的其他敏感路径不一致

 - 位置：astrophoto/storage/initializer.py::_ensure_directories（69）、::ensure_data_root（81–87）；对照
   data_root.py::DataRoots.__init__（mode=0o700）、runtime.py::StorageRuntime.initialize（root.mkdir(..., mode=0o700)）、
   initializer.py::acquire_bootstrap_lock（runtime/locks 0o700）
 - 描述：path.mkdir() 未传 mode，新建的 database/、storage/（以及经 ensure_top_level_directories 重建的 runtime/）取 0o777 & ~umask（通常 0o755）；
   同一次启动创建的协调目录为 0o700、清单/设置为 0o600。PRD 未规定目录权限，且 HEAD 的 ensure_data_root 同样未指定 mode，故不是回归；但本 Feature
   把"启动即建目录"变成默认路径，口径值得固化。
 - 影响：同机其他本地账号可列出 database/、storage/ 顶层内容（文件本身仍受 0o600/ACL 约束）。
 - 修复建议：统一 mode=0o700（或显式沿袭现有 umask 约定）并在 TECH 记录；若不一致属有意，请在 TECH 写明理由。

 ### R-05 · 低 · 权威文档仍保留旧布局名称，与 check_data_root 的白名单冲突

 - 位置：docs/local-storage.md（"Data and HTTP contracts" 段，约 90–96 行）对照 astrophoto/storage/initializer.py::check_data_root（43–46）
 - 描述：文档仍写"默认工作区为 workspace/""唯一活动 Cache 默认在 cache/""有一致性备份时位于 backups/""databases/assets.db"；而 check_data_root 的
   known 集合已收窄为 {config, database, storage, runtime}，其余顶层项一律 TARGET_NOT_EMPTY。
 - 证据：docs/local-storage.md:92、:94、:96；同文件开头（:5）已更新为新布局，形成同一文档内的自相矛盾。04_DEV_LOG.md LOG-002 声明"权威说明已同步至
   docs/local-storage.md"，此处仅部分成立。
 - 影响：运维/用户按文档在数据根放 backups/，重启即 TARGET_NOT_EMPTY、runtime.storage=None，存储整体不可用。属"文档导致的可复现故障"。
 - 修复建议：把该段更新为新布局（或显式标注为历史）；同时确认 backups/ 是否仍要作为合法顶层目录——若要保留，须加入 check_data_root 的 known 集合，否
   则文档与验收结构需删除该表述。

 ### R-06 · 低 · 旧布局实例升级会硬失败，无过渡提示（PRD 已排除迁移，仅记录发布风险）

 - 位置：astrophoto/storage/initializer.py::check_data_root（43–46）
 - 描述：known 集合从 HEAD 的 {config, databases, runtime, workspace, cache, logs, backups} 改为 {config, database, storage, runtime}。HEAD 版本创
   建的 ~/.astrophoto/（含 databases/、workspace/、cache/）在升级后首次启动即抛 TARGET_NOT_EMPTY（details.entries 列出未知项，保现场
   ），runtime.storage=None。
 - 影响：04_DEV_LOG.md 记录过 MCP 时代的 Registry ZIP 构件，说明存在旧布局用户；升级后存储永久不可用，需人工清理。PRD 明确"旧布局迁移超出验收范围
   "，故不作为阻断，但 TEST_PLAN 无对应已知限制条目。
 - 修复建议：在发布说明与 docs/local-storage.md 写明布局变更与手工处置步骤；TEST_PLAN 增加一条"已知限制"而非用例。

 ### R-07 · 低 · 宿主启动新增"清空上一会话 Cache + 启用 host_temp 会话缓存"，AC-02 边界需显式化

 - 位置：astrophoto/bootstrap.py（59：recover_cache=coordinate；99–101：host_temp 与 atexit 注册
   ）；astrophoto/storage/runtime.py（92–97）；astrophoto/storage/cache.py（33–38、209–220）
 - 描述：HEAD 宿主路径不传 recover_cache（默认 False），也不传 host_temp；本次固定 recover_cache=True 且传入 folder_paths.get_temp_directory()，于
   是每次宿主启动执行 clear_after_session()，删除 settings.cache.path（runtime/cache）与 host_temp 会话缓存中"有归属描述、无活跃租约"的条目。
 - 证据：runtime.py:96–97；cache.py:212 遍历 session_path、settings["path"]、former_paths。close() 亦调用同一方法，atexit 注册后正常退出也会清理。
 - 影响：不影响四目录与两份 JSON 的验收，但与 AC-02"已有内容保留"的表述存在解释空间；TC-02 的哨兵必须放在 runtime/cache 之外（TEST_PLAN 已如此定义
   ，建议在 TECH/验收说明中显式写出该清理语义）。
 - 修复建议：在 TECH §生命周期与 docs/local-storage.md 增一句"重启清空 AstroPhoto 已归属的会话 Cache 条目"；确认 recover_cache 与 coordinate 的绑定
   是设计意图（与 R-01(c) 同一处改动）。
