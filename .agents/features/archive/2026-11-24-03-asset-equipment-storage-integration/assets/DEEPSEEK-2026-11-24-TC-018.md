**结论与证据边界**

先前测试证据：交办材料记录 1,000 条静态分页通过；10,000 条经进程内 MCP 和本地 HTTP 两次出现 `TIMEOUT`，其中一次无其他测试并发。该记录属于既有运行事实，本次未复测，也不据此宣称测试通过或失败原因已经确认。

本次静态观察：分页 API 每次都装载并补充完整数据集；游标续页在内存列表中线性定位；精确名称查询和校准候选过滤也复用全量列表路径。这些是可从代码直接确认的结构与复杂度问题。

待验证假设：10,000 条超时的首要原因是否确为下述全量视图构建及重复查询，仍需运行时计时、SQL 语句计数或 profiling 才能确认。当前排序配置下，完整遍历的总工作量随记录数近似平方增长，这与“1,000 通过、10,000 超时”的现象高度相符，但仍属于假设，不是已证实的诊断。

**主要发现**

**F1｜高｜每个分页请求都全量装载并逐行组装视图**

证据：`astrophoto/api/catalog.py:37-43` 遍历该类型的全部行，并在返回任何分页结果前逐行调用 `catalog.view()`；`astrophoto/api/catalog.py:64-77` 仍在此后才执行字段过滤，最后才交给 `page()` 截取。对于子帧组，`astrophoto/assets/catalog.py:322` 查询日期，`:326` 查询成员数量，`:327-330` 查询文件与工作区事实，因此每行至少产生多轮补充访问。

影响：即使请求 `limit=1`，也会先构造整个目录的列表视图。按代码字面估算，10,000 条子帧组的一次分页请求约需执行一次全表选择，再加约 30,000 次逐行补充访问；完整遍历 100 页会重复约 300 万次此类访问。该估算不是实测，但足以解释 10,000 条规模为何与 1,000 条档位出现明显非线性差异。

建议：把过滤、排序和分页下推到数据库；使用 `LIMIT limit + 1` 取得当页，并单独执行计数查询。只对返回页的 ID 批量获取日期、成员统计、扩展名和工作区集合，例如分组聚合或一次 `IN` 查询，禁止为未返回的行构造完整视图。

**F2｜高｜游标续页依赖内存线性扫描，重复放大全量构建成本**

证据：`astrophoto/assets/library.py:22-32` 先接收已构建的完整列表，再在 `:28` 用 `next(enumerate(rows))` 查找 `after` 的位置并截断。`next` 仍在 `:32` 根据剩余列表生成，未形成数据库键集游标。

影响：每个后续页都重新承担 F1 的全量构建成本，并额外扫描游标之前的所有行；最后一页需线性扫描接近全部记录。完整遍历的复杂度近似 `O(N² / limit)`，与已知规模测试的失败边界一致。

建议：改为数据库键集分页。游标应包含稳定排序键和 `id`，查询使用对应的 `WHERE (sort_key, id) > (last_sort_key, last_id) ORDER BY ... LIMIT limit + 1`；降序时相应翻转比较。若暂时只能传输记录 ID，也应在数据库中先定位其排序键，而不是在 Python 完整列表中逐项搜索。该条只评性能；当前实现不提供并发快照，测试计划已明确不假定快照，不将并发变化本身列为缺陷。

**F3｜中｜精确名称查找复用全量分页路径，所有名称操作都被目录规模拖慢**

证据：`astrophoto/api/catalog.py:20-23` 在已经完成全量视图构建后，才用 Python 过滤 `exact_name`；`mcp/src/astrophoto_mcp/tools/catalog_client.py:129` 使用普通 `page()` 查询 20 条精确名称候选；`mcp/src/astrophoto_mcp/tools/catalog.py:44-50` 的 `find_name()` 也走此路径。

影响：唯一名称查询的返回规模很小，但后端成本仍与整个目录规模成正比。`library_bind_calibration` 在 `mcp/src/astrophoto_mcp/tools/catalog.py:311-317` 对一个集合和每个主帧分别执行 `find_name()`，绑定 10 个主帧时会触发约 11 次全目录扫描；更新、移除等名称操作同样受限。10,000 条规模下，这会把非列表场景也推向超时。

建议：为唯一名称提供专用查询路径，直接通过规范化名称或唯一名称索引定位记录，再补充单条详情；不要先列出目录。保留歧义检测时，可在名称索引上检测重复条目，而无需遍历全部素材。

**F4｜中｜校准候选过滤在完整主帧视图构建之后执行**

证据：`astrophoto/api/catalog.py:45-47` 先构造全部校准主帧的视图；`:48-63` 才校验集合、排除已绑定项和不允许的类型，并对每个剩余候选调用比较。`astrophoto/assets/catalog.py:195-222` 的比较逻辑本身是内存运算，但其输入依赖前述完整视图，且 `:59` 在循环内重复调用 `catalog.data(collection)`。

影响：候选查询即使最终只剩少量匹配项，也会先承担全部主帧及其关联数据的补充访问。TC-018.a 关注的候选比较规模因此会被目录总规模放大，排序步骤还要求比较所有通过类型过滤的候选。

建议：先在 SQL 中排除不允许的主帧类型、已绑定主帧及不需要的记录类型；只对实际参与候选排序的记录构建比较输入。对集合比较所需字段和 `comparison` 结果可批量准备，避免循环内重复构建集合数据。若产品要求按比较状态排序，仍需计算全部合法候选，但合法候选集合应远小于整个素材目录。

**TC-018 缺口建议**

- 现有测试在完成后才输出每页耗时：`tests/integration/test_catalog_pagination.py:47-60` 的 `print` 位于完整遍历结束之后。10,000 条一旦中途超时，已采集的分页耗时和样本数不会出现在输出中。建议逐页立即记录日志或通过失败诊断输出，而不只是使用普通断言。
- 区分夹具构建、首个请求和后续请求耗时。`tests/integration/test_catalog_pagination.py:30-38` 的 10,000 条插入与完整遍历同处一个测试过程，现有材料无法判断超时发生在测试准备、首屏请求还是后续页。建议分别记录夹具构建、单页请求、首页与末页请求以及完整遍历。
- 增加单页诊断档位：在 10,000 条夹具下先只请求一页，并与完整遍历分开报告。这样可以直接区分“单次请求已慢”与“多页累计导致超时”。
- 现有测试虽然让所有记录使用相同时间戳，但默认 `sort_by=name_asc`，未实际执行时间排序的并发同键边界。建议覆盖 `name_asc`、`name_desc`、`created_desc`、`updated_desc`，使用相同排序键并核对页内与完整基线无重复、无遗漏。
- 覆盖 `limit=1`、`limit=100`、过滤后的边界页、`exact_name`、`q`、设备/滤镜/`result_type` 过滤，以及 `assets` 聚合路由与单类型路由的差异。
- 覆盖游标失效后的重查：改变排序或过滤后复用旧游标、删除当前游标锚点、非法游标，应得到可重查的明确错误。测试计划已说明游标不提供数据库快照，并发写入只记录可能变化，不应断言严格无重无漏。
- 对校准候选补充绑定排除、类型过滤和比较状态的规模样本；对每页记录请求往返、首屏时间、载荷字节数及候选总数，但不据此自行设定正式性能门槛。
