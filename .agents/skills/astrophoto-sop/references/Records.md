# 记录模型与双向追溯

[返回入口](../SKILL.md)

目录：[标识](#ids) · [需求](#requirements) · [决定与 bias](#decisions) · [契约](#contracts) · [功能与防御](#features) · [验证](#verification) · [残差](#deltas) · [条目去向](#preservation) · [注意力与来源](#lifecycle) · [包回执](#receipt)

本文件给出最小字段及可复制模板。实际条目按行为粒度填写；不制造没有用途的工单体系。示例 ID、路径和数值均为格式示意，不能当当前仓库事实。模板中未填内容在最终交付前替换为真实信息、明确未知或有理由的 N/A。

<a id="ids"></a>
## 1. 沿用标识，保留来源

先复用项目真实编号和文件名，例如已有 `B-01/A-01/N-01/F-01/M-01`、对应 Guard 以及 `D08`。新任务无既有系列时采用 `FR-领域-序号`、`D-领域-序号`、`C-领域-序号`、`F-领域-序号`、`G-领域-序号`、`R-领域-序号`。AC 可用所属 FR 的子编号。测试优先用真实文件、函数或用例名。

不同来源同名编号建立映射：`来源包/原ID/原含义 → 当前条目ID/锚点`。保留旧 `C` 表示 Change 的历史含义；新 Contract 不覆盖它。移动章节只改定位，不复用已退役 ID 给另一行为。

每条重大结论记录：来源类型、实际来源/定位、版本/日期、适用范围、直接证据或推断依据。私人路径和凭据在跨 Chat 传递前脱敏，保持能判断行为的语义。

<a id="requirements"></a>
## 2. 需求与可观察验收

| 字段 | 内容 |
|---|---|
| FR / AC | 稳定 ID 与用户问题 |
| 来源 / Decision | 用户决定、现行 PRD 或明确标记的提议 |
| 范围 / 排除项 | 当前专题、当前版本、相关角色和消费者 |
| 前置条件 | 初始状态、权限、输入、目标实例与环境 |
| 用户动作 | 从真实 UI/API/Node/MCP 入口执行什么 |
| 预期结果 | 用户可观察的回执与持久状态 |
| 失败与恢复 | 错误/skip、原状态、清理、重试/取消/回滚 |
| 实施关联 | Feature、契约、现有/拟建符号 |
| 验证关联 | 精确测试或拟验收条件、环境与结果 |

避免只有“支持保存”“界面正常”。必须写清初始条件，例如从禁用状态保存后自动启用，不能用初始已启用的测试证明该转换。

<a id="decisions"></a>
## 3. 用户决定与持续 bias

| 状态 | 含义 |
|---|---|
| PROPOSED | 尚未由用户明确接受的提议 |
| ACCEPTED | 用户明确决定，或已有明确授权所覆盖的行为 |
| DEFERRED | 延后，目标仍保留 |
| REJECTED | 明确否决，保留来源和理由 |
| SUPERSEDED | 已被新的明确决定取代，链接替代条目 |

```markdown
## D-EXAMPLE-001 · 决定标题（示例模板）
- 用户原话或忠实正文：...
- 来源与时间：当前对话/已提供附件/已验证窗口；...
- 状态及适用范围：...
- 旧规则与替代关系：旧ID → 本ID；仅替代哪些部分
- 继续有效：没有取消的要求和边界
- 理由：用户表达的取舍；模型推断另标
- 影响：FR/AC、原型、Contract、Feature、Guard、Test、Prompt
- 落实状态：已更新哪些正文/实现；哪些待执行
- 反向链接：受影响条目都能追溯到本决定
```

用户本轮明确“全量”时，直接将该约束应用到 S4/S8，无需再次等待批准。不能因为某个旧模板要求冻结 PRD，就重新询问已经清晰的同一决定。

<a id="contracts"></a>
## 4. 共享契约与消费者

```markdown
## C-EXAMPLE-001 · 共享契约（示例模板）
- 所有者 / 集成Main：...
- 生产者 / 消费者：逐一列 Node、UI、HTTP、MCP、存储和旧工作流
- 当前契约：字段/类型/单位/路径或资产ID语义/错误码/生命周期
- 目标契约：完整新定义，注明不变部分
- 用户决定 / AC：...
- 兼容与数据处置：旧输入、旧配置、旧工作流、迁移或按授权替换
- 调用顺序与状态持有者：...
- 权限、幂等、事务、并发、失败/恢复：按风险填写
- 实施顺序与验证：生产者、每个消费者、最终集成工作树
- 状态与缺口：已有事实/拟变更/未决；来源和版本
```

仅在共享行为或其他消费者受影响时建立变更提案。一般局部样式不自动升级为全项目契约评审。用户已明确产品语义时，Main 在授权内确定技术细节。

<a id="features"></a>
## 5. Feature、Guard 与真实符号

实现状态单列：`IMPLEMENTED / PARTIAL / PLANNED / OBSOLETE / UNKNOWN`。不要用一个 VERIFIED 混合实现、环境和执行结果。

Feature 最少字段：`ID｜用户行为/AC｜AS_IS｜TO_BE｜实现状态｜入口 path::symbol｜调用链/状态持有者｜I/O与副作用｜共享契约｜Guard｜测试｜决定/来源｜缺口`。

Guard 最少字段：`ID｜所属Feature/AC｜触发条件｜实际生效调用点｜校验与拒绝/skip行为｜错误码/回执｜清理/恢复/回滚｜持久影响｜测试断言｜来源与未覆盖项`。

错误/skip 不能只列一个错误名称；说明发生在哪一步、哪些工作已执行、哪些工作跳过、输入/旧状态是否保留、用户如何继续。取消、读写权限、并发和临时文件生命周期按实际风险覆盖。

未发现 Guard/Test 时记录搜索目录、符号、调用者范围及 `NO_GUARD_FOUND / NO_TEST_FOUND`。该结论仅适用于已搜索范围。无此类风险时写 `N/A + 理由`，不虚构防御措施。

源码计划标 `EXISTING` 或 `PROPOSED`，并说明 `REUSE / MODIFY / ADD / REMOVE` 的必要性。行号只作为带版本的辅助；优先给稳定的路径和函数/类/组件名。

<a id="verification"></a>
## 6. 验证证据：三类字段分开

| 字段 | 取值或内容 |
|---|---|
| 实现状态 | IMPLEMENTED / PARTIAL / PLANNED / OBSOLETE / UNKNOWN |
| 证据性质 | SOURCE / HISTORICAL_RUN / CURRENT_RUN / INFERENCE |
| 环境与替身 | 静态、真实临时文件/SQLite、Mock HTTP、TestServer、JSDOM、浏览器、真实 CLI、宿主 GET、原生队列、MCP stdio 等实际环境 |
| 执行结果 | PASS / FAIL / SKIP / XFAIL / NOT_RUN |
| 阻塞 | 如有，写 BLOCKED 及所需条件；不代替执行结果 |

一行验收记录必须包含：

`AC/Feature｜入口与函数｜Guard/失败结果｜测试文件与名称｜关键断言｜命令｜工作树/构件/实例/版本｜环境与替身｜时间/退出码/通过失败跳过数｜结论与未覆盖边界`。

测试数量只引用实际运行输出；套件未收集应单独说明，不计作业务断言失败或通过。Fixture 漂移、测试配置、产品缺陷和环境失败分别定位。临时探针和标准命令分别记录，不互相替代。

宿主 GET 说明注册或读取；入队说明接受；history 完成、输出文件、下游收到的实际值共同支持对应图执行结论。真实 CLI 不自动等于宿主图执行通过。具体例子与命令见 [Project](Project.md)。

<a id="deltas"></a>
## 7. 残差记录

`来源｜旧条目/旧状态｜本轮新证据或用户纠偏｜新完整状态｜影响ID与消费者｜继续保留项｜代码/测试/正文落点｜未决与下一步`。

将记录放入完整包的演进章节；正文必须同步更新。没有变化可写“本轮无已确认变化”，仍携带完整有效正文。不能把该记录单独冒充 S4/S8 交付。

<a id="preservation"></a>
## 8. 信息去向与覆盖表

| 来源包/文件/条目 | 旧有效内容及限定条件 | 去向 | 新包文件与锚点 | 依据/替代ID | 检查结果 |
|---|---|---|---|---|---|
| 待填实际来源 | 需求、决定、异常、测试或风险 | 保留/修订/等价合并/取代/否决/延后/无法核验/移入归档/重新激活 | 必须是本版可读的正文或档案位置 | 用户决定或代码/执行证据 | 已核对或明确缺口 |

规则：

1. 从所有已提供有效输入逐条登记，不能只看本轮 diff。
2. 保留条件和反例；等价合并时逐来源检查独有内容。
3. 被否决或取代的内容仍有历史位置，不能静默消失。
4. 旧条目数量与新条目数量可以不同，但每个旧条目都有语义去向，每个新条目有来源/设计身份。
5. 额外核对当前源码中的功能，找出文档从未记录的项目；S8 必须覆盖未改动领域。
6. 逐一回查输出中的当前结论是否有支持，确认没有把示例或拟建符号当现实。
7. 归档条目依旧在本版保留全文，记录当前规范/影响摘要到档案的双向定位；恢复活动不抹掉归档事件。
8. Local Chat 输入需精确到会话、消息或时间范围、来源定位和承接条目；不能只列文件数量便声称语义已融合。

完整性说明写清哪些输入读取了、哪些范围核验了、哪些未获得。COUNT、字节数或哈希不得单独作为语义保全证据。

<a id="lifecycle"></a>
## 9. 注意力、复核周期与来源批次

这些字段与现有决定、实现、执行状态并列，不另造一套工单库。保留现有稳定 ID。

| 字段 | 语义 |
|---|---|
| `attention_state` | 仅 `ACTIVE / ARCHIVED`；控制是否在日常活动讨论中展开 |
| `REACTIVATED` | 事件，不是第三种常驻状态；同 ID 返回 ACTIVE、计数归零，保留旧历史 |
| 提及/变化基线 | 最后有效新提及或变化内容、来源和 Handoff ID；基线 H0 的闲置计数为 0 |
| `idle_handoffs` | 脚本维护的连续未使用轮次，达到 5 且未固定则归档；有效新提及或变化归零 |
| 未使用复核账 | 每次合格 S8 的 ID、父版本、来源批次、条目复核依据、事件判定和累计数；未知轮次不能跨过累计 |
| `pinned / pin_reason` | 固定保留及其实际原因；CONSTRAINT 必须固定，当前必办与必要阻塞信息按事实固定 |
| 归档记录 | 原条目全文、原状态、归档原因/轮次、当前影响位置、相关来源、重新激活条件及事件 |
| `handoff_id / parent_handoff_id` | 正式全量 S8 主线身份；重打包同一快照不产生新计次 |
| `source_batch_id` | 本版批量输入身份、覆盖范围、截止点和实际读取回执 |
| `completed_state` | `COMPLETE / INCOMPLETE`，仍是包完整性；只有已完成的独立全量 S8 才能固化本轮未变计数 |

在 `00_START_HERE.md` 或 `MANIFEST.md` 记录上述快照身份及完成状态。使用脚本时，以 `state.json` 为计数、事项版本与历史的唯一结构化依据，同版生成 ACTIVE_CONTEXT、16_ARCHIVED_ITEMS 和 CONTEXT_INDEX；不能在两处手改同一事实。归档条目恢复后当前全文移回活动视图，归档保留稳定恢复入口，完整旧历史仍随 state 携带。详见 [Archiving](Archiving.md)、[StructuredContext](StructuredContext.md) 和 [档案模板](../templates/16_ARCHIVED_ITEMS.md)。

事项 ID 与事件 ID 分开。`MENTION / CHANGE / TEST_RUN / ERROR_RECURRED / USER_DIRECTIVE` 只在真实 NEW_INPUT 中唤醒；`CARRY_FORWARD / ROUTINE_CHECK / HISTORICAL_QUOTE / NOT_RELEVANT` 不唤醒。事件记录原始来源 ID/版本、消息定位、引用与语义依据，去重后再计数；具体提取见 [ChatExtraction](ChatExtraction.md)。

跨轮即时 touch 设置待建立基线，下一完整 S8 才把它记为 H0=0；不将这轮误加为 1。v2.1 的 `unchanged_count` 不自动继承为新 `idle_handoffs`，首次按真实材料建结构化 H0，旧账作为历史保全。

Local Chat 每个预期来源使用 `EXPECTED / RECEIVED / READ / RECONCILED / MISSING / UNREADABLE` 记录实际阶段。`RECEIVED` 只表示收到，`READ` 需实际读取回执，`RECONCILED` 需逐项去向；无变化是带来源依据的内容标记，不是跳过阅读的状态。完整保留但尚未裁决的业务冲突仍可完成来源融合，并明确其决定状态。

`15_LOCAL_CHAT_INTAKE.md` 记录预期名单、负责人、来源路径/引用、消息范围、截止点、版本/哈希、读取范围、内容去向、最后增量回收与批次结论。原始内容随包进入 `sources/local-chats/`，详见 [LocalChatIntake](LocalChatIntake.md) 和 [登记模板](../templates/15_LOCAL_CHAT_INTAKE.md)。不假装能够访问未提供的窗口。

<a id="receipt"></a>
## 10. 阶段与包回执

```markdown
- 阶段/专题/版本/日期：...
- 本轮目标与有效用户bias：...
- 实际读取与核验范围：...
- 实际交付：正文、原型、实现或完整包位置
- 包完整性：COMPLETE / INCOMPLETE；未覆盖内容和原因
- 实施就绪或验收结论：明确可做范围与阻塞
- 条目保全：已核对旧→新与新→来源；剩余缺口
- S8 来源批次：预期/收到/已读/已融合清单、截止检查、缺失或不可读项
- 事项/事件提取：新增范围、稳定ID、事件分类、重复与歧义、原文覆盖去向、固定保留原因
- 结构化状态：CURRENT版本、预览与提交结果、事件/轮次去重；脚本不证明实际语义已读
- 归档与恢复：沿用档案、候选与实际生效事件；合格复核账和当前影响保留位置
- 实现/证据/环境/执行结果：分开陈述
- 未完成/风险/下一步：有具体责任与所需材料
```

COMPLETE 表示声明范围的内容与输入去向完整，不表示所有功能已实现或本轮测试全通过。关键来源缺失、预期 Local Chat 未读/未融合、范围未盘点或语义去向不清时 INCOMPLETE；不得为了完成而静默删掉预期来源。S4 的“可实施”还需关键技术事实、AC 与产品取舍足够确定。
