## 1. 细化到事项和事件

脚本维护计数、状态与视图，需要上游说明“这次出现的是什么”。提取以一个可独立判断的决定、行为约束、问题、测试证据或尝试为单位；同一事项多次出现，继续使用同一稳定 ID。每次真实发生的讨论或执行另记事件身份。

不逐 token 建立条目，也不把同一问题的每句话拆成新事项。一段话涉及两个独立约束时可以拆为两个事项并保留共同来源；几段话共同限定一个决定时合为一个完整事项，同时保留各段独有条件。

需要同时回答四个问题：这个事项的完整语义是什么；本次发生了什么；凭哪段原文或执行回执判断；它在新包中落在哪里。原文、结构化事实、注意力状态分别保留。

本规范细化 v2.1 的来源汇合，不降低 Main 实际读取完整相关来源的要求。各窗口可以并行提取，最终 Main 仍按 [LocalChatIntake](LocalChatIntake.md#intake-read) 核对原文、独有条件和映射。这里只处理可提供的对话消息、工具结果与附件，不要求导出模型的内部思考过程。

<a id="source-boundaries"></a>
## 2. 完整来源与本轮新事件范围分开

每个来源保留完整相关会话及附件，记录 `source_id`、`source_revision`、上一检查点、本次检查点、原始文件/消息范围、说话者、原生定位是否可取得、实际读取者与时间。消息 ID 不可取得时，用有说明的导出序号或文件行范围定位，不伪造平台 ID。

从已保存完整原文中定位“上次检查点之后的新消息或修订”，形成供候选扫描的新内容段。保留该段与完整原文的精确范围映射。新段可以单独供脚本读取，S4/S8 的正式交付仍带完整必要正文、历史和来源，不能只发这个新段。

| 来源情况 | 提取处理 |
|---|---|
| 新用户消息、新回复、新工具运行或新附件 | 进入本次事件判断，核对它确实属于新增范围 |
| 重导出同一段原文，只有导出时间或版本变化 | 关联既有事项和事件；不当作再次发生 |
| 在新消息中粘贴旧 Handoff、归档或日志 | 保留复制范围及原来源身份，先按历史引用分类 |
| 新消息引用旧内容，并提出新问题或指令 | 将引用与新增言语分别定位；新增部分可以产生提及或纠偏事件 |
| 原有消息被编辑，实际含义变化 | 保留旧版本，比较修订范围后形成有依据的新事件 |
| 前后检查点无法衔接、原文截断或附件缺失 | 明确缺口；不能把不可见范围判为“没有提到” |

重导出时不要给同一已记录事件生成新的发生身份。原事件绑定最初可核对的来源版本和定位，新导出到旧事件的关系另记在映射表；确实改变内容才产生修订事件。新的导出文件存在，不证明 Main 已读。

<a id="items"></a>
## 3. 一条事项必须保留的语义

机器字段的准确形状以 [StructuredContext](StructuredContext.md) 和 [context_manager.py](../scripts/context_manager.py) 为准。下表解释提取内容，不增加脚本未支持的字段。

| 记录部分 | 提取要求 |
|---|---|
| 稳定身份 | 沿用实际 ID、类型和标题；旧 ID 同名时保留来源命名空间与映射 |
| 完整正文 | 目标、前提、触发条件、行为、结果、例外、反例、错误/skip、状态保留与恢复；不只写一句标题 |
| 决定 | 用户原话、接受/提议/延后/否决/替代状态、理由、范围、保留项与替代关系；模型建议单独标明 |
| 测试 | 真实用例/断言、命令、工作树/构件/实例、运行身份、环境、时间、退出码和结果；已有/计划及历史/本轮分开 |
| 错误 | 新发生或历史记录、触发位置、实际回执、输入及持久状态、影响、清理/恢复、是否仍阻塞 |
| 尝试与问题 | 做过什么、预期/实际、失败或放弃依据、尚未答复的选择、长期目标与启动条件 |
| 来源 | 原始消息/行范围和必要附件，准确引用与忠实整理分别标识；不能根据记忆补造原话 |
| 关系 | 关联的决定、AC、契约、Feature、Guard、测试、风险及消费者，使用实际 ID |
| 保护原因 | 仍生效约束、当前明确必办、当前必要阻塞说明等需要保持可见的依据 |

可用类型为 `DECISION / TEST / ERROR / RISK / QUESTION / CONSTRAINT / ATTEMPT`。类型是整理粒度，不替代已有业务编号或决定、实现、证据和执行状态。`TEST` 的归档对象是上下文中的测试事项/证据叙述；脚本不删除测试代码，也不把已有 FAIL 改成 PASS。

仍有效的规则和验收约束用固定保留的 `CONSTRAINT` 或等效当前规范承载，按引擎要求 `pinned` 并写原因。当前用户明确要求处理的事项和当前必须看见的阻塞说明也固定保留；可以将较长历史讨论另作可归档事项，建立关联，不能把有效约束一起降为冷记录。

不要只因字段齐全就填写“已实现”“已通过”。没有证据的业务字段保持 UNKNOWN、NOT_RUN 或明确缺口；注意力归档不改变这些事实。

<a id="events"></a>
## 4. 事件分类决定是否唤醒

每个事件至少能定位到真实 `event_id`、`item_id`、来源 ID/版本、消息或行范围、原文片段及提取者。脚本输入所需键与枚举见 [结构化协议](StructuredContext.md)，提取回执另保存角色、匹配理由、相关附件及完整性信息。

| 本次出现方式 | 事件分类 | 对注意力的作用 |
|---|---|---|
| 用户或当前讨论明确重新提起该事项，即使代码与结论未改变 | `MENTION`，新增来源 | 恢复 ACTIVE，空闲计数归零 |
| 用户要求继续处理或改变行为边界 | `USER_DIRECTIVE`，新增来源 | 立即恢复并传播 bias；必要时固定保留 |
| 新事实、范围、实现或完整条目语义改变 | `CHANGE`，新增来源 | 更新完整状态并归零，保留旧版本 |
| 本次真实执行测试，有可核对命令、环境和运行回执 | `TEST_RUN`，新增来源 | 更新对应证据及注意力；结果相同也保留新运行身份 |
| 错误本次再次发生，具有新发生条件或运行回执 | `ERROR_RECURRED`，新增来源 | 恢复事项并保留新的复现证据 |
| 新包原样带入旧正文、测试名、来源清单或旧日志 | `CARRY_FORWARD` | 保留信息，不能据此唤醒 |
| 为生成包例行检查索引，确认原状，无新讨论或执行 | `ROUTINE_CHECK` | 记录复核；不当作实质提及 |
| 引用旧对话或旧失败，只说明历史，没有重新提出问题 | `HISTORICAL_QUOTE` | 保留引用与原来源，不据此唤醒 |
| 候选命中了同形词，但与该事项无关 | `NOT_RELEVANT` | 记录排除理由；不向该事项传播 |

前五种只有来源确实为 `NEW_INPUT` 才能成为唤醒事件。事件关键词和代码字符出现次数本身不产生计数。将“引用旧问题后重新提出的新要求”拆清楚，可以同时保留历史引用和新的 USER_DIRECTIVE，不能把新增要求埋进历史分类。

新消息明确“这个问题暂不处理”等表达时，仍忠实记录最新用户意思；不要将唤醒等同于强制实施。恢复注意力用于处理这条新的决定，业务决定可以仍为 DEFERRED。只有用户明确要处理的范围才进入实施。

测试名称出现在清单里不证明执行；旧 error 日志再次上传不证明复现；截图显示文件名不证明正文已读。上游材料不足以判定时保持待判定，不能为了让脚本继续而随意选唤醒或未变。

<a id="matching"></a>
## 5. 将自然语言匹配到稳定事项

先按精确 ID 与已登记别名产生候选，再由 Main 根据前后语义和来源定位核对。精确 ID 必须检查边界，例如 `D08` 不应匹配 `D080`。一个别名对应多个事项时保留所有候选及歧义，不按首个结果自动选择。

间接表述可以映射到旧事项：例如新消息问“恢复时还会把失败输入清掉吗”，需要先读取相关规则、确定所指行为，再映射到真实决定/错误 ID。保存这段新原话、定位和匹配理由；这不是脚本凭一般词“恢复”推断出来的事实。

`related_ids` 表示关系，不自动让整个关联图恢复。某条新决定确实影响多个事项时，Main 分别记录各项的影响依据和事件，避免一次命中让所有测试、错误或领域记录被动唤醒。

候选结论区分“已匹配、无关、等价重复、历史携带、仍有歧义、找不到对应事项”。仍有歧义的范围进入缺口；实际读全且已经明确不存在对应旧事项时，再按 Records 新建稳定 ID。缺材料不能被解释成“需要新建一个替代旧记录”。

脚本扫描和模型提取都是辅助。Main 需要核对候选之外的相关语义，防止没有出现 ID 的新纠偏被漏掉；不能宣称自动搜索保证完整理解全部聊天。

<a id="coverage"></a>
## 6. 每个来源范围都有明确去向

使用 [CHAT_EXTRACTION 模板](../templates/CHAT_EXTRACTION.md) 对声明范围建立覆盖账，可按连续且性质相同的消息段合并登记。每个范围落入以下一种或多种有依据的去向：

- 创建或修订完整事项，并链接新包正文。
- 形成关联事项的新事件，事项完整语义继续保留。
- 与既有内容等价，列出被完整覆盖的位置和原事件身份。
- 仅为历史携带或例行复核，保留来源与不唤醒理由。
- 与本任务无关，在原授权范围内排除并记录理由；原始已纳入来源仍保留。
- 缺失、未读、截断、无法匹配或无法核实，明确影响与最小补件。

纯确认或重复往复可以共用同一个去向，不能直接丢弃范围。不同来源独有的“仅在某环境”“失败时保留输入”“暂不支持”“不得自动执行”等条件逐项保留。合并正文时保留全部来源，反向核对每条新结论能否定位支持材料。

覆盖账同时列已读集合、声明集合、排除集合和缺口，核对分卷边界及附件关系。来源中存在完整记录的未决产品争议可以完成映射，决定继续未决；缺原文、未读或事件歧义则不得伪装成已对齐。

结构化提取结果本身不构成“已读”证明。负责最终 Handoff 的 Main 完成实际读取、最后更新回收及双向对账后，才能关闭批次。计数脚本只验证输入形状和声明，不能观察 Agent 是否真的理解了每段话。

<a id="engine-input"></a>
## 7. 从提取回执生成脚本输入

1. 保存完整原文、附件和来源版本；确定上一检查点之后的实际新增范围。
2. 读取并建立事项、候选及范围去向；精确搜索只是其中一个步骤。
3. Main 复核事件类型、语义匹配、固定保留项、业务状态和未决缺口。
4. 按 [StructuredContext](StructuredContext.md) 生成受支持的完整事项更新、事件与 Handoff 观察项；提取回执中的额外解释继续放在回执文件，不擅自塞入严格 JSON 输入。
5. 先运行只读预览，核对将归档、恢复、计数归零及保持固定的真实 ID；缺口不当作 UNCHANGED。为本轮最终 ACTIVE 的每条事项填写观察项，包括新增和恢复项：本次 `advance` 实际新增或变更的完整 upsert 填 CHANGED，本次尚未处理过的有效新提及填 MENTIONED；已由 `touch` 保存且此后无新变化/提及的事项填 UNCHANGED，并引用 touch 回执，由待建立基线状态形成 H0=0。UNKNOWN 或漏行不能作为完整复核。需要给 S8 组包时显式生成候选目录，候选不改 CURRENT、不固化轮次。
6. 新输入中的明确提及可以用 `touch` 及时恢复，不需要等待下一次完整 S8；它不增加 Handoff 轮次。正式全量 S8 门通过后，才推进本轮空闲计数。

上版活动事项没有本轮可靠观察，或者来源覆盖没有完成时，不提交“无提及”的轮次。新增或恢复事项先建立 H0，随后五个独立、完成的空闲 Handoff 才满足归档阈值。重复提取、重打包或重放相同事件不再计次。

跨 Handoff 的 `touch` 会先归零并留下待建立基线状态；下一次完整 S8 建立 H0=0，不能把它算成空闲第 1 轮。首次从旧记录导入新策略时按实际内容建立基线，不直接继承 v2.1 的旧未变计数。导入历史测试或错误仍保留原时间与证据身份，不能伪装成本轮新运行或复现。

新事件若同时改变正文、业务状态或固定保留要求，先读取 CURRENT 中的完整记录并合并全部有效内容，把完整 upsert 与事件放在同一次 touch 提交。仅关注度变化时才可用空 upserts。不能先消费事件，再用相同已去重事件补写状态；也不能改事件 ID 制造新发生来绕过校验。

Main 生成输入时可按协议带 `expected_revision`，绑定实际读过的状态版本；发生新 touch 后重新读取、预览，避免用旧计划覆盖新活动状态。同一事件重试保持原 `event_id` 和完整输入；导出版本变化记录到来源映射，不改旧事件的 source_revision。

不手改脚本维护的 `attention_state`、计数、事件账或已经生成的快照来迁就输出。新的明确决定先进入有来源的结构化记录，预览与提交再生成一致视图。

<a id="restore-load"></a>
## 8. 恢复时移回正文，完整历史继续存在

v2.2 对“从归档移出来”的处理是：当前 `16_ARCHIVED_ITEMS.md` 视图保留仍为 ARCHIVED 的完整条目；真实新提及后，该条目全文进入当前 `ACTIVE_CONTEXT.md`，归档视图可保留简短恢复索引，指向活动正文。旧归档快照、原事件和内容版本保留在完整状态及历史中。

这细化了 v2.1 的“恢复仍留档”表述：历史完整保留，不要求当前活动区和当前归档区各放一份完全相同的全文。移动只改变当前阅读位置，业务决定、错误结果和测试事实仍按证据记录。

普通任务先读当前有效约束、活动上下文和轻量索引，按关联跳到必要历史全文。S8 仍按完整来源及全项目范围完成对账，并交付全部活动与归档信息。使用引擎时将同版 `state.json`、`ACTIVE_CONTEXT.md`、`CONTEXT_INDEX.md` 和 `16_ARCHIVED_ITEMS.md` 完整携入新包，保留相对链接并重算全包清单；FULL 同时全文承接活动和索引正文。存储与交付全量不要求每个普通 Chat 启动时把 FULL 全文同时塞进上下文。

<a id="source-prompt"></a>
## 9. 来源窗口的短提取 Prompt

```text
按 AstroPhoto ChatExtraction 提取本窗口 [source_id]、版本 [source_revision]、范围 [起止消息/检查点]。先保留完整相关原文和附件，再定位上次检查点后的新消息与修订；记录说话者、真实消息/行范围和引用片段，不凭记忆补造原文。
按稳定事项 ID 提取决定及理由、有效条件/例外、测试及实际运行回执、error/skip、尝试失败、未决与用户 bias。区分真实新提及/执行/复现、历史复制和例行检查；同一事件重导出沿用原身份。给每个连续消息范围填写去向，保留独有条件、反向来源和候选歧义。指出需固定保留的约束与当前必办事项。
交付完整来源、CHAT_EXTRACTION 回执和已有登记的更新；缺失或未读如实列出，不自行增加 Handoff 次数，不自动发送消息。
```

<a id="main-prompt"></a>
## 10. 最终 Main 的短核对 Prompt

```text
按 AstroPhoto ChatExtraction 与 LocalChatIntake 核对批次 [batch_id] 的全部预期来源。逐份实际读取相关原文、提取回执与附件，核对消息范围覆盖、稳定 ID、事件身份及原话条件；候选搜索不能代替语义读取。
将新增内容分类为真实提及、纠偏、变化、测试运行或错误复现；历史携带、旧日志和例行检查不唤醒。对间接提及给出匹配依据，歧义和未读保留缺口；关联 ID 不自动广播恢复。保留决定/实现/执行状态，固定仍有效约束和当前必办事项。
用受支持的 JSON 协议先预览脚本结果；明确新提及及时 touch 恢复，正式 S8 完整性门通过后才 advance 计次。完成最后更新回收及双向对账，交付活动全文、当前归档全文、状态历史和原始来源；S4/S8 继续全量。
```
