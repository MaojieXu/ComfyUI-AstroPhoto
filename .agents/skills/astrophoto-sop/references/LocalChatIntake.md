## 1. 目的与覆盖边界

在最终 S8 全局综合之前，将所有已登记、属于本轮范围的 Local Agent Chat 的完整相关讨论及附件，汇入**实际负责生成 Handoff 的 Main**。保留需求为什么成立、哪些方案已被否决、失败如何发生、用户怎样纠偏，而不只汇总最终代码。

固定次序：冻结预期来源范围；各窗口导出完整原文和结构化输入；Main 逐份实际读取并建立去向；重核迟到内容并关闭批次；再作最终全局综合与归档候选判断；通过 S8 交付门后固化新包。允许边接收边预审，最终结论和归档不得早于批次关闭。

v2.2 将结构化输入细化为 [事项、事件与覆盖回执](ChatExtraction.md)：完整原始来源全部保存，同时标出上一检查点后的实际新增消息/修订范围，用来产生有证据的唤醒事件。历史携带不触发；当前明确新提及可以按 [StructuredContext](StructuredContext.md) 即时 touch 恢复。只有增加闲置轮次和新归档必须等批次及 S8 完成门。

这条通路保留原始基线作为跳跃连接；Main 的整合是有来源的残差；最新用户 bias 必须贯穿两者。归档减少活跃关注，不删除输入或历史。S4 仍为专题全量，S8 仍为全项目全量，不能因新增 intake 改成仅收本轮变化。

“每件事有记录”的可检查含义是：**已登记范围内的可读原文和附件被保留，每个有意义的决定、尝试、失败、未决和证据都有正文去向与反向来源。** 未提供、未授权、未导出或被截断的内容只能声明缺口。目录名、窗口名、附件上传、文件数和哈希不证明这些内容已读取或语义保全。

仅使用用户提供、当前任务已登记且可授权读取的来源。不猜测其他窗口，不探查无关历史，不把本机路径或截图中目录名称当作已取得的内容。这里的“注入”是可核对的资料读取与融合流程，不承诺所有历史同时常驻模型上下文。

## 2. 批次、来源与状态

### 2.1 建立一个覆盖全部预期来源的批次

Main 为当前 S8 建立唯一 `batch_id`，路径为 `.artifact/HandoffInput/<batch-id>/`。批次覆盖**全部预期来源**；按长度拆成多次工具读取、多个文件或多个阅读段，不等于把缺失窗口从本批次排除。

最终 Handoff 元数据中的 `source_batch_id` 就是此 `batch_id`，不得各自分配不相干的身份；`batch_revision` 记录本批次补收、重开后的版本，关闭回执注明最终采用的 revision。

先在 `15_LOCAL_CHAT_INTAKE.md` 的工作副本登记：来源稳定 ID、窗口名称/用户提供的链接或标识、负责人、专题与讨论范围、仓库/工作树、预期消息或时间范围、读取授权依据、导出方式及缺口。已知主对话中的相关用户决定也登记为明确来源，不因其不属于 Local 窗口而遗漏。

登记表空白表示来源尚未清点，不能解释为“零来源且全部已注入”。确实没有某类窗口时须有范围依据。不能将没有回执的已知窗口直接删除，以便满足完整性检查。

记录 `expected_set_revision` 和 `expected_set_frozen_at`。之后发现相关窗口、扩大相关消息范围或获知遗漏附件时，追加来源及修订理由；保留旧登记版本，更新受影响的完整性结论。只有范围判断有真实依据的无关来源可以排除，排除记录仍保留。

### 2.2 身份与只读快照

| 对象 | 必须记录的身份 |
|---|---|
| 批次 | `batch_id`、预期来源集合版本、Main、目标 Handoff、声明范围 |
| 来源 | `source_id`、来源窗口/文件、owner、可读方式、授权范围 |
| 来源版本 | `source_revision`、导出者、导出时间、原生消息 ID/时间范围或检查点 |
| 原始材料 | 原始文件名/格式、相对路径、大小、可取得的 SHA256、是否完整/截断/脱敏 |
| 阅读回执 | 实际 reader、读取时间、文件版本及已读消息/章节/附件范围 |
| 最终边界 | 每源最终 checkpoint、最后用户 bias 检查点、批次冻结与关闭时间 |

消息 ID 或时间不可取得时，使用导出顺序编号和原文可辨认的位置，明确它是本次导出定位，不伪造平台原生 ID。没有可靠哈希时如实记录可用身份信息；不能因有哈希就忽略截断或缺附件。

推荐按 `.artifact/HandoffInput/<batch-id>/sources/<source-id>/<source_revision>/` 接收来源快照，原文、结构化回执及附件分别存放。收到的快照视为只读；修正通过新版本进入，不原地覆盖。批次的登记、回执、映射在旁侧工作副本中追加，关闭后连同原始输入一起冻结；禁止以权限改写破坏既有项目目录。

### 2.3 来源状态独立于业务状态

| `source_status` | 含义与升级条件 |
|---|---|
| `EXPECTED` | 已登记，等待符合范围的完整输入；尚不能算收齐 |
| `RECEIVED` | 已拿到具体版本的输入，可定位原文与必需附件；尚未证明 Main 实际读过 |
| `READ` | Main 实际读完声明范围内的相关原文、结构化输入与必需附件，逐份回执完整 |
| `RECONCILED` | READ 的内容已完成语义去向、反向来源、冲突与缺口核对 |
| `MISSING` | 预期原文、窗口回执、范围片段或必需附件尚未获得；说明欠缺及影响 |
| `UNREADABLE` | 已知来源/已收到材料无法实际读全，例如权限、损坏、格式或截断；说明可读与未读部分 |

常规推进为 `EXPECTED → RECEIVED → READ → RECONCILED`。MISSING/UNREADABLE 补齐后从适当步骤重新核对；历史接收和阅读回执保留。部分已读不能把整份来源升为 READ；将实际范围与剩余范围分别写清。

新的来源版本必须建立新的接收/读取/映射回执，旧版 READ 不自动覆盖新内容。既有可重用材料仍需精确关联旧版本和旧回执；Main 核验未变内容，读完新增/修订后才能对当前完整版本声明已读。

来源状态不替代决定的 `PROPOSED/ACCEPTED/DEFERRED/REJECTED/SUPERSEDED`、实现状态、测试结果或 `ACTIVE/ARCHIVED`。完整读取并如实呈现的待决冲突可以是 RECONCILED：资料已对齐，产品选择仍未决定；不能因为争议存在就谎报 MISSING，也不能把 RECONCILED 当作用户已接受。

<a id="intake-source"></a>
## 3. 每个来源窗口交付什么

### 3.1 完整原文与可转交材料

每源同时交付两层：**相关完整会话原文/可授权读取记录及原附件**，与**结构化 Handoff 输入**。结构化输入帮助 Main 定位，不能替代原文。相关范围从约定起点到该源最终检查点，保留消息顺序、说话者、代码块、限定条件、反例和附件关系。

若讨论依赖更早决定，将其完整相关原文一并携入或登记必要的前置来源。不能用“前面已经说过”跳过前置要求。确有无关私人内容时仅在原有授权范围内排除，并登记排除范围和理由；脱敏保留行为语义、位置及脱敏事实，不能把缺失称为逐字完整。

优先保留来源原始导出格式及文件名。无原生导出能力时，可把当前确实可读的原文按消息顺序写入可转交文本；注明获取方式、完整边界和不可读部分。不能根据记忆重建“逐字原文”，不能把 Agent 自写摘要标为 transcript。

Main 不能直读某窗口时，给用户本页的短导出 Prompt 转交该窗口，接收其文件后再读取。不因“已提供 Prompt”就记 RECEIVED，也不自动向其他人或窗口发送消息。输入太大可按连续消息范围分卷，保留顺序索引、无缺口范围和附件关联，不能只保留最后一卷。

### 3.2 结构化输入的必填语义

| 内容 | 必须保留的信息 |
|---|---|
| 用户 bias | 原话或忠实正文；来源定位、适用范围、例外、被替代部分、仍有效部分；模型建议另标 |
| 决定与方案 | ACCEPTED、PROPOSED、DEFERRED、REJECTED、SUPERSEDED 分开；理由、取舍、替代 ID、未定条件 |
| 尝试与失败 | 尝试内容、预期/实际结果、失败条件、已回滚/仍保留影响、避免重复的限制 |
| 未决与长线目标 | 未答问题、待证假设、延后且未取消的需求、依赖与下一步责任 |
| error / skip | 实际触发点、已执行/跳过步骤、错误回执、状态保留、清理、恢复和重复发生情况 |
| 源码事实 | `repo-relative-path::symbol`、真实入口、工作树/分支/HEAD/脏树、已存在与计划符号区别 |
| 验证回执 | 精确测试及断言、命令、日期、环境/替身、退出码/结果、原日志、未测范围；历史与本轮分开 |
| 集成状态 | 来源工作树与目标工作树、改动是否进入目标、证据和未知；来源分支 PASS 不冒充集成 PASS |
| 原始材料 | 原文分卷、附件、日志、原型及相互引用；不能访问的材料单独列缺口 |
| 原条目关系 | 既有 D/FR/C/F/G/Test/R 与历史归档 ID，原含义、当前有效状态及继续保留项 |
| 事项/事件提取 | 稳定事项ID、独立事件ID、原文定位、NEW_INPUT/历史边界、类型、去重、语义匹配理由、固定保留与覆盖缺口 |

“本轮没有修改”也必须返回来源身份、范围、最后检查点、无实质变化回执，并携入该源完整有效输入。可按真实已存原文复用同一内容身份，最终包仍实际带齐必要原文；不能只有“无变化”一句话或外部旧路径。

来源证据不够时分别记 UNKNOWN、NOT_RUN 或已知缺口，不能为填满表格编造符号、测试通过数、用户接受或工作树集成状态。

<a id="intake-read"></a>
## 4. Main 的逐份读取与语义对齐

### 4.1 实际读取，不以接收代替注入

Main 按预期登记逐一核对来源身份、范围、版本及附件，先标 RECEIVED，再实际读取。每次读取记录文件/分卷、消息或章节范围、版本、reader、时间和未读部分。非文本必需附件记录实际查看方式；仅下载、解析文件名或计算哈希不等于阅读。

可按领域和长度分批实际读取，保持同一个 `batch_id`。工具输出截断时继续读取未覆盖范围；只看到文件头、摘要、检索片段或其他 Agent 的短报告，不能对整源登记 READ。仍无法读取时标 UNREADABLE，并继续处理其他可读内容。

其他 Agent 可帮助索引和核查，最终 Main 仍须实际读到所负责最终综合的完整相关来源。换 Main 时保留旧阅读回执作为历史，由新 Main 按当前输入范围建立自己的接手读取回执；不能把他人的 READ 改成自己的已读。

分段读取不保证材料一直存在于当前上下文。最终综合前重载登记、有效用户 bias、未决冲突与已映射关键正文，并按需回读精确原文；上下文压缩后沿索引恢复。尚未读完的范围继续记未读，不能靠“模型应该记得”关闭批次。

### 4.2 逐来源内容建立双向映射

依据 [Records 的去向规则](Records.md#preservation)，对原文消息或连续相关段落建立：

`source_id / revision / 消息或段范围 → 原内容及完整限定 → D/FR/C/F/G/Test/R 或归档条目 → 新包文件与锚点 → 保留/修订/等价合并/取代/否决/延后/无法核验/移入归档/重新激活 → 依据`。

反向检查输出的每个重要结论是否能定位来源原文和证据。无现成 ID 时按 Records 建立稳定 ID；重名保留来源命名空间，旧 C 的 Change 含义不能被新 Contract 覆盖。

| 来源内容 | 至少核对的去向 |
|---|---|
| 用户纠偏、方案取舍 | D；影响 FR/AC、契约、实施与验收时建立直接关联 |
| 需求、长期目标、未定产品行为 | FR/AC 与 D；未决进入 R/缺口，保留全部选项与条件 |
| 接口、数据与消费者 | C 与相关 F；保存旧/新完整语义及兼容范围 |
| 实际行为、尝试和实现状态 | F、实现说明；失败相关 G/Test/R 一并关联 |
| error、skip、清理、恢复 | G、Test、R；保留实际结果、复现条件与未覆盖边界 |
| 测试与运行证据 | 精确 Test/证据条目及 F/G/AC 反向链接 |
| 未解决事项、历史风险 | R；归档时另映射 `16_ARCHIVED_ITEMS.md` 的稳定条目锚点 |

等价重复可映射到同一目标，逐源独有的条件必须保留。纯确认、无新语义的往复也给出范围及“已由哪些正文完整覆盖”的依据，不能把相关讨论任意归为噪声。原文继续留包，映射负责语义去向。

`15_LOCAL_CHAT_INTAKE.md` 还须呈现每个来源的**实质讨论结论**：确认了什么、为什么、否决或替代了什么、哪些未定、什么证据支持、哪些地方仍未知。不能只有来源统计或全部写“见源码”；详细完整内容可位于其他同包正文，通过具体锚点直接到达。

### 4.3 处理冲突与归档关联

比较主张的身份、适用范围、时间和证据。用户明确决定约束产品目标，源码证明实现事实，运行回执证明对应环境中的执行；它们不互相冒充。先判断是否为不同版本或范围，再确认真实矛盾。

不按 Agent 人数、模型名、文件日期或最后发言多数投票。已清楚裁决的用户 bias 直接传播；真正待决的产品取舍保留选项、来源、影响和最小问题，不因局部待决停止其他可完成工作。

只要相关来源已读全、各主张完整呈现且去向清楚，未决争议可以登记为已知未决并通过该源的 RECONCILED；这不代表业务争议已解决。缺来源、缺原文或缺实读回执则不能以“有争议”掩盖。

归档按 [Archiving](Archiving.md) 核对五次 Handoff 的真实未使用复核历史。在批次关闭之前仅能预审新归档；最新有效提及、新证据或错误复现可以及时触发恢复，不能被旧计数压掉。归档条目必须保留关联来源、原条目和完整正文去向，不能用归档掩盖未注入的内容。先分类新事件，再判断未使用；全文复制与例行索引检查不能自动产生 MENTION。

<a id="intake-close"></a>
## 5. 最终 flush、冻结与关闭

批次状态单列为 `OPEN / FROZEN / CLOSED`，不代替来源或交付状态。开始为 OPEN；预期来源集合可以先冻结，实际输入仍按版本接收。FROZEN 表示本次将用于生成的全部来源版本和边界已固定，CLOSED 表示完成下列核对。

1. 对预期集合逐源复点。所有应纳入来源均到当前有效版本的 RECONCILED；MISSING、UNREADABLE、未读范围、未到的必需附件均不得静默留空。
2. 最后 flush：向每个来源取得截至本轮约定检查点的更新或明确无变化回执，重核最后导出之后的消息、附件、用户纠偏和集成/验证变化。回执不可取得时记缺口，不以安静或等待时间推定无变化。
3. 特别核对 Main 当前对话的最新用户 bias，以及跨窗口被替代的决定和未传播例外；将迟到内容写为新来源版本，重新实际读取并更新受影响映射。
4. 固定各源的最后消息/时间范围、材料清单、版本与内容身份，登记 `input_frozen_at`，状态转 FROZEN。关闭前再次检查已知待收输入；有新材料则回到 OPEN 并追加修订，保留旧冻结记录。
5. 检查旧→新和新→来源的语义覆盖，记录已知未决、排除理由、每源最终回执、Main reader 和结论。满足后登记 `closed_at`、`closed_by`，转 CLOSED，才能在该声明范围/检查点内写“上下文已收齐并完成注入”。

最终生成前若新用户决定或来源更新进入当前任务，重新打开批次并增加 revision，读取、映射、flush、冻结及关闭后重新生成受影响的完整 Handoff；不能让已过时的“关闭”回执继续背书新结论。

已经正式交付后的内容进入下一版新包，保留前一版冻结身份与快照。时间上的边界必须写清，不能声称覆盖尚未发生的消息。

缺源时仍制作已知信息的全量当前草案，标 `INCOMPLETE` 并写欠缺、影响、补充责任和最小材料。不能称批次 CLOSED、上下文全齐或 S8 最终 COMPLETE。资料齐全但有完整呈现的未实现、未测或待决事项时，分别如实记录，不把它们自动等同资料缺失。

<a id="intake-package"></a>
## 6. 最终包与 FULL 的责任

| 位置 | 内容与责任 |
|---|---|
| `.artifact/HandoffInput/<batch-id>/` | 接收原始快照只读，工作登记追加；关闭后全部登记一并冻结，可追溯全部有效来源版本 |
| `15_LOCAL_CHAT_INTAKE.md` | 同版预期登记、覆盖范围、身份与版本、接收/实读/映射回执、实质讨论结论、冲突、flush 和关闭结果 |
| `sources/local-chats/<source-id>/` | 相关原始会话、必要版本/分卷、原附件、结构化源回执及身份清单；尽量保持原格式 |
| `02/04/05/06/11/12/14` 等既有正文 | D/FR/C/F/G/Test/R 的完整有效语义、失败历史、依据及反向来源；按实际稳定文件名定位 |
| `16_ARCHIVED_ITEMS.md` | 归档正文、复核历史、原因、重开条件及来源映射；按 Archiving 执行 |
| `FULL_HANDOFF.md` | 同版 `00`–`16` 全部正文的完整合订，包括 15/16；正确说明未内联原始附件的依赖 |
| `MANIFEST.md` / `MANIFEST.sha256` / 完整 ZIP | 枚举实际随包材料及身份；校验全部最终文件，解压后可独立读取必需正文与来源 |

最终包必须**实际携入**完整相关原文及必需附件，不能只引用 `.artifact/HandoffInput/`、其他工作树、聊天网址或上轮包。包内来源映射采用最终相对位置；同时保存原始来源身份，以便反查。必要输入版本保留修改前后关系，不能把被替代原文覆盖掉。

原文内的历史本机路径或失效链接按原文保留，在 15 的映射中补充实际同包材料位置，拿不到时标缺口。检查报告区分原始记录中的历史引用与本版正文导航；不能为了让机械校验通过而篡改原文或伪造目标文件。

使用技能校验脚本时，可显式加 `--raw-chat-sources` 区分 `sources/local-chats/` 下原始 Markdown 的历史出站引用；这些文件仍纳入枚举、锚点、符号链接限制和哈希。当前正文指向来源的链接仍须有效，完整性判断仍需人工核对 15 的历史引用映射/缺口；开关不代表源内容已读。调用见 [机械工具](Packages.md#tool)。

S8 默认主体为 **19 份 Markdown**：`00`–`16` 共 17 份正文，加 `FULL_HANDOFF.md` 与 `MANIFEST.md`。原始来源附件独立计数；用户要求保真时，即使原聊天导出也是 `.md`、导致总数超过普通目标，也须保留并在清单说明。不得改扩展名规避计数，不得为文件数删减原文或必需附件。

启用 v2.2 结构化引擎时，同根另携 `ACTIVE_CONTEXT.md`、`CONTEXT_INDEX.md` 和完整 `state.json`；因此实际至少 21 份 Markdown，原始来源另计。当前 16 与两份视图来自同一状态；恢复的全文在 ACTIVE，旧历史在 state。FULL 还须全文承接 ACTIVE/INDEX，完整 ZIP 保留全部状态与来源，不能只发工作上下文视图。

FULL 完整合订正文中的需求、决定、理由、反例、失败、归档和讨论结论；不强制再逐字重复所有原始聊天附件。单独发送 FULL 时明确写“原始会话与附件另见需同时携带的 `sources/local-chats/`”；没有内联的内容不能宣称已包含在一个 Markdown 内。**完整 ZIP** 必须包含这些来源附件并可独立转交。

原始材料尚未拿到时保留缺口，不写成已经随包。包自足说明覆盖交接资料；实际仓库或宿主仍按声明的版本和权限读取，不能把缺失执行环境伪装成已附带。

<a id="intake-gates"></a>
## 7. 阶段接入与完成检查

| 时点 | 动作 |
|---|---|
| S1 分工或新增窗口 | 登记来源窗口、owner、范围及共享关系，避免临近 S8 才猜测参与者 |
| S4/S5/S6 及持续用户 bias | 保持完整输入定位；新增决定、失败和执行回执进入原来源，标明需要传播的窗口 |
| S7 专题收尾 | 连同完整专题材料导出该窗口相关完整讨论和结构化输入；完成截至检查点的回执 |
| S8 最终生成前 | 按本规范建立统一批次、收齐、实读、映射、flush、关闭，再作最终综合及归档判断 |
| S9 接手 | 读取 15、有效正文、16 及所需原始来源，按身份核对；不把上次 Main 读过当自己已读 |

交付前至少核对：预期来源都有明确结果；每源最新版本的必需原文/附件均已 Main 实读；讨论内容双向有去向；无变化来源也有回执；最新 bias 已 flush；批次 CLOSED；原始材料已同包；FULL 与 15/16 同版；缺口和未决未被伪装成完成。

哈希、链接和 ZIP 解压校验只证明相应机械范围。语义覆盖、实际阅读和最终综合仍由以上回执与正文支持。可用 [登记模板](../templates/15_LOCAL_CHAT_INTAKE.md) 开始，未有真实来源时保持未初始化，不填示例为事实。

## 8. 来源窗口导出 Prompt

将占位替换为当前已知值；缺少原生 ID/时间就明说未知。仅提供给用户转交，不代表已经发送或已收到文件。

```text
请为 AstroPhoto 最终全量 Handoff 导出本窗口输入。batch_id=[批次]，source_id=[来源]，范围=[专题及起止消息/时间/检查点]，交付位置=[获准的新目录或可下载文件]。
保留该范围完整可读原文及原附件，再提供结构化输入：用户bias原话与条件；接受/提议/延后/否决/替代及理由；尝试、失败、error/skip、未决；真实源码符号、测试断言与执行回执；工作树/HEAD及集成状态。注明来源身份、导出时间、最后检查点、文件清单和缺失范围。无变化也给明确回执并保留完整有效内容。
不要只写最终代码总结，不凭记忆伪造原文。无法导出的部分标MISSING/UNREADABLE。原材料只读；更新给新版本。最后再次检查导出后的用户纠偏与消息，交付更新或截至检查点的无变化回执，供Main实际读取。
```
