## 1. 归档解决什么问题

对某个抉择点、历史 test 回执、error、风险、延后方案或遗留问题，在最后一次有效提及或实质变化后的连续五个有效全量 S8 Handoff 中逐次复核，既未改变也未在新输入中有效提及，则默认暂时移出重点处理队列，将当前完整记录放入 `16_ARCHIVED_ITEMS.md`。这是本项目的关注分配规则，不是“时间过去所以问题无害”的事实判断。

v2.2 采用 `idle_handoffs`，将 v2.1 的“未变”进一步限定为“未变且未使用”。有效新提及会重置计数，即使代码和结论不变。使用 [细粒度提取](ChatExtraction.md) 给出证据，再由 [脚本](StructuredContext.md) 执行；旧 `unchanged_count` 不能未经核对直接当新计数。

用户已授权这项默认规则；满足条件后直接归档并记录，不再逐条重复请求批准。用户当前明确要求处理的条目继续 ACTIVE，不能被旧计数压掉。必要权限与实际执行范围仍按当前授权判断。

归档只调整注意力和文档位置，不等于修复、验收通过、接受方案、拒绝需求、取消约束或删除记录。未解决错误在归档后仍写未解决；历史失败仍是原日期和环境下的失败。

以稳定条目为单位处理，不按整份文件、整个模块或文件修改时间剪枝。有效需求、权限边界、验收条件、正式契约和拒绝过的方案约束不能因五轮未变而失去效力。

原始表述、条件、来源、讨论结论、被替代关系、证据与反例都保留。可合并已核实等价的重复文字，但要保留各来源，不能丢掉某个来源独有的限定条件。与 [信息保全原则](Principles.md#preservation) 一起使用。

<a id="states"></a>
## 2. 关注状态与业务状态分开

| 字段 | 取值或用途 |
|---|---|
| `attention_state` | `ACTIVE` 或 `ARCHIVED`，仅表示当前关注位置 |
| `idle_handoffs` | 从最近有效提及/实质变化基线后累计的连续未使用轮次，归档阈值为 5 |
| 剩余轮次 | `max(0, 5 - idle_handoffs)` 的派生显示，不维护另一套可漂移计数 |
| `baseline_handoff_id` | 最近有效提及/实质变化被完整记录的 H0；即时唤醒后的下一完整 S8 建立 H0 |
| `archived_at_handoff_id` | 实际满足归档条件并正式固化事件的 Handoff |
| `reactivation_event` | `REACTIVATED` 事件，回到 ACTIVE，重设基线并把计数归零 |

决定状态继续使用 `PROPOSED / ACCEPTED / DEFERRED / REJECTED / SUPERSEDED`。实现状态继续使用 `IMPLEMENTED / PARTIAL / PLANNED / OBSOLETE / UNKNOWN`。证据性质、执行结果、阻塞字段继续使用 [既有记录模型](Records.md#verification)。

`ARCHIVED` 不能填进决定状态或执行结果；`REACTIVATED` 不是第三种永久关注状态。归档事件不能把 `FAIL` 改成 `PASS`，不能把 `PLANNED` 改成 `IMPLEMENTED`。缺业务状态时写未知及原因，不因归档补造结论。

结构化记录中 `pinned=true` 表示固定保留，并写明原因；仍生效约束、当前用户必办与当前必需阻塞信息据事实固定。`CONSTRAINT` 类型强制固定；历史讨论可以单独建可归档记录并关联它。TEST 归档只调整历史回执/讨论的加载，不删除可执行测试、覆盖矩阵或当前实际失败结论。

<a id="checkpoints"></a>
## 3. 什么算一次有效 Handoff

一轮必须同时满足以下条件：

1. 属于同一正式交接主线的独立全项目 S8 快照，存在可核对的父子关系。
2. 已完成本轮 Local Chat 批量收集、实际读取、来源对账和最新用户 bias 融合。
3. 本条目在该轮真实复核，有负责人、来源、比较结果和当前影响记录。
4. 本轮通过完整性与收集批次门，`completed_state = COMPLETE`，正式交付记录与包内容一致。
5. 与已计数轮次不是同一批次的重打包、另一个文件格式、草案重试或并行分支副本。

最小快照元数据放在 `00_START_HERE.md` / `MANIFEST.md`，无需为此强制引入数据库：

```yaml
handoff_id: <本次唯一正式快照标识>
parent_handoff_id: <本主线上一正式快照标识；首版明确说明>
source_batch_id: <本次实际来源汇合与复核批次标识>
completed_state: COMPLETE | INCOMPLETE
```

同一天可以有多轮，只要它们是主线上依次完成的独立交接，且各有真实收集和复核。日期变更、目录序号加一、改名 ZIP 或人工新建批次号均不足以证明独立一轮。

没有新聊天内容的完整复核也可以成为一轮，但必须如实记录本轮来源盘点和复核事实；不能将同一次读取拆成五个包制造五轮。

不同分支的并行包不能相加凑五轮。并入正式主线时，重新核对条目与证据；只有能证明属于同一连续正式主线的历史检查点才可继承。其他分支记录仍保留为来源，不当作额外的时间轮次。

截图中的目录列表、文件数量、ZIP 数量和修改日期只提供定位线索。未实际读取对应快照和复核记录，不得据此填写计数。

<a id="material-change"></a>
## 4. 按语义判断是否变化

| 情况 | 是否重设基线与计数 | 记录要求 |
|---|---|---|
| 新用户 bias、优先级、范围、约束或当前明确处理指令改变条目 | 是 | 忠实记录原话、来源与受影响位置 |
| 新对话中明确提及条目，或经原文映射确认的间接提及，即使内容未改 | 是 | 给出新消息位置、事项 ID、事件 ID 和提及依据 |
| 实际执行新的测试，或同一错误新发生/复现 | 是 | 有新执行/发生证据；不能将旧回执重贴当新事件 |
| 问题行为、触发条件、影响、风险、恢复方式或解决方案改变 | 是 | 保留旧状态，写完整新状态和依据 |
| 新证据使原因、结论、实现状态、验证边界或相关风险发生变化 | 是 | 区分源码、历史运行、本轮运行及推断 |
| 新失败、相关测试结果变化或发现旧证据不适用 | 是 | 保留结果身份，不能因仍未修复就说没有变化 |
| 仅排版、标题、编号映射、日期、路径迁移、拼写修正 | 否，前提是语义和限定条件相同 | 保留映射及有效链接 |
| 例行复核再次得到同样结论，没有新增事实或改变证据适用性 | 否 | 保留本次复核记录，不冒充重新执行测试 |
| 全量包携带旧内容、历史原话引用、脚本生成视图或例行索引扫描 | 否 | 标历史携带/引用/检查，不能自触发提及唤醒 |
| 无法读到关键材料，或未检查条目是否改变 | 无法判断，不计一次 | 记录缺口，补证或另立新基线 |

mtime、文件哈希、字节数和 diff 只能辅助定位；文件字节相同不等于外部事实不变，文件字节改变也不等于条目语义改变。五轮“没有修改”以条目实际语义和相关证据边界为准。

对变化性质存在实质不确定时，不自动宣称“未变”。先记清不确定处和必要证据；本轮不能支撑计数就不计数。

<a id="counting"></a>
## 5. 计数、缺口与正式固化

H0 是最近有效提及或实质变化的完整基线，计数为 0；H0 后的 H1、H2、H3、H4、H5 各复核一次且未变、未被有效提及，计数依次为 1、2、3、4、5。达到 5 即归档，不再多等第六次。不能把 H0 算成第一轮。

执行顺序固定如下：

1. 完整读取上一版基线、归档正文和既有计数账。
2. 完成本轮所有已声明 Local Chat 的批量读取与来源对账，融合新证据和用户 bias。
3. 对条目逐一比较完整语义与新增提及事件；变化或有效提及重设 H0 和计数，固定项保持 ACTIVE。
4. 对没有变化的条目检查主线、批次、真实复核和历史连续性；计算本轮候选计数与候选归档。
5. 将候选结果、档案全文、仍有效规则及当前影响摘要写入本轮草案，完成全量 S8 检查。
6. 只有本轮收集批次和包完整性门通过，才在同一次正式完成中固化计数与 ARCHIVED 事件；随后生成最终清单、合订本和完整 ZIP。

第 4–5 步期间本轮还没有完成，候选数字不得当作已累计历史。失败草案、INCOMPLETE 包和重试不会增加计数，也不会生成已生效的归档事件。正式化后如内容改变，重新校验本次新包，不回写旧包。

如果中间存在未复核或资料缺失的正式轮次，不能跳过缺口把前后读到的相同文字拼成连续五轮。可选择：

- 补齐缺轮的原包、来源和该条目复核证据，经核对后恢复可证明的连续账；补证说明记录在新包，旧包不改。
- 无法补证时，从本轮重新确认的完整状态建立新 H0，计数归零；旧计数和缺口作为历史保留。

在缺口未解决前，保留最后已证明的历史计数并标明资格冻结；它不是可以继续累加的有效连续序列。未完成草案本身不属于正式轮次，但草案期间产生的实际新证据仍须在下一次完整汇合时处理。

归档后停止为“是否再次归档”无意义地累计 6、7、8……；每轮检查新输入是否触发重新激活，不要求为重复计数而反复加载全部冷档全文。原五轮账及归档时点完整继承。脚本的 dry-run 不写状态，预览目录只承载候选；同一正式 Handoff 重跑不得重复加一。

## 6. H0 到 H5 的具体序列示例

**以下完全是假设示例，不是本项目已经存在的 Handoff 或已验证记录。** 例中 `DEMO-H0` 至 `DEMO-H5` 沿同一父子主线依次完成，每轮有不同真实收集批次。

| 假设快照 | 条目事实 | 该轮完成后的计数 | 关注状态 |
|---|---|---|---|
| DEMO-H0 | 新记录某个延后错误，保留触发条件、当前影响和未解决身份 | 0 | ACTIVE |
| DEMO-H1 | 批量汇合后真实复核，条目与相关证据未变且无有效新提及 | 1 | ACTIVE |
| DEMO-H2 | 同样完成复核，未变 | 2 | ACTIVE |
| DEMO-H3 | 仅改排版；事实、影响和限定条件未变 | 3 | ACTIVE |
| DEMO-H4 | 同样完成复核，未变 | 4 | ACTIVE |
| DEMO-H5 | 第五次完成复核，未变；全部完成门通过 | 5 | ARCHIVED，错误仍未解决 |

如果 DEMO-H3 出现新用户 bias，则它成为新 H0，DEMO-H4 计 1，DEMO-H5 计 2，不能归档。如果 DEMO-H3 未实际复核，则冻结资格，补齐证据或以新确认快照重建 H0。

如果 DEMO-H5 只完成草案，候选为 5，但正式历史仍停在 4；若该草案最终未通过完整性门，不能写“已归档”。

<a id="archive-record"></a>
## 7. 归档文件必须保留的内容

使用 [16_ARCHIVED_ITEMS 模板](../templates/16_ARCHIVED_ITEMS.md)，沿用实际条目 ID；同名来自不同来源时增加来源映射。锚点使用稳定 ASCII 标识，不以会改变的标题替代身份。

每条归档正文至少包括：

- 稳定 ID、原 ID、来源命名空间、标题、类型、所属领域、当前关注状态。
- 首次出现与最后实质变化的 Handoff/来源，归档 Handoff、主线、批次及起止范围。
- 原始表述、全部独有条件、讨论和历次修订的完整语义；原始来源的实际定位及可访问性。
- 现行决定状态、实现状态、证据身份、执行结果、是否解决、当前影响与阻塞；没有证据的字段明确未知。
- H0 基线和 H1–H5 逐次复核账：快照、父快照、批次、完成状态、复核者、来源、变化判断及计数。
- 归档原因、当前未解决身份、仍有效规则和 AC 的正文去向、当前影响摘要位置。
- 重新激活条件、事件历史、替代/关联 ID，以及归档正文与当前章节的双向稳定链接。

较长原始聊天或日志可以保留在同包实际存在的来源文件中；归档正文仍应完整表达条目，不能仅写“详见旧聊天”。引用原文和模型归纳分开标识，无法取得的原文写明缺失，不反向伪造。

当前归档视图完整承载仍为 ARCHIVED 的条目；恢复的条目全文移到同版 `ACTIVE_CONTEXT.md`，归档仅留带稳定锚点的恢复索引与活动链接。完整旧正文、原状态、五轮账与事件仍在同包 `state.json` 及旧不可变快照中；每个旧条目在 [信息去向表](Records.md#preservation) 中仍有本轮位置。不得只搬视图却丢掉规范化历史或原始来源。

## 8. 当前正文留下什么

把过长讨论移入归档后，当前章节继续保留以下两类内容：

1. **仍有效的规范正文**：用户决定、权限、验收条件、正式契约等继续完整生效；不能只把它们藏进归档。
2. **当前影响摘要**：条目仍影响当前工作时，写稳定 ID、未解决/已解决身份、触发条件、当前影响/阻塞、下一步或暂缓条件，并直达档案锚点。

摘要是阅读入口，归档正文是完整记录；两者共同存在于当前全量包。摘要不能弱化严重性、隐藏失败、暗示已解决，也不能覆盖用户当前明确的处理优先级。

输出包中的链接示意如下，仅在实际文件与锚点已经存在时填写：

```markdown
- <真实ID>：未解决；<触发条件与当前影响>；<阻塞或继续条件>。
  [完整历史与五轮账](16_ARCHIVED_ITEMS.md#archive-真实ascii-id)
```

与当前范围已无关联的纯历史讨论可只保留档案索引和来源映射。是否仍有效、仍影响当前工作必须有依据，不能只看年限或计数。

<a id="reactivation"></a>
## 9. 什么时候重新激活

出现以下任一相关变化时，在汇合阶段追加 `REACTIVATED` 事件，将 `attention_state` 改为 ACTIVE，建立新基线并把计数置 0：

- 新输入中明确提及该条目，或 Main 根据新原文确认间接语义提及；无需等待代码发生修改。
- 用户明确要求继续处理，或提出影响该条目的新 bias。
- 问题复现、影响扩大、出现新风险/反例、依赖或范围改变。
- 源码、运行事实或验证证据改变，原有结论不再足够。
- 当前任务需要决定该问题，或既有重新打开条件满足。

记录触发来源、旧归档状态、完整新状态、当前工作位置与新的基线。当前全文从归档视图移回活动视图，索引注明已重新激活并直达活动正文；旧归档事实、原文和事件保留在规范化历史与旧快照，不将新处理伪装成从未讨论过。

当前任务中确认有效新事件后可运行 `touch --apply` 立即恢复，无需等待最终 S8 收齐。它不会增加 Handoff 轮次；下一完整 S8 将该条目设为 H0=0。最终归档/增加闲置轮次仍必须等全量收集与完成门。相同原始事件重复传输不得再次唤醒，事件重导出保留原发生身份。

仅为了生成新包而再次读到同一条目，不自动重新激活。归档后的例行检查只确认有无触发；没有新事实就完整继承。

<a id="packaging"></a>
## 10. 与 S8、S4 和合订本共同工作

S8 先完成 Local Chat 输入汇合，再执行本规则。前者不完整时，不宣称已经记录所有窗口，也不能用旧计数抢先归档本轮可能重开的条目。

每版全量 S8 都包含当前 `16_ARCHIVED_ITEMS.md`、`ACTIVE_CONTEXT.md`、`CONTEXT_INDEX.md` 和含完整历史的 `state.json`，以及来源可达关系；`FULL_HANDOFF.md` 同步合入人可读正文，重写内部链接。新 Agent 从当前包就能找回历史原因，不需要向前拼附件。旧 Handoff 快照保持原样。

日常 Chat 默认从活动视图、有效约束和轻量索引开始，按当前任务取回必要归档全文。完整 ZIP 的存储范围保持全量，工作上下文按需装载；不能每次先灌整个 FULL 再声称归档节省了上下文。

S4 携带与当前专题有关的完整归档上下文、有效条件、来源和重新激活记录，可放入已有来源/保全章节或独立归档文件，并合入 `FULL_REQUIREMENTS.md`。无关专题历史不必强行纳入 S4；相关内容不能仅链接到未随包提供的旧 S8。

首次启用本规则不追造过去五轮的复核记录。已有完整可核对历史可以据证重建；否则从本次确认的实际基线开始。没有可读项目历史时只交付空模板和规则，不能宣称“项目没有问题”或“已完成五轮审计”。

## 11. 交付前检查

- 输入表中的每项都有本轮正文、完整档案或明确缺口位置；新输出能反查来源。
- 归档计数从 H0 后起算；各轮独立、同主线、完整且真实复核，没有草案、分支或重打包凑数。
- Local Chat 与 bias 融合发生在归档判断前；未完成轮只保留候选，不伪造已生效事件。
- 每个归档条目保留原始语义、全部条件、未解决身份和五轮账；当前影响与有效规则仍可直接找到。
- 新触发条目已重新激活并归零，原归档历史保持可查；当前用户任务未被自动剪掉。
- 全文档案、合订本、索引、活动摘要和信息去向表一致；链接与锚点实际可达。
- “都有记录”的结论限定于已提供、已成功读取并完成来源对账的输入；缺失或不可访问窗口显式登记。

这套机制提供可追溯的覆盖检查，不把计数、文件存在或哈希当作语义无损证明。具体完整性回执遵循 [包检查](Packages.md#checks)。
