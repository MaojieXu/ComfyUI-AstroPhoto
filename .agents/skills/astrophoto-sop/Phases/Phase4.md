# Phase4 · S4：专题全量开发包

[返回 SKILL.md](../SKILL.md) · [核心原则](../references/Principles.md) · [完整包规则](../references/Packages.md) · [记录字段](../references/Records.md)

阶段编号固定为 S4。由 Web Chat 合成可实施的专题全量包；必要时 Local Main 承担合成，并负责补充本地事实。S4 每次输出完整版本，不能交付只包含本轮变化的附件。

目录：[目标](#scope) · [输入](#inputs) · [构建步骤](#steps) · [交付](#outputs) · [验收与分支](#exit) · [Prompt](#prompt)

<a id="scope"></a>

## 1. 目标与完整性边界

让一位没有原 Chat 记忆的 Local Agent，取得本次包后能够理解本专题全部有效目标、决定、实现依据、实施方法、异常恢复、兼容约束和验收条件。

“全量”覆盖本专题所需的完整语义：本轮未改变的有效内容仍进入新包；被取代的内容保留历史身份与替代关系；延后且未取消的需求继续登记。

专题之外的共享依赖，需要纳入实施本专题所必需的契约、消费者和边界。S4 的全量范围不会自动扩大为全项目实现，也不要求复制整个仓库源码。

残差记录说明变化如何进入完整基线。跳跃链接让用户原始依据、AC、源码、Guard 与测试直接互达。执行方法见 [核心原则](../references/Principles.md)。

<a id="inputs"></a>

## 2. 输入与可信度

读取并登记以下实际材料：

1. 本专题原始需求和完整有效 PRD，包括仍有效的旧条款。
2. 用户最新及此前有效的纠偏、决定来源、否决/取代/延后关系。
3. 适用原型、交互状态与模拟边界。
4. S3 真实源码披露：工作树、路径/符号、调用链、Guard、消费者和测试断言。
5. 上一版完整专题包、当前全局 Handoff 的相关契约与限制。
6. 官方参考及其目标版本适用性，必要的许可和上游复用信息。
7. 已有实施或验证回执，以及当前材料缺口。
8. 本专题相关的完整归档条目、Local Chat 对话来源及读取/融合回执；按 [归档规范](../references/Archiving.md) 和 [对话注入规范](../references/LocalChatIntake.md) 保留来源边界。

把材料区分为用户决定、源码事实、运行证据、历史记录、方案与未知。仅提供本机路径的材料，由可访问的 Local 阅读；Web Chat 不能因此宣称已经审阅正文。

缺少影响实施的源码时，先形成完整当前草案并标 `INCOMPLETE`，给出定向补充请求。不得用虚构符号填满技术表或把缺口隐藏在“沿用旧版”中。

<a id="steps"></a>

## 3. 构建完整包的步骤

### 3.1 建立输入条目的去向表

以原始 PRD、上一版完整包及用户纠偏为基础，列出每条有效需求、决定、AC、共享约束、Guard、验证条件和未完成项。

| 原条目 / 来源 | 本轮处理 | 新包位置 | 处理依据 | 未解决项 |
|---|---|---|---|---|
| 填入真实编号与来源 | 保留 / 修订 / 取代 / 延后 / 否决 / 归档 / 恢复关注 | 填入实际文件与锚点 | 用户决定或事实证据 | 无则明确写无 |

没有变化的内容完整保留。真正重复的信息可以共用一个包内正文条目，但要保留各来源映射和全部独有条件。只有明确依据才能改变条目的状态。

本专题完整性包括活动正文、相关归档全文及必要来源附件。归档内容携入同版包并保留稳定 ID，不能只链接旧 Handoff；仍有效的规则、约束和当前阻塞保持可见。Local Chat 中独有的决定、条件、失败与未完成项进入完整正文，原始对话材料按来源规范同包保留。S4 本身不累计五轮 S8 计数；新的明确处理要求或实质证据按 S6 恢复相关条目。

对未找到去向的旧条目先调查，不默认删除。长度减少、字节数增加或条目数量相等，都不能单独证明语义完整。

### 3.2 合成当前有效 PRD 与决定记录

形成能独立阅读的完整 PRD；同时明确哪些决定被最新用户 bias 修订、哪些保持有效。用户已明确要求的行为直接进入当前目标，未决定的产品选择保持其状态。

保留原型文件并使交互与当前 PRD 一致。界面和工程方案不一致时，定位受影响 AC 与差异，修正具体条款；不要重开已经明确的无关决定。

### 3.3 逐 AC 映射到工程契约

为每条 AC 填写下列内容。可分表呈现，但稳定编号必须贯穿。

| 工程项 | 必需内容 |
|---|---|
| 用户行为 | 条件、动作、可观察结果及来源决定 |
| 现状 | 已披露的实际行为、工作树标识与缺口 |
| 改动方式 | REUSE / MODIFY / ADD；最小方案与必要性 |
| 源码落点 | 已存在的 `path::symbol`、签名、调用方；拟新增符号明确标为计划 |
| 调用顺序 | UI / API / 服务 / 存储 / 外部进程或 Node 的实际边界 |
| I/O | 类型、字段、约束、返回值与用户可见回执 |
| 副作用 | 持久化、文件发布、资产登记、缓存、并发及清理 |
| 共享影响 | 生产者、消费者、旧值/新值、兼容及实施顺序 |
| Guard | 校验/拒绝实际生效点，错误码、skip 条件、恢复或回滚 |
| 测试 | 已有精确用例与断言，拟新增断言、环境、命令及完成条件 |
| 依据 | 用户决定、源码、官方参考和相应证据边界 |

保留关键源码披露中的判断依据和必要片段。避免大段无关源码；任何省略都不得使调用顺序、状态归属、重要分支或副作用无法核对。

### 3.4 写清异常、skip 与恢复

针对真实行为覆盖适用边界：输入/类型/范围、路径与文件、权限、状态与并发、外部进程、取消、预览及宿主生命周期。

每个适用条件写出“触发 → 生效调用点 → 可观察回执 → 是否跳过后续动作 → 已产生副作用如何处理 → 可恢复状态 → 对应断言”。

不适用项注明理由。没有发现 Guard 时保留搜索范围与 `NO_GUARD_FOUND`，并明确是否计划补充。产品要求允许的行为，不能被无依据新增的限制静默改变。

数据处置严格继承用户决定的范围。某批测试数据获准直接替换时，不强行设计无需求的迁移，也不把该决定扩张为删除其他真实数据的授权。

### 3.5 核对官方复用与代码示例

把每个关键复用点写到上游仓库、版本/提交、路径/符号及项目调用位置。区分公开 API、内部实现、许可允许的移植与本地补足；查证失败保留缺口。

附实施所需的短小官方代码示例，并注明出处、目标版本适用性和需要替换的变量。官方示例仅说明接入方式，不能标为仓库已存在实现或实机验证结果。

前后端功能的实际复用核查按 [项目约束](../references/Project.md) 和目标仓库适用 Skill 执行。查证入口见 [官方参考](../references/Sources.md)。

### 3.6 制定实施顺序与验证方案

按可以从正式入口触发的端到端操作安排实施，先完成用户可观察结果，再补同范围的异常与恢复。直接复用优先，保持已有用户修改和未受影响行为。

测试设计同时写明已有断言和缺失条件。区分静态、单元、真实临时文件/数据库、HTTP 替身、真实 CLI、宿主注册、原生队列、浏览器、MCP 和发行证据。

计划测试写为计划；历史执行保留原日期和环境；本轮实际执行必须有回执。构建命令可能写入产物时说明副作用。不能把用例名或通过数量当作全部 AC 已验证。

实施 Prompt 需说明整包版本、读取顺序、目标、允许操作、关键约束和回报要求。详细契约由包内正文承载；Prompt 保持简洁且可独立转交。

### 3.7 构建双向跳跃链接

检查至少这些路径可以直接到达：

- 原始需求 / 用户纠偏 → 当前决定 → FR/AC。
- FR/AC → 原型状态 → 实施文件/函数 → Guard → 测试断言。
- 测试 / Guard → 对应 AC 与用户可见行为。
- 共享契约 → 生产者、消费者、兼容方案和组合验证。
- 本轮残差 → 原条目、当前完整正文、修订依据。
- 未完成 / 未验证项 → 缺口、下一步、所需环境与负责人。

沿用既有 ID；来源重名时建立对应关系。行号随版本变化，应同时保留符号与工作树身份。包内链接目标须实际存在。

### 3.8 生成版本化目录与 ZIP

依 [完整包规则](../references/Packages.md) 在新目录生成完整版本，建议本地落点为 `.artifact/<专题>/<版本>/`。保持旧包完整，除非用户已明确指定覆盖。

文件按职责合并或拆分，覆盖完整 PRD/决定、原型、源码披露、契约/实现计划、错误与测试、官方参考、实施 Prompt、输入去向及清单。从同版全部专题正文及相关归档全文生成 `FULL_REQUIREMENTS.md`，重写内部导航，不另行摘要正文。原始对话导出属于来源附件；正文保留全部必要语义，单文件投递时说明仍需携带的必要附件。

每次 S4 都生成以主要需求及版本命名的完整 ZIP，包含本次目录内全部交付文件。不要只打包变更文件或要求接手者叠加旧 ZIP。

原始需求、关键决定和实施必需的项目规范须在包内自足。真实仓库仍由 Local 按路径读取，官方网页可作为外部来源；二者不替代包内所需的具体契约与结论。

<a id="outputs"></a>

## 4. 必须交付

交付完整版本化目录及同内容 ZIP，并在回执中提供：

1. 包名、版本、覆盖范围与实际包含的文件。
2. 新接手者阅读入口和短实施 Prompt。
3. 全部有效 AC 的工程映射与完成前提。
4. 输入条目去向、被取代关系、未决/延后/未验证项，以及相关归档全文与对话来源的落点。
5. 包内链接、原型、清单及 ZIP 内容的检查结果。

材料不完整时仍交付当前能够成立的完整草案，并标明 `INCOMPLETE`、缺失材料及影响；不要宣称达到最终实施就绪状态。

<a id="exit"></a>

## 5. 验收条件与后续分支

逐项检查：

- 全部有效条目均有包内去向，未变化内容未因“增量”而消失。
- 没有以“同上版”“其余不变”或只有旧附件链接代替必要正文。
- 每条 AC 可追到工程动作、失败处理和拟验收断言。
- 已存在与拟新增符号、历史与本轮验证明确分开。
- 用户纠偏已同步到 PRD、原型、契约、测试及实施 Prompt。
- 共享消费者、兼容决定、数据副作用及恢复均明确。
- 所有包内链接和锚点有效，适用原型可运行，ZIP 解压内容与目录一致。
- 完整合订本由同版全部专题正文生成，内部跳转有效，与专题全文一致。

达到实施就绪条件后进入 [S5](Phase5.md)。关键源码证据缺失时回到 [S3](Phase3.md) 的具体问题；只有新的产品取舍才回到 [S2](Phase2.md)。补充完成后再次生成全量 S4 包。

## 6. 可直接复制的 Prompt

```text

逐项核对旧内容去向，完整保留仍有效需求、约束、证据和延后项，记录修订/取代关系。每条 AC 对应真实或明确拟新增的 path::symbol、REUSE/MODIFY/ADD、调用顺序、I/O、副作用、消费者与兼容、Guard/error/skip/恢复、精确已有断言或拟新增验收；区分历史验证、本轮执行和未知。附目标版本官方短示例与来源。
输出完整 PRD、适用可运行原型、必要源码披露、技术契约与实施计划、错误/测试、决定与残差、完整性去向、短实施 Prompt 和清单，建立双向跳跃链接。生成完整目录及同名完整 ZIP；不得用增量附件或“同上版”替代正文。资料缺失则标 INCOMPLETE 并列出定向补充问题，不虚构实施就绪。
```
