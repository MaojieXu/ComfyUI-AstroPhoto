## 1. 职责与输入

将用户每次明确纠正纳入当前有效规则、代码与验收条件。用户的 bias 持续作用于流程；对用户已经决定的行为直接推进，不再机械要求第二次确认。

Local 处理事实已经明确的实现修正。Web Chat 处理仍有实质产品取舍的体验或行为问题，并按需要提出定向源码披露。只要求解释或 Prompt 时，完成对应交付，不代替用户启动实现。

取得以下输入；已有材料直接沿用，缺失项按具体影响记录。

| 输入 | 必须辨认的内容 |
|---|---|
| 用户反馈 | 原话或保留条件的准确复述、发生场景、期望结果、必须保留的行为 |
| 完整有效需求 | 当前专题完整 PRD/AC、原型、技术契约及此前仍有效的决定 |
| 当前实现 | Local 的真实入口、工作树、目标实例与复现回执 |
| 验证记录 | 用例断言、执行环境、日期、结果及没有验证的边界 |
| 其他专题依赖 | 共享接口的提供方、消费者、负责窗口、集成目标 |

用户给出截图时，辨认其显示的状态；截图无法证明持久状态或调用链时，提出对应的本地核对问题。不要因材料不全重新询问已经明确的产品意图。

<a id="s6-work"></a>

## 2. 执行步骤

### 2.1 确定反馈的性质

| 分类 | 判断依据 | 后续动作 |
|---|---|---|
| `BUG` | 当前实现违反仍有效的 AC | 定位最小责任入口并修复，保留其他已接受行为 |
| `CHANGE` | 用户明确改变目标、约束或体验 | 记录新决定及取代范围，更新受影响的契约和实现 |
| `DOC_DRIFT` | 文档与已有明确决定、真实实现或证据不一致 | 修正文档，保留变更来源；不要凭文档错误反改正确代码 |
| `UNKNOWN` | 缺少足够证据定位原因 | 列出已知事实和最小待核对问题；已明确的需求仍然生效 |

同一反馈可以包含多种问题，按条目分别处理。分类服务于定位，不让分类讨论阻止已授权的明确修正。

### 2.2 形成可追溯的 bias 记录

沿用既有 Decision ID；没有编号体系时按 [Records](../references/Records.md) 建立。

记录用户来源、旧规则、新规则、影响范围、取代关系、保留条款、受影响 AC、共享消费者和下一步。用户明确决定标 `ACCEPTED`；Agent 提议保持 `PROPOSED`。被取代决定标 `SUPERSEDED` 并链接新决定，不删除其历史来源。

真实新增讨论重新提及条目，即使行为与结论未变，也按 [归档规范](../references/Archiving.md) 沿同一稳定 ID 恢复 `ACTIVE` 或将 `idle_handoffs` 归零。新用户要求、实质证据、实际测试运行、错误复现、范围或风险变化同样处理；按 [ChatExtraction](../references/ChatExtraction.md) 记录来源范围、事件 ID 和分类，历史复制、旧日志及例行扫描不唤醒。

使用 [StructuredContext](../references/StructuredContext.md) 的 `touch` 可在 S8 尚未完成时及时恢复。由 state 生成新的活动/归档视图：条目全文移回 `ACTIVE_CONTEXT.md`，当前归档保留稳定锚点与简短恢复索引；全部历史正文、原计数和事件仍在完整 state 与旧快照中。`REACTIVATED` 是历史事件，不是第三种注意力状态，不自行改变决定、实现或验证结论。当前明确必办和有效约束按依据固定保留，不用旧空闲次数拒绝落实。

本阶段反馈及来源按 [对话注入规范](../references/LocalChatIntake.md) 留存，供最终 S8 完整汇合后再判断剪枝。S6/touch 不增加 S8 次数；touch 后下一次完整 S8 建立 H0=0。读取 CURRENT 指向的状态，不能手改生成视图、复核账或计数。

将这条记录直接连接到受影响的 PRD、原型、技术契约、源码入口、Guard 和验收断言。让最终实施者可以越过中间摘要读到用户的纠正及原始条件。

保留尚未取消的长期需求和仍有效的例外条件。用户对一个测试数据集的处置决定，仅在该范围内生效，不扩张为全部真实资产的删除授权。

### 2.3 沿正式入口修正

Local 先核对已有改动、实例身份和实际复现条件，再沿 UI/API/Node/MCP 到状态所有者追踪。共享工作树由 Local Main 统筹写入；不要覆盖其他窗口刚发生的改动。

优先复用和局部修改。明确用户要的可观察结果，检查成功、失败、skip、取消、清理、回滚、只读与旧消费者等适用路径。字段变化需要说明生产者、消费者及兼容处理。

有实质未决取舍时，Web Chat 只比较受影响的少量方案，列明差别和代价。已有用户决定、现成复用点和技术范围内的普通选择直接采用。缺少本地事实时，返回 [S3](Phase3.md) 的定向披露，不扩散成无关全仓扫描。

### 2.4 更新完整的有效规格

修复代码可以只涉及少量文件。更新正式需求包时，按 [S4](Phase4.md) 生成本专题完整新版本，保留未改变的全部有效内容。Decision Delta 是包内的变化索引，不能成为唯一交付附件。

将用户纠偏传播到所有受影响的原型、契约、实施要求与测试条目。逐项核对旧内容的新去向；禁止以“其余同上版”代替应进入本轮包的正文。

S6 尚处于即时修正、用户未要求发布规格包时，可以先交修正回执和有效决定，但要明确它是实施回执。进入 S4、S7 或 S8 时，将回执完整融合进对应范围的全量交付。

### 2.5 验证并同步影响

按本轮授权运行能够观察到变化的最小必要验证，补充受影响回归。读实际断言，区分产品失败、测试配置失败、过期 fixture 和环境失败。用户明确先不测试时记录 `NOT_RUN` 及原因。

对跨层状态修正，检查最终持久状态及重新读取后的用户可见行为。一次 Mock 通过不代替真实 CLI、宿主队列或跨卷行为；各环境分别记录结果。

反馈影响其他专题时，记录受影响窗口、旧/新契约、需同步的实现和断言，以及集成目标。没有跨专题影响时在所属专题完成。未取得其他窗口回执时，记录具体缺口，不假设对方已经改完。

向其他窗口实际发消息、归档窗口或合并代码，按本轮已有授权执行；只读同步请求只做核对与汇总。

<a id="s6-output"></a>

## 3. 必须交付

- 反馈分类与来源明确的用户决定，包含旧行为、新行为和保留范围。
- 实际改动位置、调用链、Guard/error/skip/恢复变化，以及共享消费者影响。
- 对应 AC 的验证断言、环境、命令、日期与结果；未运行或仍阻塞的条件。
- 受影响文档的更新状态；若输出正式需求包，给出完整版本及包内信息去向。
- 仍有差异、未完成项及下一步；保留尚未取消的长期要求。
- 涉及归档条目时，记录同 ID 的恢复事件、计数重置依据及继续保留的历史位置。

使用 [Records](../references/Records.md) 的独立字段记录决定、实现、证据来源和执行结果。`BLOCKED` 作为阻塞字段，说明具体条件。

<a id="s6-exit"></a>

## 4. 退出条件与分支

用户最新纠偏已传播到实际负责该状态的位置，相关 AC 有结果或明确未验证原因，未受影响要求仍可定位。

- 实现修正完成：回报结果，继续本轮剩余已授权任务。
- 需要调整正式规格：进入 [S4](Phase4.md)，交付专题完整新版本。
- 仍有未决定产品取舍：仅将该条目交回 [S2](Phase2.md)，继续无依赖的已授权工作。
- 专题准备收尾：进入 [S7](Phase7.md)，按完整专题范围回收。
- 用户要求整轮交接：进入 [S8](Phase8.md)，覆盖全项目，不能以本次反馈记录代替。

<a id="s6-prompt"></a>

## 5. 可复制 Prompt

根据本次接收方填入正文或可读取路径。对话里已有内容直接填好，避免把可推断信息再次交给用户补充。

```text
按 AstroPhoto SOP 执行 S6。专题：[专题]；完整有效规格：[附件或路径]；用户反馈：[原话/条件/期望/必须保留]；Local 现状与回执：[材料]；允许的改动和验证：[范围]。
逐条区分 BUG、CHANGE、DOC_DRIFT、UNKNOWN。明确决定直接采用，记录旧/新规则、来源、取代范围、保留项及受影响 AC。真实新提及沿同 ID touch恢复或归零，即使代码未变；旧日志和例行检查不唤醒。由state生成活动/归档视图并保留历史。Local 核对真实入口与状态所有者并最小修正；Web Chat 只对未决取舍比较方案，缺源码时给短披露请求。
检查错误、skip、恢复、消费者及实际测试断言，分别报告实现、证据环境和执行结果。将用户 bias 直接连接到需求、契约、源码和验收。正式规格更新按 S4 输出专题全量包，保留未改变内容和未取消需求；变化清单只作包内索引。返回实际结果、未验证项、同步影响和下一步。
```
