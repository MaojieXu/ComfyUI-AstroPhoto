## 1. 职责与边界

由 Local Main 为本轮任务建立可核查的当前基线。先确定本轮覆盖范围，再观察真实工作树、相关入口、目标实例和证据。

区分以下四类结论：

| 类别 | 本阶段回答的问题 | 依据 |
|---|---|---|
| 有效需求 | 用户现在要求什么，哪些旧要求仍然有效 | 用户原话、有效 PRD、决定及纠偏记录 |
| 源码事实 | 当前工作树实际上实现了什么 | 正式入口、函数、调用链和持久化位置 |
| 运行事实 | 用户正在使用的实例加载了什么 | 实例身份、Schema、前端构件与操作回执 |
| 验证事实 | 哪些行为在哪个条件下经过验证 | 断言、命令、环境、日期和结果 |

只读核查业务源码、依赖、宿主与用户数据。S0 不包含功能修复、安装依赖、发布或清理工作树。

用户只说“注入上下文”时，读取可获得材料并确认理解即可。没有实际仓库访问和核查结果，不能宣称完成 S0 源码核验。

S0 的专题核查范围不改变 S4、S8 的全量交付要求。需要全项目交接时转入 [Phase 8](Phase8.md)，不能用本专题的 S0 报告代替完整项目盘点。

<a id="p0-input"></a>

## 2. 输入与读取顺序

先读 [核心原则](../references/Principles.md)、[记录字段](../references/Records.md)；根据任务读 [项目背景与验证](../references/Project.md)。

依次读取：

1. 当前任务、用户最新纠偏、操作范围和期望输出。
2. 已指定的实际仓库根目录及其中生效的 `AGENTS.md`、相关 Skill、task note。
3. 最新可获得的完整 Handoff 入口、决定、版本、风险及本轮相关专题；已有归档时同时查看归档索引和本轮相关条目的全文。
4. 本轮有效原始需求、已有 PRD、其他窗口回执和已知共享契约。
5. 实际源码、依赖元数据、测试源码及相关运行记录。

优先采用用户指定或当前对话已确认的仓库。历史路径仅是定位线索，不能据此假装访问成功。

输入缺失时列出“缺少什么、影响哪个判断、目前仍能完成什么”。没有旧交接时，直接从现有源码建立本轮基线；没有仓库时，只做文档上下文核对并生成定向补充请求。

已有 Local Chat 来源登记时，按 [对话注入规范](../references/LocalChatIntake.md) 核对未收、未读、未融合的缺口。文件存在或窗口名称可见不代表内容已经读取；S0 只恢复当前来源边界，不代替最终 S8 的批量注入。

## 3. 执行步骤

### 3.1 固定本轮身份和核查范围

- 记录任务名称、日期、实际仓库根、负责人和相关窗口。
- 写明本轮是专题核查还是为 S8 提供全项目盘点输入。
- 列出允许读取、允许执行查询或验证的范围，以及明确排除项。
- 从最新用户纠偏记录确定当前有效语义；未取消的长期需求继续保留。

### 3.2 记录工作树与既有变化

读取分支、HEAD、暂存、未暂存和未跟踪文件。可使用以下只读命令，并在实际仓库中执行：

```bash
git status --short --branch
git rev-parse HEAD
git diff --name-status
git diff --cached --name-status
```

相关 diff 用于确认现有改动及冲突边界。不要输出凭据、私有素材或不相关用户内容。

多个窗口共用目录时，diff 只能证明改动存在，不能证明是谁完成。多个 worktree 时，分别记录路径、分支、HEAD、改动和最终集成目标。

遇到核查过程中发生的新变化，重新读取相关文件并记录观察时点。保护已有未提交工作，不能通过 reset、clean 或覆盖文件获得“干净基线”。

### 3.3 核对实际环境与实例

- 从项目配置、lock、包元数据和已安装环境分别取得版本，避免混用。
- 本轮涉及运行行为时，核对用户指向的 URL、端口、进程身份或加载时间、Node Schema、路由和前端构件。
- 同一工作树可能对应多个不同状态的实例；源码与旧 Python 进程返回不一致时，分别记录。
- 没有可用宿主时，标明运行未知；静态阅读结果仍可用于后续设计。
- 对历史版本、测试数量、旧失败保留原日期和来源，不当作本轮查询结果。

### 3.4 从入口追踪相关能力

有可用 CodeGraph 索引时先查精确项目路径与符号，再读实际文件；索引缺失或过期时用 `rg` 并注明范围。

按用户动作定位 UI、Node、HTTP、MCP 或 CLI 入口，追到服务、存储、宿主或外部进程。明确生产者、消费者、状态所有者和持久化位置。

对每项相关能力记录实现状态、关键 Guard、实际错误/skip 行为和现有测试定位。必要时交给 [Phase 3](Phase3.md) 深入披露，不能用猜测填满表格。

区分本项目代码、官方源树、参考镜像、生成物和历史材料。官方复用检查遵循实际仓库 Skill，并采用 [项目背景与验证](../references/Project.md) 中的定位方法。

### 3.5 对照旧基线，保留直达依据

将旧基线、用户最新纠偏、源码观察和运行证据并列核对。为差异保留原条目 ID、来源、旧说法、新观察、影响和下一步。

原始需求与用户决定直接连接到当前功能及待验证项，避免只继承上一位 Agent 的抽象结论。没有变化的有效要求仍属于本轮基线。

按 [归档规范](../references/Archiving.md) 保留归档条目的稳定 ID、完整内容与来源；归档不使有效规则失效。先查索引，再按本轮相关性读取全文，不默认重复翻阅全部归档。S0 核查本身不累计 S8 的无变化轮次。

不能因为当前代码不同，就自动宣布用户需求失效；也不能因为 PRD 要求某行为，就宣布代码已经实现。

### 3.6 控制查询与验证的副作用

先读准备执行的脚本和命令。会构建前端、写 `js/`、更新数据库、改变宿主状态或调用真实外部软件的命令，不属于天然只读查询。

仅执行本次已授权且已确认适合核查环境的验证。必要时使用现有隔离环境；其余记录 `NOT_RUN` 及具体条件，不为了完成基线检查擅自改变环境。

结束时再次核对工作树，说明本轮报告文件及任何意外变化。

<a id="p0-delivery"></a>

## 4. 必须交付

交付一份可独立理解的本轮基线回执，至少包含：

| 章节 | 必填内容 |
|---|---|
| 核查身份 | 仓库、工作树、HEAD、观察日期、实际读取范围 |
| 有效要求 | 用户最新决定、保留的既有要求、范围与排除项 |
| 能力现状 | 相关功能、入口、文件/符号、共享消费者和实现状态 |
| 运行状态 | 目标实例、版本来源、实际回执或未知条件 |
| Guard 与测试 | 已发现的生效校验、错误/skip、精确断言与验证边界 |
| 基线差异 | 历史说法、当前证据、纠偏关系、影响及下一步 |
| 缺口 | 未读取、未运行、无法核实、Local Chat 来源缺失或未融合及其影响 |
| 接手入口 | 下一阶段、需要携带的正文或实际附件名称 |

基线中每条重大事实给出路径/符号或实际回执来源。仅做文档阅读时，用“材料记载”说明来源。

向 Web Chat 转交时携带正文或可实际读取的附件；本机绝对路径只供 Local 定位。单独发一个 Windows 路径不能传递文件内容。

<a id="p0-exit"></a>

## 5. 退出条件与分支

- 需求、源码、实例和测试结论已分开，未知项有明确边界。
- 本轮已知用户纠偏已纳入有效基线，未取消要求没有消失。
- 现有改动和共享消费者已可辨认，相关材料有可追溯入口。
- 没有把历史记录、模板或未执行命令写成本轮实测。

通过后按任务进入 [Phase 1](Phase1.md)、[Phase 3](Phase3.md) 或 [Phase 5](Phase5.md)。用户只请求核查时，到基线回执结束；用户已授权连续工作时，继续下一项具备输入的工作。

缺口只阻塞依赖该事实的动作。已经明确且可执行的部分继续完成，不重复询问已确认的产品决定。

## 6. 可复制 Prompt

填入本次已知值。用户仅要 Prompt 时返回代码块；要求执行 S0 且具有本地访问时，直接执行本段。

```text
使用 AstroPhoto SOP 的 S0，在 [实际仓库] 核对 [任务/专题] 的当前基线。输入为 [完整交接入口、相关PRD、最新用户纠偏]，本次操作范围为 [范围]。
先读 AGENTS.md、适用 Skill 和相关记录，检查归档索引、相关全文与对话来源缺口；核对工作树、HEAD、既有修改及与任务相关的实际实例和版本。从正式入口查功能、共享消费者、Guard/error/skip 和测试断言。将有效需求、源码事实、运行回执、历史验证与本轮执行分别记录，原始要求和用户纠偏直接关联当前条目。只读业务代码、环境与用户数据；验证先检查授权和副作用。
交付完整的本轮核查回执：范围、真实路径/符号、有效决定、现状、差异、证据、缺口及下一阶段输入。未知如实标注，不把文档注入当作源码审计完成。保护原基线与未提交工作；若下一步是 S4/S8，仍按其全量范围交付。
```
