# Phase1 · S1：专题边界与多 Chat 分工

[返回 SKILL.md](../SKILL.md) · [核心原则](../references/Principles.md) · [记录字段](../references/Records.md)

阶段编号固定为 S1。由 Web Chat 负责专题设计边界，Local Main 负责可访问的本地事实与集成安排。单个 Agent 可以兼任角色；职责仍需明确。

目录：[职责](#scope) · [输入](#inputs) · [执行](#steps) · [交付](#outputs) · [退出与分支](#exit) · [Prompt](#prompt)

<a id="scope"></a>

## 1. 职责与范围

建立一份能独立转交的专题约定，使每个 Chat 知道要解决什么用户问题、保留什么行为、依赖谁以及将成果交给谁。

- 将本专题置于全项目背景中，保留有效的既有需求和用户决定。
- 将用户本次明确目标转为可观察的结果，不提前代替 S2 做完整交互设计。
- 明确共享接口的生产者和消费者，不将“本 Chat 负责设计”解释为对所有相关代码拥有写入权。
- 将原始目标、用户纠偏与相应条目直接链接，避免依赖中间摘要才能理解范围。
- 用户已明确决定的行为直接采用；只有真正缺失、会改变产品结果的选择才询问。

S1 产出专题约定和分工。用户只要求上下文注入时，按要求阅读并说明已有基线及缺口，不因此宣布本地 S0 已完成。

<a id="inputs"></a>

## 2. 必需输入与读取顺序

依次读取：

1. 本次任务、用户最新原话及允许的操作范围。
2. 当前完整项目交接入口、有效决定、架构与共享契约。
3. 本专题的已有 PRD、尚未取消的长期需求、功能/Guard/测试条目及未完成项。
4. S0 的源码和实例基线；若尚无本地核验，标明所依据的历史日期和待核实内容。
5. 已登记的其他专题、Local Main、窗口、工作树与集成目标。

Web Chat 只将已提供的正文或可读取材料列为输入。Windows 本机路径可供 Local 使用，不能证明 Web Chat 已读取该路径。

缺少非关键资料时，先完成可判断的分工，并列出缺口。缺少共享契约实际定义时，为 S3 登记定向问题，不凭名称猜字段或类型。

<a id="steps"></a>

## 3. 执行步骤

### 3.1 形成专题约定

填写以下字段；旧约定已有字段时更新原记录，保留来源和稳定编号。

| 字段 | 需要写清的内容 |
|---|---|
| 专题身份 | 项目、专题名称、Chat 标识、当前包或基线版本 |
| 用户问题 | 谁在什么条件下遇到什么问题，本轮期望什么结果 |
| 有效依据 | 原始需求、最近纠偏、仍有效的旧决定及其来源 |
| 本期范围 | 本轮处理的行为及可观察 AC；已有 FR/AC 沿用原编号 |
| 排除与延后 | 明确不在本期实施的内容；延后不等于取消 |
| 主责路径 | 本专题预期涉及的路径；尚未查证的标为待 S3 核实 |
| 只读依赖 | 需要理解、但本轮未安排修改的模块与原因 |
| 共享契约 | Node 端口、API/DTO、配置、持久数据、注册/构建入口等 |
| 消费者与所有者 | 谁生产、谁读取、谁决定集成顺序 |
| UI 与原型 | 是否引入界面或实质交互变化；需要模拟哪些关键动作 |
| 实施与验证边界 | 允许的操作、目标实例、测试环境及尚缺的条件 |
| 汇合责任 | 一名 Local Main，以及下一阶段接收方 |

不要为整齐填入虚构路径、测试名或宿主 URL。无相关内容写明“不适用及原因”；不明内容保留待核实状态。

### 3.2 登记并行分工

多 Chat 任务至少登记一行一个专题的表：

| 专题 / Chat | 目标与 AC | 主责路径 | 只读依赖 / 排除项 | 共享契约与消费者 | Local Main / 集成目标 |
|---|---|---|---|---|---|
| 填入实际专题 | 填入可观察结果 | 填入已核实或明确待核实的范围 | 填入实际边界 | 填入已有契约及待查项 | 填入实际负责人 |

有多个本地窗口时，再记录窗口链接或可识别名称、仓库、worktree、分支/HEAD 和成果流向。窗口尚未建立时写计划分工；不可读取窗口时保留资料缺口。

同步建立未来 S8 必须回收的 Local Chat 来源名单，按 [对话注入规范](../references/LocalChatIntake.md) 记录稳定 Chat 标识、可访问引用或导出位置、负责人、专题范围和已知消息/时间范围。新增、转移或结束窗口时更新这份名单；窗口关闭不等于其讨论无需交接。资料尚未收到或未读时如实登记，不能把计划来源记成已完成注入。

共享工作树由一个 Main 统筹写入。不同 worktree 的结果须有明确集成目标；单个窗口测试通过不证明组合结果已集成。

### 3.3 标出共享契约变化

仅在行为确实影响其他消费者时记录契约变更，不把单个控件的局部调整扩大为全项目审批。

一条契约变更至少包含：

- 原字段、类型或行为及其来源。
- 拟变字段、类型或行为；尚未确定处保持提议状态。
- 生产者、所有消费者和共享文件所有者。
- 对旧工作流、旧数据、权限和生命周期的影响。
- 可行兼容方式、顺序依赖和需要验证的组合。
- 用户已有决定，或尚待决定的具体产品取舍。

Local Main 可以在已授权范围内决定实现细节。新的用户可见取舍或未获授权的数据处置，先形成具体可审阅方案，再处理必要的决定；不要要求用户重复批准既有决定。

### 3.4 建立跳跃链接与纠偏入口

在专题约定中建立可直接到达的链接：

- 用户原始问题与最新纠偏 → 对应 FR/AC。
- FR/AC → 相关共享契约与消费者。
- 本专题已有功能 → Guard、测试、未验证项。
- 排除/延后项 → 原始依据与后续接手位置。

按 [核心原则](../references/Principles.md) 保留完整基线。发生范围变更时，明确旧条目是保留、修订、取代还是延后；未提及不能解释为删除。

用户对方向的纠正可以发生在本阶段任意时点。及时更新受影响条目，并将该决定作为后续阶段的有效输入。

<a id="outputs"></a>

## 4. 必须交付

交付一份可独立理解的专题约定，包含：

1. 用户问题、当前目标、完整有效范围及明确排除项。
2. 本专题相关的有效决定、持续纠偏记录和未取消需求。
3. Chat/Local 分工、共享契约、消费者、集成责任及供 S7/S8 回收的 Local Chat 来源名单。
4. 已知事实、历史材料和待查事项的区分。
5. S2 的输入，或直接进入 S3/S4 所需的定向问题。

专题规模小可用一个 Markdown 节承载。文件组织遵循 [完整包规则](../references/Packages.md)；不能因为分组或长度方便而省略有效条目。

<a id="exit"></a>

## 5. 退出条件与后续分支

通过前核对：

- 下一位 Agent 能说明本专题做什么、不做什么、影响谁、交给谁。
- 所有已知用户纠偏都已映射到范围或决定记录。
- 共享接口的未知项已明确，不存在假定其他 Chat 已同意的改动。
- 可以直接追溯原始依据，不必重新翻阅完整聊天才能理解关键约束。

需要产品设计时进入 [S2](Phase2.md)。需求已充分明确而缺源码事实时进入 [S3](Phase3.md)。已有有效 PRD 和充分披露时可进入 [S4](Phase4.md)，并遵守专题全量交付。

用户只要求推荐路线或 Prompt 时，到本次要求的产物为止。用户已明确要求执行时，继续推进不依赖缺失材料的已授权工作。

<a id="prompt"></a>

## 6. 可直接复制的 Prompt

发出前用当前对话中的实际内容填入变量。操作说明放代码块外；接收者不依赖本 Chat 的隐式记忆。

```text
你负责 ComfyUI_AstroPhoto 的 [专题 / Chat]，执行 SOP S1。当前目标是 [用户问题及结果]；输入为 [实际附件或可读路径]；最新用户决定为 [相关原话]。
读取完整基线中的相关决定、需求、架构、契约与未完成项，区分源码事实、历史验证和未知。形成专题约定：有效范围与 AC、排除/延后项、主责路径、只读依赖、共享契约及生产者/消费者、原型需求、Local Main 和集成目标。登记供 S7/S8 回收的 Local Chat 来源、负责人和范围。路径未核实时明确标注。
已有用户决定直接采用；仅提出会阻塞产品判断的具体问题。保留原始需求与纠偏到 AC/契约的跳跃链接，说明旧条目的保留、修订或取代去向。输出完整专题约定及下一阶段所需资料；不要把分工或计划写成已实现、已验证。
```
