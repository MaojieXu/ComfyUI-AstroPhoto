## 1. 职责与输入

由 Web Chat 根据已明确需求提出定向问题，由 Local 沿当前工作树查证。目的是让 S4 能将本专题全部有效 AC 映射到真实调用点、复用选择、Guard 和验收条件。

Local 对业务源码、依赖、宿主和用户数据只读。本阶段返回事实与技术选择依据，不实施功能、不擅自决定新的产品行为。

必需输入：

- 本专题完整有效 PRD/AC、相关原型及最新用户纠偏。
- 实际仓库根、相关运行实例（未知时明确写未知）。
- 最新基线和需要核实的问题、入口、目录、消费者。
- 本轮查询与验证范围，以及明确保护的现有改动。

先读 [核心原则](../references/Principles.md)、[记录字段](../references/Records.md) 和 [项目背景与验证](../references/Project.md)。需要独立研究时使用 [只读子任务](../references/Subagents.md)。

用户已经给出足够源码时，核对材料版本、覆盖范围和缺口，复用有效披露；仅补足影响判断的部分。进入 S4 时，已获得且仍有效的披露必须完整纳入本轮专题包。

<a id="p3-questions"></a>

## 2. 准备披露问题

Web Chat 先从每条 AC 倒推：

1. 用户动作从哪个正式入口触发？
2. 状态由谁持有，怎样传到 API、Node、MCP、存储或外部进程？
3. 当前有哪些可复用的项目能力和目标版本官方能力？
4. 失败、skip、取消、权限拒绝及恢复在哪里生效？
5. 哪条现有断言能证明预期，哪些边界仍然缺证据？
6. 哪些生产者、消费者、旧数据或旧工作流可能受影响？

将上述问题收敛成短 Prompt。通常约 300–500 个中文字可承载任务，复杂范围可以适度增加；不为字数限制省略会改变结论的输入和边界。

只给 Local 当前专题实际需要的正文、附件或可访问路径。子任务不能依赖主 Agent 未传递的聊天记忆。

<a id="p3-steps"></a>

## 3. 执行步骤

### 3.1 固定披露基线

- 核对 `AGENTS.md`、适用 Skill、分支、HEAD 与相关未提交变化。
- 列出实际读取目录、文件、测试和引用资料。
- 核对实际目标实例；未查询运行实例时保留未知状态。
- 有 CodeGraph 时使用精确项目路径并复核文件；否则使用 `rg`。
- 区分项目源码、官方源码、参考镜像、生成物和历史资料。

### 3.2 对每条 AC 追踪正式调用链

从 UI 操作、HTTP handler、Node execute、MCP tool 或 CLI 入口出发，追到最终可观察结果。

每个关键节点给出：

| 字段 | 要求 |
|---|---|
| 定位 | 仓库相对路径、真实符号、必要行号及其工作树版本 |
| 签名与调用方 | 函数/类/事件、实际调用者、注册或挂载位置 |
| 输入输出 | 类型、值语义、缺省值、回执、路径或资产 ID 的区别 |
| 状态所有者 | 状态来自何处、谁更新、何时持久化或刷新 |
| 副作用 | 文件、数据库、缓存、图/队列、外部进程和网络影响 |
| 消费者 | 共享接口、下游 Node、旧工作流及其他专题 |

披露关键分支的必要源码；必须理解完整函数才能判断时，提供该函数完整实现并注明原因。避免无关整文件 dump，也不能用泛泛摘要跳过决定性分支。

### 3.3 核对复用候选

先查项目已接入的能力，再核对对应版本官方实现和公开接口。前端、后端的检索入口按实际仓库 Skill 与 [项目背景与验证](../references/Project.md) 执行。

每个候选注明上游路径/符号、版本、公开性、项目现有调用点、必要依赖、许可、兼容边界和待测行为。

区分以下结果：直接复用、最小修改、移植适配、部分匹配、本地补足、未找到匹配、检索未能完成。发现技术方案可以说明理由，但新的用户可见取舍交给相应阶段处理。

### 3.4 追踪实际生效的 Guard

逐项检查与行为相关的参数/类型、路径、格式、权限、状态、并发、生命周期和外部进程边界。

每个 Guard 记录：触发条件 → 检查位置 → 谁调用 → 拒绝或 skip → 错误码/用户反馈 → 清理、回滚、恢复 → 对应测试。

明确校验在客户端、服务端、宿主还是外部软件中生效。一个孤立校验函数不能证明生产调用链受保护。

记录正常失败与异常失败、部分成功和重复调用的可观察结果；无需该类 Guard 的行为可写 `N/A` 并说明理由。

没有发现时写检索范围与 `NO_GUARD_FOUND`，不能据局部搜索断言全仓不存在。

### 3.5 读真实测试断言

定位精确测试文件、测试函数或用例名、fixture、模拟边界和断言。

检查测试的前置状态是否与 AC 一致。例如需求是“原来禁用，成功保存后启用”，从已启用 fixture 开始的版本拒绝测试不能证明这次状态转换。

分别记录：

- 测试源码存在，尚未运行。
- 历史执行结果及原环境、日期、版本。
- 本轮实际执行的命令、环境、退出码、结果和关键断言。
- 真实 CLI、宿主注册 GET、队列提交、完成与产物分别覆盖的边界。

没有找到测试时说明检索范围并写 `NO_TEST_FOUND`。不按测试文件名或 Agent 的口头报告宣布通过。

运行验证前先检查本轮授权与副作用。会重写前端构件、数据库或宿主的命令不能当作只读查询；不适合执行时写 `NOT_RUN` 和所需条件。

### 3.6 对照 PRD 与用户纠偏

为每条 AC 给出当前行为、差距、可复用/修改/新增位置及影响消费者。现有符号和拟建符号分列，拟建项明确标记。

原始要求、用户纠偏、代码与测试之间建立直接关联；本轮重新发现旧条目仍有效时，保留原编号与来源。

如果源码与 PRD 不同，分别写现状和目标。仅将实际阻止设计的问题交回 Web Chat，不因一项冲突重开全部已确认需求。

<a id="p3-delivery"></a>

## 4. 必须交付

回复仅使用一个最外层 Markdown 代码块，内容是一份可独立转交的完整披露文档。需要内嵌源码时使用不同长度围栏，避免破坏外层代码块；输出过长时可同时给出完整文件。

文档应包含：

1. 任务、AC、最新相关决定、仓库与工作树标识。
2. 实际检索范围、相关文件树及未读取范围。
3. 逐 AC 的正式入口、文件/符号、调用链、输入输出与副作用。
4. 官方与项目复用矩阵、版本和适用边界。
5. Guard/error/skip、取消、清理、恢复及共享消费者。
6. 精确测试定位、断言、替身边界和执行证据。
7. 现状与目标差异、拟修改位置、待裁决问题和未知。
8. S4 必须携带的条目、来源及附件。

必要片段应脱敏。不能将真实 Token、私人素材路径或不相关用户输入转交其他 Chat。

<a id="p3-exit"></a>

## 5. 退出条件与分支

- S4 能逐 AC 判断复用、修改或新增，而无需猜目录与函数。
- 主调用链、共享消费者、失败与恢复、关键测试断言都有定位或明确缺口。
- 静态事实、历史验证、本轮执行与未知已分开。
- 没有冒充当前实现的示例路径、拟新增符号或未运行结果。

达到条件后进入 [Phase 4](Phase4.md)，生成包含既有有效内容和本次披露的专题全量包。

关键事实不足时继续定向查证；缺少访问条件时交付已有事实与精确缺口，不能宣布披露完整或以虚构信息补齐。新的产品冲突仅返回 [Phase 2](Phase2.md) 的相关条款。

## 6. 可复制 Prompt

```text
使用 AstroPhoto SOP 的 S3，在 [实际仓库] 对 [专题完整PRD/AC与最新纠偏] 做只读源码披露。目标实例 [地址或未知]，重点问题 [清单]，允许查询/验证 [范围]。
先核对工作树与适用 Skill，再从正式入口追到最终结果。逐 AC 给出真实 path::symbol、签名、调用链、输入输出、状态所有者、副作用、共享消费者、官方及项目复用候选；披露影响判断的必要源码。追踪实际生效的 Guard、error/skip、权限、取消、清理与恢复，并定位精确测试及其前置条件、断言、Mock/真实边界。
分别记录静态事实、历史验证、本轮命令结果和未知。说明搜索范围，标明 NO_GUARD_FOUND、NO_TEST_FOUND 或 NOT_RUN；现有与拟建符号分开。只读业务代码、环境及用户数据。将全部结果放入一个最外层 Markdown 代码块，携带相关原始要求和用户纠偏，供 S4 合成专题全量包。
```
