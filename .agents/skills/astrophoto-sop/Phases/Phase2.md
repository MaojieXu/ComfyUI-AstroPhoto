# Phase2 · S2：产品需求与可操作原型

[返回 SKILL.md](../SKILL.md) · [核心原则](../references/Principles.md) · [记录字段](../references/Records.md) · [官方参考](../references/Sources.md)

阶段编号固定为 S2。Web Chat 负责研究、产品表达和原型；用户持续纠正方向；Local 为本地事实提供证据。

目录：[职责](#scope) · [输入](#inputs) · [执行](#steps) · [交付](#outputs) · [退出与分支](#exit) · [Prompt](#prompt)

<a id="scope"></a>

## 1. 职责与范围

把本专题全部有效目标变成可理解、可操作、可验收的产品需求。明确正常流程、失败与恢复、数据副作用、共享边界以及当前仍未决定的事项。

用户已经给出具体要求时直接采用。仅在存在实质取舍时比较少量方案，说明体验、复用、代价和风险，再由用户已有或新的明确决定确定目标。

PRD 描述用户需要的行为。当前函数、接口是否存在由 S3 的真实披露证明；产品设计中的名称不能冒充已实现符号。

<a id="inputs"></a>

## 2. 必需输入

- S1 专题约定，或本次对话中同等明确的目标、范围、依赖和负责人。
- 当前完整基线中的相关需求、历史有效决定、未交付项和共享契约。
- 用户本次及此前仍有效的纠偏，包括不得恢复的旧规则和限制。
- 已有 PRD、原型与 Local 回执；原型和实际运行状态分别记录。
- 本轮相关的目标宿主版本、已有官方复用线索和尚缺的源码问题。

材料不足时标明其对判断的影响。可以继续完成已知部分；对未知本地行为安排 S3 定向核查。

<a id="steps"></a>

## 3. 执行步骤

### 3.1 保留完整需求集合

先列出本专题原始需求、仍有效的旧条款、本轮新增要求、延后项及被明确取代的规则。沿用既有编号；无编号时按 [记录规范](../references/Records.md) 建立。

对每条旧条目登记其当前去向，避免在重写 PRD 时只留下最近讨论过的功能。用户改变一处行为时，保留其他未被取消的约束。

用户的 bias 持续进入产品定义：记录来源、适用范围、旧行为、新要求和影响条目。不要把建议自动写成用户已接受的决定。

### 3.2 进行必要的官方研究

围绕具体疑问检索官方文档、官方仓库和相关标准原文。优先核对与目标版本一致的内容；记录 URL、访问日期、版本/Tag/提交与适用限制。

区分公开 API、上游内部实现、项目适配和方案推断。滚动网页提供线索，Local 的目标版本源码与运行证据用于确认是否可用。

将研究转为具体产品判断，例如某机制能保留宿主键盘行为、某接口影响旧工作流。不要仅罗列链接，也不要凭一个网页标题宣布官方支持。

复用顺序与环境核验见 [项目约束](../references/Project.md)；引用入口见 [官方参考](../references/Sources.md)。遇到查找失败，明确搜索范围和缺口。

### 3.3 编写完整 PRD

按实际需要分节，至少覆盖下表中的适用内容。

| 部分 | 必须表达的内容 |
|---|---|
| 用户与问题 | 目标用户、触发场景、现有痛点及成功后的变化 |
| 范围 | 本期目标、非目标、与其他专题的边界及长期延后需求 |
| 主流程 | 前置条件、用户动作、系统响应、最终可观察结果 |
| 输入与输出 | 数据语义、来源、必需与可选字段、输出归属 |
| 状态 | 初始、空、加载、成功、失败、禁用、过期、冲突等适用状态 |
| 错误与恢复 | 触发条件、提示、保留状态、重试/取消/回退、可否继续 |
| 数据副作用 | 读写位置、原件保护、配置持久化、缓存与资产边界 |
| 权限 | 谁可以执行、授权何时生效、拒绝后可观察结果 |
| 兼容 | 既有工作流、共享接口、消费者与旧数据处理的实际影响 |
| 交互 | 布局、控件行为、键盘、焦点、主题、窄栏与生命周期 |
| 验收 | 每条 AC 的条件、动作、期望结果与应保留的行为 |
| 决定与未知 | 已明确、提议、延后、否决、被取代条目及其来源 |

对不适用项目写明理由。不要为完整表格虚构权限系统、持久库、通用框架或未来模块。

### 3.4 写可验收条件

一条 AC 应能被实现者复现，并能区分成功与失败。

采用“给定条件 → 执行动作 → 可观察结果”的结构，必要时增加失败分支和不得发生的副作用。

示意：在隔离测试配置中给定某开关初始为关闭，保存有效配置，重新读取后应看到开关打开；无效配置保存失败时旧有效配置仍保留。该示意仅说明 AC 的写法，不能作为本项目已实现或已测试的声明。

避免“体验好”“正常运行”“覆盖全部场景”等无法直接核对的结论。测试方法可先描述拟验收行为；真实测试函数和既有断言待 S3 确认。

### 3.5 提供适用的可操作 UI 原型

设计新 UI 或实质交互变化时，交付 `prototype/index.html`，可自包含 CSS/JS，离线打开后能操作关键流程。已有控件的简单明确纠偏，可引用用户标注及原有交互；说明本次无需重新原型的具体原因。

原型至少检查：

- 主要按钮、选择、输入、保存、取消、重试等实际行为。
- 相关空态、加载、失败、成功、禁用或冲突状态。
- 目标 Sidebar 窄栏、必要的宽度变化、滚动和内容溢出。
- 键盘访问、焦点移动和可观察的控件状态。
- 当前宿主的明暗主题、布局与既有组件风格。
- 操作前后状态，以及失败时保留或恢复的内容。

标明模拟数据、模拟响应与真实宿主差异。截图或展示图可以辅助说明，但无法替代可操作原型。不要让原型暗中调用真实接口或修改真实用户数据。

### 3.6 连接 PRD 与下一步源码披露

给每条相关 AC 登记需要 Local 回答的具体问题：入口在哪里、由谁持有状态、已有契约是什么、哪个 Guard 生效、当前断言覆盖哪些条件、哪些消费者受影响。

保留直接链接：用户决定 → FR/AC → 原型状态 → 待查源码问题。已得到可靠答案的项沿用来源，避免重复全仓调查。

输出一段短的 S3 请求，通常控制在约 300–500 个中文字，以能独立执行为准。复杂信息由随附 PRD 承载；需要影响判断的函数分支时明确指出。

<a id="outputs"></a>

## 4. 必须交付

1. 覆盖本专题全部有效需求的 PRD，带明确状态和来源。
2. 可观察 AC，与已有决定、共享边界和延后项相连。
3. 适用的离线可操作 HTML 原型，以及模拟边界说明。
4. 官方研究结论和版本适用性；本地事实缺口单列。
5. 一段可直接交给 Local 的定向 S3 Prompt。

有 Frontend、Backend、MCP 或 Node 多端需求时按阅读职责拆分；相关条款通过稳定编号互相链接。拆分不得造成有效信息丢失。

<a id="exit"></a>

## 5. 退出条件与后续分支

- 用户已明确的行为已写入有效条款；尚有产品取舍的部分保持待决定状态。
- 正常与失败流程、数据副作用和相应 AC 已有可核对描述。
- 适用原型能实际打开和操作，且与 PRD 行为一致。
- S3 的问题足够具体，能够调查真实入口、Guard、测试断言和消费者。

已有明确用户指令无需再次机械确认。缺本地事实进入 [S3](Phase3.md)；证据已充分时进入 [S4](Phase4.md)。需要等待某项决定时，继续完成不依赖它的部分并说明实际缺口。

进入 S4 时使用完整 PRD 和全部相关材料，不只转交本轮差异。

## 6. 可直接复制的 Prompt

```text
你负责 ComfyUI_AstroPhoto 的 [专题]，执行 SOP S2。输入为 [完整基线、专题约定、已有 PRD/原型及实际附件]；目标是 [结果]；最新用户决定为 [相关原话]。
保留本专题全部有效需求、约束、延后项和决定来源，持续吸收我的纠偏。核对相关目标版本官方资料，必要时比较少量有实质取舍的方案；已有决定直接采用。输出完整 PRD：主流程、输入输出、正常/失败状态、数据副作用、权限、兼容、共享消费者、可观察 AC 与未决事项。
涉及新 UI 或实质交互时，制作离线可操作 prototype/index.html，覆盖关键动作、相应错误态、窄栏、键盘及主题，标明模拟边界。建立用户决定到 AC、原型状态及源码问题的直接链接。最后提供一段短的 Local S3 披露 Prompt，只查相关真实入口、函数、Guard、断言与消费者；不要把方案写成已实现事实。
```
