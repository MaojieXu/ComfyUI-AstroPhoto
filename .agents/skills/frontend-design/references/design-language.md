设计前先读项目根目录 `DESIGN_SYSTEM.md`，以目标宿主的实际界面和当前项目决定为基线。下列资料用于定位设计依据，不代表上游内部组件可以被扩展直接导入。

## 将参考转化为项目决策

- **画布和节点**：先看同类原生节点的标题、输入输出、Widget 顺序和折叠行为。让用户先识别对象、输入输出和下一步；缩放或窄节点下保留关键识别信息，不以铺满节点或装饰为目标。
- **侧栏**：依据任务顺序组织标题、导航、搜索或主要操作；对照同宿主侧栏的空间密度和控件层级。窄宽、滚动、长名称不能遮挡主要操作。
- **菜单与弹窗**：明确触发位置、主操作、取消和关闭；危险后果与错误用用户可理解的文字说明。检查键盘进入、关闭和焦点返回，避免单凭颜色表达状态。
- **视觉细节**：优先项目中已验证的语义主题值、控件和图标；对照目标宿主当前主题、hover、选中、禁用和焦点状态。尺寸与色值从实际版本和批准方案取得，不从一般 Web 规范臆造。
- **状态和文案**：只设计业务可到达的正常、加载、空、错误、禁用等状态；说明触发条件和用户可采取的下一步。检查中英文、长文件名或路径，避免把内部标识当成主要信息。

## 可借鉴的扩展案例

- [ComfyUI-Custom-Scripts](https://github.com/pythongosssss/ComfyUI-Custom-Scripts)：其补全列表把建议和信息入口放在使用位置，适合研究画布内辅助操作；具体交互、实现和许可仍须按目标场景核对。
- [rgthree-comfy](https://github.com/rgthree/rgthree-comfy)：其节点与群组操作展示围绕图结构集中执行操作的思路；先核实自身工作流是否存在同类需求，不把其节点样式视为官方规范。

案例是设计启发，不是宿主 API 或项目已批准设计。引用时记录版本、访问日期及与当前需求的关系。
