# Feature Pipeline

以持续演进的共享文档和实际代码恢复上下文，按用户当前意图推进，无须依次经过固定阶段。遵循项目 AGENTS.md、Docs 和相关 Skills；用户仅要求讨论、分析或测试时不修改业务代码。

## 初始化与接手

- 在项目约定的 Feature 目录中创建或接手；没有约定时使用 `.agents/features/`，新目录命名为 `YYYY-MM-DD-NN-feature-name`。同一 Feature 可以包含多个独立需求。目标不明确且无法从上下文判断时询问用户。
- 初始化时根据 [PRD](templates/PRD.md)、[DEV](templates/DEV.md)、[TEST](templates/TEST.md) 模板创建文档；正式代码审查时才按 [REVIEW](templates/REVIEW.md) 模板创建审查记录。模板注释仅为填写指引，省略无意义的空字段。
- 工作前读取相关的当前需求、开发状态、代码、测试和项目规范；按需读取测试及审查记录。默认不读取 archive 中的历史 Feature。接手恢复的归档时，根据原文档和实际代码整理当前有效上下文，保留重要历史证据。

## Chat 与需求

- 使用用户指定的标签，如 `@chat1`；持续使用直到用户明确修改。切换身份后重读共享文档，不自动继承旧 Chat 的任务归属。不维护注册表、系统会话 ID 或身份文件；未指定标签时不编造身份。
- 在需求变更、任务归属、重要决策、实现结果、测试和审查记录中标记相关 Chat；同一批相关记录可以共用标签。标签不决定需求优先级。
- 多 Chat 写入前重读相关文件，以最新内容增量修改，保留他人工作；无法安全合并时协调冲突部分，继续处理独立工作。
- 按独立需求分配稳定的 `R1`、`R2` 等编号；新增需求增加条目，调整修订原条目。区分已确认需求、探索方案和待确认事项。最新明确的用户决策替代冲突的旧决策，保留重要否决原因；切换任务不代表撤销，修复 Bug 不擅自改变需求。仍有重大产品取舍或冲突无法判断时，提出具体问题。

## 开发与文档

每轮恢复相关上下文，理解用户意图，必要时更新需求和实施方案；在授权范围内完成可观察、可验证的最小有效增量，执行与风险相匹配的局部验证，再按实质变化更新文档并根据反馈迭代。

- `PRD.md`：当前有效需求、产品决策、约束和待确认事项的事实源。
- `DEV.md`：实施方案、任务进度、关键代码位置、技术决策及重要反馈的事实源。状态仅用：待开发、开发中、已实现、暂缓、阻塞、已撤销；验证状态由 TEST 管理。
- `TEST.md`：验证场景、入口、实际结果和未覆盖事项的事实源。状态仅用：通过、失败、未执行、待复测、待用户确认、阻塞。
- `REVIEW.md`：正式审查发现、修复与复审结果的事实源。

只更新本轮发生实质变化的内容。保留影响后续开发的用户决定、否决原因、技术发现和未完成事项；不记录完整对话、工具输出、文件哈希、重复状态或可直接从 Git 获取的信息。

## 测试与审查

- 根据当前需求、实际代码和已有测试维护 TEST；区分已实现、已验证和用户已确认。需求或代码变化后，判断相关结论是否仍有效，并将需要重测的场景标记为待复测。如实记录失败、缺口和环境限制。
- 用户要求全量测试时，补充必要测试代码，执行 Feature 测试和相关回归，并记录实际结果及未覆盖事项。用户只要求测试时不改变业务代码。
- 用户要求正式代码审查时，优先由独立 Chat 承担；依据 PRD、DEV、TEST、项目规范及实际代码审查，在 REVIEW 中记录范围、问题、位置、影响和处理状态，修复及复审后更新对应发现。用户明确要求只读审查时不写文件。审查不能代替实际测试。

## 经验与归档

回顾需求、实现、决策、反馈及验证，提出具有长期复用价值的经验和目标位置：架构与技术知识放入 Docs，通用约束放入 AGENTS.md，可复用流程放入 Skills。经用户确认后落实选定内容，不将一次性决策泛化为长期规则。

用户确认归档后，将整个 Feature 目录移入 `.agents/features/archive/` 并保留名称与文档；归档后需要继续开发时，可恢复到活动目录。
