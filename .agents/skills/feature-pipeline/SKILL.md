# Feature Pipeline

## 1. 工作方式

维护一个持续演进的 Feature，而不是强制用户依次通过固定阶段。以项目现有规范和真实代码为依据，按用户当前授权推进：

- 需求/讨论 → 理解与分解策略、按项目规则开展产品和前端设计审阅 → 确认适用的产品取舍和前端设计 → PRD 生效、DEV 计划 → 获准实现 → 代码及局部验证 → DEV、DEV_LOG、TEST_PLAN 增量同步。
- 正式验证 → 基于 PRD、DEV、DEV_LOG、TEST_PLAN 建立或补全实际测试文件、执行 Feature 全量及必要回归 → TEST_REPORT → 缺陷回到开发循环。
- 完成 Feature → 提取可复用工作流程、技术经验及用户纠正 → CLOSE 中提供候选 → 用户选择后才写入长期 Docs/Skills。

用户仅讨论、只读分析或只确认方案时，不擅自实现。用户明确要求“按此方案开始实现”等，已授权的部分直接完成，不重复询问；若只确认方案而将开始开发留待下一条指令，先同步已确认的需求和计划，不改业务代码。一次实现工作包含关联文档同步，不等用户再次提醒。

## 2. 找到 Feature 与恢复上下文

1. 确认仓库、目标 Feature、当前请求和权限范围。有明确活动 Feature 时复用；有多个且无法判断时问一个简短问题。不要把普通任务强行归入 Feature。
2. 识别项目已有的 Feature 根目录（例如 features/、.agents/features/）。没有约定时使用 .agents/features/；不要同时创建两套目录。已有 Feature 优先复用其命名与路径。
3. 按第 3 节确定当前 Chat 身份。只读讨论不需要身份；首次需要写入 Feature 而用户尚未指定 Chat ID 时，先请其指定。
4. 先读相关 PRD 和 DEV；按具体问题追溯关联 DEV_LOG、TEST_PLAN、源代码、现有测试、项目指令及必要的对外契约。正式验证再读取有关 RUN；关闭再回看用户反馈。不必每轮读取全部历史。
5. 初始化仅创建缺失的 PRD、DEV、DEV_LOG、TEST_PLAN，使用 assets/templates/ 中的模板填充当前 Feature、Chat 和真实日期；未知内容留为待确认，不造需求。TEST_REPORT 和 CLOSE 按实际任务创建。
6. 原有编号式文档（如 01_PRD.md、04_DEV_LOG.md、05_TEST_PLAN.md、06_TEST_REPORT.md、07_CLOSE.md）是对应逻辑文件；保留名称及历史 ID。没有开发计划才增加 DEV.md。既有 UXUI、TECH、INDEX 可继续作为相关契约或导航，不重复维护状态、不自动迁移或删除。正式代码审查按需建立 REVIEW.md。

## 3. Chat 身份与并行写入（适用于所有 Feature 文档）

- 用户明确指定的 Chat ID 是当前会话的写入身份，如 chat1；之后连续使用，不每轮询问。**用户最新明确指定的身份覆盖任何继承的旧身份。** 当用户复制/分支聊天并说“你是 chat2”，保留继承的需求知识，立即切换为 chat2，重读共享文件；不把 chat1 历史改成 chat2，也不默认接管 chat1 未完成任务。会话分支不等于 Git Branch。若已明确知道是复制/新会话但尚未指定新身份，先只读恢复；写入前请用户确认本 Chat ID，不沿用被继承的旧身份。
- 每次写入（包括新增、修改、失效、迁移或小修订）在对应记录或本次修订记录上保存实际写入者 Chat ID 和可获知的时间；包括需求修订、任务归属/状态变更、测试用例修订、正式 RUN、知识候选及确认处理。保留原创建者与历史，不冒用其他 Chat，不编造真实系统会话 ID。一次相关修订可以共用一条明确列出受影响 ID 的修订记录，不必给每一行重复标签。
- 新条目采用稳定、可跨 Chat 唯一的 ID，例如 FR-chat1-001、TASK-chat2-001、DEV-chat1-001、TC-chat2-001、RUN-chat1-001、K-chat2-001；同 Chat 同类型从磁盘选择未占用编号。旧 ID 原样保留。变更语义用修订号/历史或 Supersedes 引用，不重编号现有记录。
- 多 Chat 以共享文件为准。启动实现前和写入前重新读取相关文档及实际工作区状态，确认任务仍有效；记录当前任务预计涉及的共享文件/接口和负责人 Chat。避免两个 Chat 同时修改同一文件或共享契约；有依赖时先明确接口及顺序。对非冲突范围自主推进。
- 使用最小、基于最新内容的增量编辑，保留其他 Chat 未提交/未跟踪的工作；写后复读并核对 diff。如果真实并发冲突无法安全合并，暂停冲突部分、说明差异并协调短时串行写入，非冲突工作继续。Markdown 不等于原子锁；不得用陈旧全文覆盖新内容或假定 Chat 间有共享记忆。默认不新建分支、Worktree、角色文件、Chat 注册表或锁文件。正式审查按 review.md 记录独立审查 Chat 和角色。

## 4. 六份权威文档

| 逻辑文件 | 唯一权威信息 | 创建时机 |
| --- | --- | --- |
| PRD.md | 当前已确认的产品需求、FR/AC、重要变更及待决 | 初始化 |
| DEV.md | 实施策略、当前任务/Chat 分工、预计修改范围、依赖与状态 | 初始化 |
| DEV_LOG.md | 实际实现/修订/撤销、全部实际改动路径、局部验证与历史 | 初始化 |
| TEST_PLAN.md | 需求/实现关联的 TC、测试覆盖与缺口、测试代码映射、局部证据引用 | 初始化 |
| TEST_REPORT.md | 正式测试的代码基线、测试套件与真实 RUN/缺陷/复测结论 | 正式验证 |
| CLOSE.md | 有复用价值的经验候选及用户选择和落地结果 | Feature 完成或知识提取 |

每次正式审查或复审完成后，默认在最终回复前按 [review.md](references/review.md) 主动写回 Feature，包括没有新发现的轮次。

只维护一个事实源；其他文件引用稳定 ID，不复制整份计划或日志。DEV 记录预计与当前状态，DEV_LOG 记录事实，TEST_PLAN 记录验证设计及证据引用，TEST_REPORT 记录正式执行证据。复杂原型或独立技术契约按需拆出 UXUI.md/TECH.md，简单方案分别留在 PRD/DEV。

## 5. 需求冲突与决断

**以最新已确认、适用的有效决策为准，不以文件更新时间或 Chat 数字判优先级。**

- 发现新旧 PRD、开发方案、代码、测试预期、历史对话或并行任务不一致时，核实条款、依据、适用范围、用户确认和依赖。先检查是不是不同场景可以并存。
- 用户明确的新决定在重叠范围替代旧决定；未冲突的旧要求保留。可确定的过时文档、实现策略、内部技术取舍、测试预期错误由 Agent 自主修正并说明依据；不要为已明确的决定重复问用户。
- 若两个仍有效的产品要求互斥、范围/兼容性不明、改变对外承诺且无授权，或技术选项有重要不可推断取舍，则简要列出冲突、建议及影响，向用户询问具体决定；只阻断依赖它的部分。未确认的新方案不能覆盖已确认要求。
- PRD 只展示当前有效行为；保留旧决策摘要、原 FR/AC 版本/引用、被替代原因、新版本和写入 Chat。不因历史日志保留旧方案而继续实现它。DEV_LOG 追加重要决断/撤销/回滚事实（未编码写明无代码改动）。
- 决断后核对并增量同步受影响的 DEV、DEV_LOG、TEST_PLAN；已有正式 RUN 保留原证据，明确其失效范围及所需复测。仅在用户已授权的实现范围内改代码。既有产品契约没变的纯内部修复只读 PRD 并引用它，不凭实现倒推新需求。

## 6. 按任务加载 Reference

| 本次用户意图 | 读取 |
| --- | --- |
| 新增/修改/否决需求，讨论分解策略，确认方案 | [requirements.md](references/requirements.md) |
| 初始化/接手/计划/实现/修复、同步 DEV 与 DEV_LOG、复杂技术方案 | [development.md](references/development.md) |
| 更新 TEST_PLAN、构建最终测试、正式验证 | [testing.md](references/testing.md) |
| 用户明确要求正式 Feature 代码审查、复审或回写审查结果 | [review.md](references/review.md) |
| Feature 完成、用户反馈归纳、候选知识、归档/重开 | [knowledge.md](references/knowledge.md) |

只读所需 Reference；初始化时使用对应模板 [assets/templates/](assets/templates/)，以实际内容填充，不保留无意义空段。普通增量以 development 和 testing 中的日常同步规则为准。

## 7. 实现完成后自动核对（最终回复前）

- PRD：核对本次最终行为与现行 FR/AC；只有产品契约有授权的变化才修改。无变化在 DEV_LOG 注明及引用。
- DEV：更新本次任务与分工、状态、实际阻断和 DEV_LOG 引用；不重复记录实现细节。
- DEV_LOG：追加本次实际事项、相关需求和任务、实际变更的所有 File Path（新增/修改/删除/重命名）、本 Chat 归属、证据、失败/未验证项及重要用户反馈。
- TEST_PLAN：核对现有 TC、局部证据链接、调整失效用例、增加缺口及更广覆盖；没有对应 TC 时补最小设计。旧局部 Pass 不等于正式通过。
- 已有 TEST_REPORT：仅当变更影响其正式结论时标注失效范围，保留既有 RUN；需要复测则列入计划。
- 检查各文档已写入正确 Chat ID、引用可追溯、真实 diff 与记录一致、未覆盖跨 Chat 改动。发生无法写入/验证的真实阻断时如实记录已完成与未完成，先完成独立可做的部分。

## 8. 正式测试与完成

按 testing.md 执行，最终的 Test Suite 是实际项目测试代码，不仅一份 Markdown 清单；覆盖现行 Feature 全部验收条件、相关实现和风险回归，基于真实测试结果报告。开发自检和正式验证可按需审查变更。用户另行发起的正式 Feature 代码审查由独立审查 Chat 按 review.md 执行。正式审查是可选流程。

Feature 达到完成/验收条件或用户要求总结时，按 knowledge.md 提取候选。按项询问用户哪些值得写入 Docs、哪个 Skill 或其他长期知识；在确认前不自动固化。用户批准某候选后执行对应写入、检查与 CLOSE 更新，不因其他未选候选阻断。

## 9. 汇报

回复应简明，按本次实际工作说明：决定及冲突处理、实现及变更文件、文档同步、验证与尚未覆盖、必要下一步。仅讨论时给方案与待决问题；实现时给事实和证据；正式测试与知识提取分别使用对应报告。不要把计划、静态自检、旧版本结果或用户未确认意见写成已验收。
