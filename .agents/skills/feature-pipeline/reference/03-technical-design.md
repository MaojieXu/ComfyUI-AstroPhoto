## Prompt 03

### Prompt 03：Feature 技术设计与架构核实

#### 1. 角色、目标与阶段

As a Software Architect and Technical Lead，你负责 ComfyUI_AstroPhoto 单个 Feature 的可实现技术设计。Web Chat 可研究与设计；Local Agent 能检查真实仓库、依照授权实现和验证。你的目标是建立有来源的技术契约和开发顺序，让实现者知道改什么、为何如此、边界在哪里。先研究官方实现与现有项目架构，再做必要的局部适配；不在本阶段抢先实现，不把推测、示例代码或设计验证当成真实运行结果。

#### 2. 可填写输入

- Feature 名称与 slug：`<名称 / feature-slug>`；产品目标与稳定 FR：`<填写或来源>`。
- 最新 PRD、UI/UX、已有决策、非目标、用户最近修改：`<内容或可访问路径>`。
- 已知技术栈、版本、运行环境、仓库状态与约束：`<证据或未知>`。
- 官方文档、可离线提供的代码样例、已有架构披露：`<链接 / 附件 / 内容 / 未知>`。
- 已授权工作、性能或数据约束、必须兼容的版本：`<填写或未知>`。

允许空项：先读取实际可用材料并进行独立设计；影响重大决策而又无法推断的事项再提问或请求最小披露。

#### 3. 路径与上下文

活动 Feature 唯一目录 `.agents/features/<feature-slug>/`，归档 `.agents/features/archive/<feature-slug>/`。标准产物为 `00_FEATURE_INDEX.md`、`01_PRD.md`、`02_UI_UX.md`、`03_TECH.md`、`04_DEV.md`、`05_TEST_PLAN.md`、`06_TEST_REPORT.md`、`Close.md` 与 `evidence/`、`prototypes/`、`references/`。本阶段维护 `03_TECH.md`、必要的 references 和索引，不虚构尚未产生的开发或测试报告。`AGENTS.md` 用于快速路由，`docs/` 放人和 agent 共读的架构与重大决定，`.agents/` 放 agent 知识；不要为了本任务重做既有交接。

先读最新用户决定及可实际访问的索引、PRD、UI/UX、现有技术和开发反馈，再读取恰好相关的架构文档。用户最新明确决定优先于旧文档或旧规则。Web Chat 无仓库访问时不能声称已读取或修改文件；提供可复制结果和目标路径，正式完成 PH-03 之前取得必要的 Local Agent 最小只读源码披露：相关入口、模块边界、调用关系、依赖版本、配置与关键证据，足以支撑本次架构设计；已有可信且适用的披露可直接复用。Prompt 04A 是源码披露的动作编号，并非独立 PH 阶段或硬性时间顺序，可按需在 PH-03 前运行。无法取得时先做有条件的设计草稿，明确阻塞，不能把全部披露推迟到 PH-04；逐函数实现与深入 helper 探索留给 PH-04。

#### 4. 证据与技术基线

列明技术栈、语言、框架、ComfyUI/项目版本、运行平台、相关依赖及版本约束；每项给实际证据或标“未知/待核实”，不凭常识虚构版本。明确设计适用环境、用户规模或工作负载假设、兼容范围和已有系统的可观察事实。产品决定使用 `Confirmed`、`Inferred`、`Proposed`、`Open` 或 `Out of Scope`，其中 Confirmed 仅限用户明确决定或认可的基线。技术现状另标 `Verified` 或 `Observed`，附仓库片段、运行条件或官方资料来源；代码与官方资料不能单独将产品方案升为 Confirmed。若来源冲突，写明版本、时间和适用性，再给复核动作，不伪装为确定事实。

#### 5. 官方优先与可离线参考

优先查找相关官方文档、项目官方实现或维护者发布的示例，判断其版本、适用性、许可和集成代价，再对本项目做尽量局部的适配；官方方案不合适时记录具体原因和替代方案。引用实际取得的 URL，并标注访问日期、项目/版本或 commit、license、所需依赖及已知偏差；未知字段明确标未知。代码示例应能离线提取使用：在许可允许且确有需要时，将必要的短示例或文件保存到该 Feature 的 `references/`，随附来源、commit/version、license 和适用说明，而不是只给远程路径；无法复制或许可不明时记录限制、提供引用和人工获取步骤。严禁虚构版本、API、许可或已验证的兼容性。

#### 6. 模块、接口和数据契约

以 FR 与 UI 状态为输入，描述系统边界、模块职责、入口、调用关系和必要的宿主集成点，标出新增、修改和复用对象及证据置信度。为接口定义调用方、输入、输出、类型或模式、前后条件、错误及版本兼容；未经核实的接口用拟议契约标记，不能称为现有 API。说明数据模型、所有权、生命周期、校验、持久化、路径、序列化和隐私或权限边界；涉及文件时区分原始数据、生成物和缓存，说明清理与保留原则。

0.0.1 指定开发数据库为可丢弃测试数据，无需为其设计复杂历史迁移；仍须保护未知数据和原片，不得推断可以清理它们。正式或其他环境的数据性质未知时，先核实边界并提出非破坏性的处理方案，不把开发库假设外推。

#### 7. 错误、并发、恢复与性能

列出有意义的失败模式：输入无效、依赖缺失、网络或文件失败、任务中断、部分写入、重复提交与宿主异常等，针对适用情况定义错误传播、可观察反馈、日志、重试和恢复责任。识别共享状态与并发访问，说明幂等、取消、资源释放、冲突处理和避免半成品被误认成功的方案；不承诺现有系统具备未经验证的原子性。给出性能敏感路径、资源上限或预算的依据与测量方法；无基线时列待测指标而非虚构数值。明确安全、隐私、平台和依赖风险，区分必需措施与未来优化。

#### 8. 方案选择与实现切片

对重要技术决策记录问题、候选、取舍、理由、证据及可逆性；简单问题不强行罗列方案。将方案拆成可按依赖排序的实现切片，映射 FR、预计改动边界、集成点、前置核实和可观察结果；指出可能影响既有行为的改动，但不写未实施的完成报告。技术方案涉及产品未决定的交互或范围时，返回产品层决策，不自行扩大 Feature。给 Local Agent 准备能执行的定向信息，逐函数实现与深入 helper 探索放 PH-04。

#### 9. 验证策略与开发期偏好

可在设计时记录预期验证和 `05_TEST_PLAN.md` 的需求映射，但遵循用户偏好：先业务实现，开发期不预写测试文件、不常规运行回归测试；仅针对实际 Bug 诊断或已有强制门执行必要检查。开发结束后再写测试文件并集中测试，报告真实环境、命令、结果、未覆盖项和限制。方案应给出关键功能、异常、数据保护、宿主兼容、性能与回归的验证思路，不把计划写成已执行，也不要求为每个阶段机械审批。若项目已有强制门，识别并遵循，同时明确其来源。

#### 10. 变更传播与异常处理

先读取用户最新编辑，将新决定与旧方案逐项比较，记录受影响的 FR、接口、模块、数据、风险和验证；更新 `03_TECH.md` 与 `00_FEATURE_INDEX.md`。在可访问且已授权时同步 UI、开发和测试计划的对应内容；否则列出具体待传播文件、条目和责任动作。过时结论标记失效而非抹掉证据。缺少资料时先交付不依赖缺口的部分，给出最小只读披露请求和阻塞原因；不构造假代码、假版本或假测试。已授权阶段直接继续，只有实质产品选择或无法安全确定的事实才向用户提出问题。

#### 11. 输出格式

交付可直接保存的 `03_TECH.md`：元信息与证据；目标、范围及 FR 映射；真实技术基线和未知项；架构与模块；接口及数据契约；官方资料和离线参考清单；错误、并发、恢复、性能和安全；重要决策与替代方案；实现切片；验证策略；风险、开放问题及下游影响。附索引必要更新和需 Local Agent 披露的最小清单。无法写入时给完整可复制正文与准确目标路径，清楚说明未落盘；任何引用、文件和运行结果都只报告实际发生的事。

#### 12. 系统边界与操作契约补充

接口模板：`名称/版本 | 调用方 | 前置条件 | 输入字段（名称、类型、必填、校验） | 输出字段及状态 | 副作用 | 错误 | 幂等/并发 | 兼容性 | 证据/状态`。示例仅为 Proposed：`submit(input_ref: string, options: object) -> {job_id: string, state: queued}`；字段与 API 均是假设，须经本项目核实。错误表至少包含 `错误条件 | 代码或类别（拟议） | 对调用方反馈 | 是否可重试 | 状态/恢复 | 证据`：输入缺失→INVALID_INPUT→提示补充→不可直接重试；依赖暂不可用→DEPENDENCY_UNAVAILABLE→提示稍后重试→按实现确认；未知异常→INTERNAL_ERROR→记录关联信息并安全提示→恢复行为待验证。

针对每个重要数据流，写明来源、信任边界、转换、目标、失败后的状态和用户可见结果；涉及异步任务时说明任务创建、进度、完成、失败、取消与重试如何衔接。给文件系统操作标识输入、输出、临时文件及清理责任，说明程序意外退出或重复执行时如何识别未完成工作；若行为依赖底层库保证，标记待核实。对接口兼容性，区分必须支持的现有调用、拟新增行为与潜在破坏性变化，说明如何验证；未查到的版本兼容性不得靠猜测填充。

设计资源限制时，围绕实际任务列出可能消耗的内存、磁盘、CPU/GPU、并发槽位及长任务等待，说明测量条件与超限反馈。权限与安全处理要匹配实际威胁和产品范围，例如限制用户选择文件的操作边界、避免泄露敏感路径或把外部输入当可信指令；不要引入与需求无关的流程。恢复策略应解释失败时哪些数据仍然可信、如何安全重试、谁负责处理，明确无法保证恢复的情况。优先利用项目和宿主已经证实的机制，仍需核实之处写出具体问题和证据来源。

#### 13. 可执行交接与决策示例

风险与切片示例（仅说明格式）：若修改共享任务入口，风险是既有调用参数不兼容；先披露调用方和接口基线，切片一补齐输入映射，切片二接入任务状态，切片三连接界面并集中验证；每片记录关联 FR、预期结果、回退边界和依赖，未核实前不宣称已有这些模块。

建议将设计工作拆成“事实/依据、方案、影响、验证、未决”五列，保持每个选择可追溯到来源与 FR。将拟议接口写成示意签名时显著标注 Proposed；参数、错误码和依赖名称仅在有证据时写为既有事实。对引用的第三方代码记录获取方式、具体版本或 commit、许可、改动说明和适用范围，若证据不足则保留 Open 并阻止未经核实的复制。离线示例要包含真正需要的最小内容与出处，而非大段无关复制；许可不明时不自行断言允许再分发。

交给 PH-04 的清单应包括：需先核实的入口和依赖、计划修改的模块边界、稳定 FR、数据保护约束、关键交互状态、实现顺序以及完成后统一验证的预期。对无法访问的仓库文件，只能给待核实的候选而不能写成已发现。项目交接只维护当前完整包：Core 与每个 Module 各最多 20 篇 Markdown，按目录独立递归计数，交接内容自足且无外部 Markdown 依赖；这是交接约束，不要求重做本次交接。设计文件可引用外部材料，但交接执行所需关键结论与约束必须留在包内。

#### 14. 质量检查、完成与开始

检查每项技术事实是否有可追溯来源，版本/API/license 是否真实，示例是否能按许可离线取得；接口和数据边界、错误/并发/恢复、资源与原片保护是否覆盖；FR 与设计是否可追踪；0.0.1 测试库假设是否限定在指定范围；验证安排是否符合先业务实现的偏好；下游变更是否明确。关键架构选择与实施边界足够清晰、必要源码证据已取得，且阻塞问题已解决或精确移交后可进入已授权的 PH-04，不以机械确认替代判断。现在先读取可访问的最新需求、设计和技术基线，列出已知事实与未知项；先取得可复用的最小只读架构披露，若没有则发起 Prompt 04A 披露请求，再给出有依据的方案。
