# 需求理解与 PRD

## 入口与确认

1. 阅读活动 Feature 的当前 PRD、DEV 及相关源代码，理解用户目标与真实现状。必要时沿前端、API、后端、数据、MCP、外部程序的实际业务链路追踪；不要只按文件名称猜测。
2. 从自然语言提取目标、业务规则、对象/状态、交互、失败和恢复预期、边界、验收标准；区分用户明确决定、源码事实、Agent 推断和待决问题。
3. 先在 Chat 中提出可讨论的分解策略：理解、涉及范围、可复用实现、预计任务、依赖/风险、局部与正式测试方向。按用户请求的深度展开，不为简单修改强制长文或原型。用户要求“先记录方案”可把方案放 DEV 的 Proposed 区并标注 Chat，不能作为已确认需求。
4. 用户明确确认后先更新现行 PRD，再更新 DEV。直接明确的行为指令即是确认，无需再次审批；若用户只确认方案、未授权编码，停在文档和计划；明确要求开始时按计划推进。讨论尚未确认的事项留在 Open/Proposed，不擅自实现。

## PRD 信息模型

PRD 是产品行为契约，不是任务日志。

- Feature 背景、范围和非目标：简洁描述为什么做、服务对象、边界。
- FR/AC：用稳定 ID；AC 应具体可验证，描述可观察结果而不是绑定某个函数实现。关键状态、输入输出、错误、恢复、兼容行为及重要非功能约束按需要记录。
- 每个 FR 可有多个 AC，例如 FR-chat1-001 / AC-01（完整引用 FR-chat1-001/AC-01）。旧有 ID 原样使用。
- 当前已确认行为和重要决定放现行区，未确定条款与已失效行为明确分离。每次实质变更保留修订号、Chat、真实时间、来源/依据、替代关系；引用旧条款摘要或历史条目，不需重复全文。
- 简单 UI 文案、行为、交互放在 FR/AC 中。复杂视觉、原型、状态流转如确有必要，创建按需 UXUI 契约，PRD 引用它而非复制。

## 如何分类用户反馈

| 反馈 | 文档行为 |
| --- | --- |
| 新增/明确改变用户可见行为 | 更新 PRD 的有效 FR/AC；更新 DEV 与相关覆盖 |
| 修改多个方案或否决原需求 | 依公共冲突规则判断；明确 superseded，保留历史 |
| 对现有规则的 Bug 修复、内部重构 | PRD 只读，DEV/DEV_LOG 引用现行需求 |
| 技术约束变化 | DEV 的设计/任务；重大独立契约可用 TECH |
| 用户纠正 Agent 工作方式 | DEV_LOG 知识候选细节；不直接升格为产品规则或永久 Skill |
| 只讨论且不允许写 | 只给分析与候选，不写 Feature 文件 |

## 冲突示例

原 FR-chat1-001 v1 要求断开后不重连。用户在 chat2 明确要求自动重连三次：

- 新现行 FR-chat1-001 v2：自动重连三次；AC 对次数、成功/失败进行可测试描述。
- 修订历史：chat2、确认依据、v2 supersedes v1。v1 只作为历史。
- 未完成的旧 TASK 标记 Superseded/Cancelled 或按新目标修订；保留原作者。
- DEV_LOG 记录决断及实际实施（未编码注明）；TEST_PLAN 调整旧“不重连”测试并增加重连次数、失败恢复等场景。
- 已有正式 RUN 仍是旧版本的真实记录；标注对新行为不再适用。若用户仅确认需求，不擅自编码。

若“自动重连”与“用户主动断开后禁止重连”看似冲突，先判断二者是否可分别适用于异常断线与主动断开；能依据已有决定解释就自主收敛，不能确定便具体询问用户，而不是默认取消整个旧功能。

## 输出

按 PRD 模板写入或增量更新，验收条款和待决事项能被 DEV、TEST_PLAN 直接引用。仅讨论时返回分解策略、明确假设和需用户决定的少量问题。
