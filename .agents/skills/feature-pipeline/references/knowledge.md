# Feature 完成与知识沉淀

## 1. 完成条件与范围

在 Feature 达到已确认的验收条件、用户确认完成，或用户明确要求总结时启动。引用 TEST_REPORT 的最终范围、RUN、未覆盖及已接受的风险；若仅做中途知识回顾，明确不是最终验收。没有必要再执行独立验收审计、重复代码审查或生成另一份测试结论。缺陷/测试未完成不虚报已关闭。

## 2. 提取候选

在本轮或 Feature 全过程的 PRD、DEV、DEV_LOG、TEST_PLAN、TEST_REPORT、实际代码和可用的用户反馈中，寻找真实有长期复用价值的内容。关注：

- 可重复的需求理解、实现、调试、验证、集成、交接 Workflow。
- 真实证据支持的项目架构/模块职责、接口契约、技术坑、资源管理、可复现解决方案、测试模式。
- 用户对 Agent 的明确修改意见及被纠正的行为（区分产品需求和工作方式）。特别保留用户明确纠正但只适用于本次的上下文，避免自动泛化。
- 曾失败或被否决的方案及其原因；若仅 Feature 特有历史，留在 DEV_LOG，不提升为长期规则。

先查看实际存在的 Docs、Skills、项目规范及其适用范围；已有知识时优先补充或更新，不重复新建。不是所有发现都值得沉淀；如果代码/测试已清楚表达且不存在额外复用价值，可选择不提取。

| 候选类型 | 推荐归属 |
| --- | --- |
| 项目架构、接口、长期技术约束、维护知识 | 现有 Docs |
| 跨任务重复执行的操作流程、Agent 行为约定和用户确认的工作偏好 | 现有 Skill 或合适的新 Skill |
| 能由代码和测试长期表达的规则、fixture、复用实现 | 已有测试/代码工具（提出候选，不自行扩展范围） |
| 当前 Feature 特定选择、旧尝试、一次性记录 | 保留该 Feature 历史 |

## 3. CLOSE：用户选择是决策，而非额外审批阶段

CLOSE 只负责简要结论引用和候选记录，不重复 DEV/TEST_REPORT 的正文。

每个候选有 K ID、Chat、时间、来源（FR/DEV/TC/RUN 或用户反馈）、建议的准确内容、为何可复用/适用范围、现有或建议目标文件、与已有知识的关系、状态 Proposed/Approved/Rejected/Applied/Skipped。不要编造用户原话或跨 Chat 隐式记忆。已有记录留历史；不同 Chat 新增候选标注来源。

向用户集中提供按 ID 的候选与建议目标，让用户选择哪些写入 Docs/Skills、哪些保留或修改。**未经用户确认不得修改全局 Docs、Skill 或 Agent 指令以固化经验。** 用户已明确选择某条则直接落实，不再次确认；其他候选继续保持未选。针对已获准的具体项目文档一致性修正按当前授权处理，不将其混同为永久知识沉淀授权。

落实时查目标实际内容、保留现有规则、最小修改；如更新 Skill，遵循可用的 Skill 创建/更新工作方式。完成后记录实际写入文件、Chat、摘要、验证以及每条候选的状态；若未成功如实记阻断。

## 4. 归档或重开（仅需要时）

如果用户要求归档，先确认当前验收范围与历史证据位置；遵循项目已有的归档路径，不默认删除或移动工作区代码。保留 PRD/DEV/DEV_LOG/TEST_PLAN/TEST_REPORT/CLOSE、已有 REVIEW 和必要证据。用户明确重开归档 Feature 时恢复/引用活动目录，保留历史 RUN 和 CLOSE，按新有效需求续开发，不重写历史。添加新的开发及验证记录，并标记旧验收不覆盖新的范围。
