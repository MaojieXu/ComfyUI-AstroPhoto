# 测试计划、测试工程与执行报告

## 目录

- 日常 TEST_PLAN
- 正式全量测试准备与套件建设
- 执行、缺陷与复测
- 测试与代码审查的关系

## 1. TEST_PLAN：持续覆盖设计

TEST_PLAN 从开发第一轮开始随 Feature 增量演进。以现行 PRD FR/AC 为预期依据，结合 DEV 任务、DEV_LOG 的实际改动路径及局部证据、现有代码与测试，辨认业务链路和缺口。只设计当前需要的范围，不仅根据实现代码猜测验收条件。

每个测试用例/覆盖项记录：

- TC ID、创建/修订 Chat、时间、关联 FR/AC 与 TASK/DEV/相关版本。
- 测试场景与风险优先级，必要前置、数据、环境、步骤、可观察预期。
- 类型与层次（单元、接口、集成、端到端、人工、非功能或回归），预期测试文件/函数或现有实际映射。
- 设计/实现状态（Planned、Implemented、Superseded 等）；已执行的局部验证用 DEV_LOG ID 和证据链接，必要时标明当前仍适用或 Stale；正式 RUN 仅引用 TEST_REPORT，不在计划里另维护一份 Pass/Fail 历史。
- 失效/替代关系、尚未覆盖的风险和后续验证。

### 每次实现后的增量更新

核对已有 TC 是否仍覆盖本次变更；可以关联已有 TC，不要求每次制造新用例。补充新的正常场景、异常/边界、状态转换、依赖/接口接线、数据一致性、故障恢复、回归风险。局部验证通过只是局部证据；正式验证仍按范围待执行。关联其他 DEV/TC，标记已失效的旧测试并保留历史。测试预期必须符合现行 FR/AC；遇到未确认产品规则走冲突协议，不为了让实现通过而降低断言。

## 2. 正式全量测试：读取输入与构建测试工程

用户明确要求全量/正式验收、或已授权完成整个 Feature 时，执行完整验证，而不只输出一份测试建议。

1. 核对 **PRD、DEV、DEV_LOG、TEST_PLAN** 和实际源码/测试目录/项目测试约定；明确全部有效 FR/AC、涉及 TASK/DEV 和实际改动文件、受影响调用链、未完成/待验证项。确认范围与当前代码状态可识别（HEAD/比较基线及未提交/未跟踪相关文件哈希或可复核 diff）。不能把只读过的 HEAD 当作包含工作树修改的快照。
2. 若 Chat 并行开发，针对这次验证范围协调稳定的代码状态；其他互不影响的工作无需全面暂停。用可复核前后状态判断测试是否漂移；漂移则标明哪些结论无效并重测相关部分。确认缺失依赖/阻断并完成不受阻部分。
3. 集中核对覆盖：每个现行 AC 有可执行 TC 或明确未覆盖原因；每个相关实现改动评估风险及必要回归。根据现有真实测试和 DEV_LOG 的局部证据，复用、扩展、合并或补全测试，不盲目重复造文件。
4. **构建实际测试代码**：在仓库现有测试目录和工具链中新增/修改测试文件、测试函数、fixtures、数据、mock/真实集成环境等，组织完整 Feature Test Suite。覆盖正常业务、异常边界、接口与集成、状态和恢复、回归；只选与实际需求和风险相关的测试层级。不要强制每个 Feature 新建 unit/integration/e2e 目录或脱离真实技术栈。不可自动化的场景写可执行人工步骤及限制；不将未观察人工结果记为 Pass。
5. 对照计划标出 TC→实际测试文件及选择器，从测试实现核对预期、隔离、数据和可重复运行性。将所有本次新增/修改/删除测试及辅助文件作为实际变更写入 DEV_LOG（引用对应 TC 与 Chat），DEV 同步任务；测试代码变更若不涉及产品契约则不改 PRD。
6. 构建测试代码后采集实际 RUN 的最终代码、测试文件、配置/依赖及需求计划基线；执行完整 Feature 套件以及与变更影响范围相关的既有回归；用户要求全仓库测试时再按约定执行全仓库。真实项目的 pytest、前端测试、lint/build、E2E、数据库/外部程序等按实际适用性执行。避免真实数据污染，优先隔离测试环境；不能验证的部分如实记录。

### 技术栈提示（仅适用时）

若项目存在 Vue/HTTP/Python/SQLite、ComfyUI Node、FastMCP、Siril 等，关注实际浏览器交互/API 契约、注册与调用链、数据库事务和隔离、节点输入输出、资源生命周期和外部程序失败/恢复。优先使用仓库真实依赖及测试工具，不虚构设备、外部程序、结果或框架。若硬件/外部进程不可用，区分 mock 证明与真机待验。

## 3. TEST_REPORT：真实正式执行结果

每个正式运行记录独立 RUN ID、Chat、实际时间、有效 PRD/TEST_PLAN 修订、具体代码快照与范围、环境/配置、实际命令/步骤、测试文件与选择器、预期和证据引用。记录各 TC 或可复现的测试集合结果、覆盖矩阵缺口、失败、跳过与阻断；大批结果可附 assets/test-runs/ 中实际证据而非复制日志。统计只从已取得的真实结果汇总，不把未执行算 Pass。

状态可以为 Pass / Fail / Skip / Blocked / Not Run；执行证据不充分或环境缺失则相应标明。仅局部验证或代码审查不能充当正式 RUN。保留旧失败与复测记录，最新结果引用新的 RUN 和代码状态。测试套件构建文件 Path 以 DEV_LOG 为事实源，报告可列测试文件/选择器及日志 ID 便于重跑。

### 缺陷和复测

- 失败时核对代码、测试契约、环境，区分产品缺陷、测试缺陷和环境限制；关联缺陷 ID、文件/位置、实际与预期、证据及影响。
- 已授权做交付修复时，解决确认的问题并走正常 DEV/DEV_LOG/TEST_PLAN 更新，执行受影响复测与回归；若用户只要求验证/只读审查，不擅自改生产代码。测试代码的错误在授权的测试工作范围内可修正，但不能通过弱化断言来掩盖产品缺陷。
- 不自动否决尚存的其他已通过用例；根据变更的依赖和范围标记哪些旧结果不再有效，再以新快照复测。旧正式 RUN 永不伪装成新版本的结果。
- 如实总结当前需求覆盖、失败及未验证范围、剩余风险、是否达到本次验收标准。用户明确接受的例外记录为范围/风险决定，不当成 Pass。
- 全量 Feature 验证通过且无未处理阻断后报告可验收；需要用户实际使用/硬件检查时标记待用户确认，不代替用户作最终接受决定。

## 4. 测试与代码审查的关系

开发自检和正式验证可按需查看 diff，发现的缺陷和测试缺口按对应流程处理。用户单独发起的正式 Feature 审查见 [review.md](review.md)。只读审查遵守用户指定的写入范围。审查结论与正式测试 RUN 各自记录证据。
