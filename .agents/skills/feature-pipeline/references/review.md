# Feature 代码审查

仅在用户明确要求对 Feature 做独立审查、复审或回写审查结果时加载。开发自检与正式测试仍依各自流程执行。

## 交接与权限

- 开发 Chat 在 DEV.md 中记录待审 TASK、关联 FR/AC 和审查范围。独立审查 Chat 使用用户指定的实际 Chat ID，角色为 Code Reviewer，且与该任务的实现 Chat 不同。正式审查发起前确认这个角色已有接手的 Chat。当前 Chat 若是实现者，可准备交接，由用户切换到审查 Chat。独立子 Agent 只有在用户另行要求时使用，并如实标为子 Agent，不登记为独立 Chat。
- 原生审查或委派时，向审查者显式传入 Feature 路径、相关 TASK/FR、审查基准和工作树范围。保留当前入口附带的审查准则与回报格式。普通 Chat 调用时使用下节准则。
- 正式审查及复审请求默认包含本轮 Feature 记录。身份已明确且入口可写时，直接按下节同步后回复。业务修复另需授权。用户指定只读时仅在 Chat 返回结果；入口只读时在报告中标明待转录，由可写 Chat 记录实际审查者与写入者。可写但缺少 Chat ID 时，主动请用户指定，取得身份后完成写回。

## 审查

1. 先读现行 PRD 和 DEV，确认有效 FR/AC、已承诺的交付范围和明确暂缓项。按需读 DEV_LOG、TEST_PLAN、先前 REVIEW、已有测试与适用的 AGENTS.md。需求或范围存在真实冲突时，列明证据和待决定的问题。
2. 确认比较基准 SHA、目标提交 SHA 或可辨识的工作树快照。按用户指定范围查看暂存、未暂存和未跟踪文件，记录排除项。复审只核对指定发现及相关变更。工作树漂移时说明受影响的结论和复核范围。
3. 报告本次变更引入、可定位且可修复的问题。每条包括文件位置、触发场景、预期和实际行为、影响与建议。违反有效需求时引用对应 FR/AC。已暂缓的工作仅在引入适用范围内的连带回归时作为发现。将需求疑问、未覆盖测试和已确认缺陷分开记录。按审查入口要求输出 Markdown 和适用的行级评论。

## 记录与复审

- DEV.md 记录审查任务的 Owner Chat、Code Reviewer 角色、关联实施任务、状态和 REVIEW ID。
- REVIEW.md 按轮追加，使用 [审查模板](../assets/templates/REVIEW.md)。复用现有等价 Feature 审查记录并保留既有 ID。每轮使用未占用的 REVIEW-<审查 Chat>-<序号>，发现编号以该轮 REVIEW ID 为前缀。转录时按实际审查者标识报告来源，另列写入者与时间。即使没有发现，也记录实际审查范围和未验证项。
- DEV_LOG.md 记录写入、处置及复审事实并引用 REVIEW 或发现 ID。TEST_PLAN.md 仅在发现实际测试缺口时更新对应 TC。后续修复由实施 Chat 在获准后执行并引用发现 ID。复审追加新轮次和新快照，按原发现 ID 标明已修复、仍存在或未验证，另列本轮新增发现及待处理状态。保留旧轮次作为历史。审查结论单独保存，正式测试结果仍记入 TEST_REPORT.md。
