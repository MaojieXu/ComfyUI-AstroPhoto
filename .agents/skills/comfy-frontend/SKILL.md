# ComfyUI 前端开发

主 Agent 负责用户可见前端的需求、设计、组件选择、实现与视觉验收，遵循仓库 `AGENTS.md` 和 `DESIGN_SYSTEM.md`。先恢复用户已确认的方案及当前实现；仅要求讨论或分析时不修改业务代码。提交具体可审阅的界面方案并取得用户明确确认后实现；已批准且仍适用的方案直接沿用，发生实质变化时重新确认。

## 按需求发现并选择

1. 明确用户任务、交互及实际使用场景，核对目标 ComfyUI Frontend 版本、现有界面、组件和设计规范。优先选择同版本、同场景的宿主界面作为完整参照，再对照相关结构、内容、组件、图标、排版、间距、主题及交互状态，避免只复用局部。需要宿主接口细节时读取项目 `comfyui` Skill 的前端专题。
2. 优先检查宿主公开能力（例如原生节点控件、侧栏、设置、通知及对话框），再按需求搜索 `reference/ComfyUI_frontend/packages/design-system/` 的 README、公开导出、组件源码、类型和使用实例；设计语言查看 `reference/ComfyUI_frontend/docs/guidance/design-standards.md`，扩展开发查看 `reference/ComfyUI_frontend/docs/extensions/`。先查项目已有适配和依赖，避免重复实现；成熟上游组件符合需求时优先使用，不因已有自研组件而保留双轨。
3. 按实际需求比较候选的行为、可访问性、外观及调用方式；核对所选 npm 版本的公开导出、许可证、依赖、构建和宿主版本。参考目录的 `main` 不代表当前宿主或已发布包，源码存在也不代表可作为公开接口导入。引入新依赖前查阅官方文档，确认适用性和维护状态。
4. 使用宿主公开接口或已发布包，而非假定扩展能直接导入宿主内部 Vue 组件；Vue 等依赖按上游扩展打包要求处理。只有已有成熟方案确实不满足需求或自研具有明确技术必要性时，才设计专属实现，并说明差距和原因。复用源码时核对版本、许可、依赖及维护成本。

搜索以当前任务为准，不维护静态组件目录。参考源码不可用时检查本地已安装依赖和官方资料；无法核对的版本或行为如实列为待验证，不凭假设声称已兼容。

## 设计与验证

- 方案以相关界面整体为单位说明参照来源、选择的宿主能力或组件、主要交互和可见状态；区分直接复用、依据上游规格适配与有意保留的产品差异，解释差异原因。内部组件不可直接导入时，可在许可及公开接口边界内按其规格适配，不称为直接复用。
- 特别核对候选与实际需求的差异：例如单选项禁用、缺失值、搜索防抖与输入法组合、焦点、清除及多选行为。按任务需要检查属性、事件、插槽及调用方，必要时用最小验证确认。
- 避免扩展样式影响宿主：检查主题和工具类的作用域、全局重置、字体、图标及 portal 弹出层；不要未经验证引入完整全局主题。检查项目 CSS 是否覆盖上游组件的尺寸、字体、颜色、悬停和焦点样式；使用官方组件本身不等于最终样式一致。
- 运行与改动相关的类型检查、构建及交互测试。主 Agent 在同一目标宿主中对照批准方案和选定的原生参照检查实际渲染，按范围覆盖整体布局、组件、图标、字体、间距和交互，以及明暗主题、窄尺寸、弹出层、键盘和可达状态；必要时核对计算样式。记录实际一致之处、保留的差异和未验证事项，区分源码、模拟环境与真实宿主证据；未对照或仅外观相似时不声称严格一致。
