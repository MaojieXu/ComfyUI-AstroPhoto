# 工具名称、描述与契约

## 定义

名称表达业务对象和动作，并和相邻工具保持可区分。描述解释用途、适用及不适用情况、必要前置步骤、关键副作用、结果及后续动作；参数描述交代单位、范围、来源、默认值与示例。例子应是有效调用，不掺入不可执行的占位值。

针对每项参数检查：是否必填；是否允许省略、null、空列表或空字符串，各自代表什么；是否有互斥、依赖或条件必填；中文用户表述如何对应固定枚举；路径属于宿主物理路径还是业务逻辑路径。不要给模型猜测配置、授权或目标的理由。

返回适量结构化信息：对象名称及足以区分的上下文、实际处理状态、下一步所需引用和可恢复错误。结果数量大时分页或提供摘要/详情；不因节省 token 省略识别目标或确认副作用所需的信息。允许访问必要的机器标识，但不要让模型手工编造或变换它们。

## 身份、分页和确认

- 能用唯一且稳定的可读名称就使用名称；多个匹配时返回候选供选择。名称并不自动等同于不可变身份，修改或删除时服务应重新校验实际目标。
- 业务层短引用可降低长值回传负担，但应绑定相应调用方/会话或可信作用域、目标实例、对象、用途、请求条件和有效期；并发查询应互不混淆。作用域或有效性无法确认时明确失败，告知如何重新获取。
- 短引用不是认证、用户同意或授权。涉及确认时仍需真实用户同意及服务端校验；避免让错误消息暴露原始令牌、私密路径或其他敏感值。
- MCP 协议的 tools/list 等列表分页使用所协商版本规定的 opaque cursor；业务工具自己的分页接口可有不同设计。不能因为模型使用短引用就更改协议层客户端/服务器的分页语义。
- 业务分页通常不是冻结快照；如不能提供快照一致性，应如实说明并考虑数据并发变化。

### 项目示例：续读

中文请求“查找名称包含 M31 的素材，每页 20 项”可由 library_list 接收 JSON 参数 {"query":"M31","limit":20}。如果结果有更多项，使用服务实际返回的 continue_with 值继续调用，避免自行重写编号或重复填写筛选条件。续读引用关联原工具、条件和目标实例；过期或跨作用域时明确要求重新查询。这里是 AstroPhoto 源码中的设计；当前已连接会话是否加载这一版本必须另行核实，不要求其他 MCP 服务照搬。

## 结果和错误

区分协议层无效请求与工具执行失败：遵循协商版本的 JSON-RPC / MCP 错误规则；业务失败应通过客户端可识别的工具错误表达，并带稳定、可理解的原因和可执行下一步。不要把失败、部分完成或状态不明描述为成功。检查 structured content / output schema 与对应文本是否一致，并核对客户端实际支持。

可行时标明字段“已提交修改/清空”与“值实际发生变化”的区别，避免把两者混为一谈。

## Schema 与厂商边界

MCP 的 inputSchema / outputSchema 以协商协议及 SDK 为准。OpenAI Function Calling 的严格模式对对象和必填字段有额外约束；这是该接口的规则，不是所有 MCP 客户端的通用要求。按目标客户端检查支持的 JSON Schema 子集与严格模式行为；严格结构只约束形状，不证明值、目标、权限或语义正确。
