# 从任务定位 MCP 工具

## 找到真实边界

选取用户代表性目标，逐步写出 Agent 已知什么、要判断什么、需要哪些结果、下一步如何使用。根据业务语义把动作分为读取、修改、任务执行和结果获取；检查目标、调用方和结果是否需要跨步骤保持一致。

- 检查现有 MCP 工具和底层公开 API，能复用就不要增加工具；不要只按 API 路由数量设计工具。
- 能在服务内安全完成的确定性操作，不要求 Agent 编排大量细碎调用。存在独立的用户决策、权限或可观察状态时，再考虑明确分步。
- 为职责接近的工具写清对比。例如“搜索已注册的节点类型”和“查找当前画布里的节点实例”是不同目标。
- 判断一个工具在结果过多、多个匹配、对象变化和操作结果不明时，是否能让 Agent 做出正确下一步。没有足够信息时返回可辨认候选或要求补充条件，而不是猜测。
- 渐进发现是权衡：原生 MCP 工具发现、SDK 的搜索/目录能力或应用内分类各有成本。核对目标客户端是否保留类型、注解、权限与调用链路；不要因工具多就默认增加通用 call_tool 转发层。

## 流程案例：关联删除

任务：删除一个有项目引用的素材。

1. 按可读名称找到唯一素材；缺失或重名时返回可区分候选。
2. 查看影响，明确哪些引用被解除、文件将如何处理。
3. 将影响告知用户并取得明确同意。
4. 提交与目标和影响快照绑定的确认引用；服务端重新核对对象、授权、关联及文件保护。
5. 返回实际删除结果或明确冲突/部分失败，让 Agent 按回执处理。

此例适用于项目已要求预检和确认的删除操作；不意味着普通查询或所有删除都必须采用相同流程。用户的关联确认不能解除对共享或已变更文件的保护。

## 审查输出

按真实任务列出建议工具、输入从哪里来、结果提供给下一步什么、可能失败及补救。指出复用或合并的依据、未覆盖场景和待确认的产品取舍；不把推测写成现有行为。
