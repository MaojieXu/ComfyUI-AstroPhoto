# MCP 工具设计

先理解 Agent 要完成的任务，再设计工具。将协议要求、当前 SDK/客户端能力、厂商建议、项目规则及未经验证的假设分开；具体结论以项目当前协议版本和实际实现为准。

## 工作方式

1. 确认本次是设计、审查还是实现，以及用户任务和授权范围。阅读适用的项目规则，查看现有工具注册、公开 API、SDK 及调用链；涉及已连接服务时区分源码版本和当前会话实际发现结果。优先复用已有能力。
2. 从真实任务梳理调用流程，列出 Agent 每步已知信息、要得到的信息、工具选择依据和失败后的下一步。检查职责重叠与遗漏；按需阅读 [流程与定位](references/planning.md)。
3. 为每个新增或变化工具明确名称、作用/边界、调用时机、参数来源和含义、返回与错误、副作用、下一步，以及与相邻工具的区别；按需阅读 [工具契约](references/contracts.md)。
4. 在有长任务、跨调用状态、删除或外部副作用时检查进度、取消、重试、权限和作用域；按需阅读 [运行与恢复](references/operation.md)。短编号、延迟发现和异步任务是可选方案，不是每个工具的必需组件。
5. 用实际用户场景审查工具是否可选、可填、可续用、可恢复；区分确定性契约验证与模型能力评测。按需阅读 [评估](references/evaluation.md)。
6. 报告依据、现状、设计和未验证项；用户只要求方案或审查时不修改运行时。涉及本仓库实现时遵守当前 AGENTS.md 和现行 Feature 决策，不凭过往案例引入额外需求或兼容层。

## 原则

- 工具应表达有意义的任务边界，勿逐一镜像底层 API，也勿为了减少数量把不同权限或副作用塞进一个模糊工具。
- 优先提供可读、无歧义的参数与高信息密度结果；名称不唯一时返回候选，不能猜测目标。机器标识的真实性、作用域与并发由服务维护。
- 用户明确同意与系统校验是不同事项；描述、短编号、模型输出或注解均不能替代服务端授权、确认和业务保护。
- 针对小模型减少选择、参数和上下文负担，但不承诺效果；在真实模型上验证之前标明假设。
- 资料追溯或版本复核时阅读 [研究来源](references/sources.md)；不要把特定厂商的 Schema 规则或 AstroPhoto 案例当作 MCP 通用要求。
